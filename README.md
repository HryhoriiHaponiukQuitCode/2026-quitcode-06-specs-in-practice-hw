Домашка шостого воркшопу курсу QuitCode **«Modern Development with Agentic AI»**.

> Воркшоп 6: **Специфікації на практиці: старт командного проєкту**
> Автор: В'ячеслав Колдовський — Dev AI Consulting (dev-ai.dev)

З цього тижня ви працюєте в командах над одним продуктом до кінця курсу. PM пише специфікацію: вимоги, межі,
критерії приймання (AC). Кожен розробник реалізує її у своєму форку, зі своєю базою й своїм деплоєм. Кожне наступне
заняття додає в проєкт новий шар, а на demo day PM показує, як одну спеку прочитали й реалізували по-різному.

**У цьому репозиторії застосунку немає.** Код живе в репозиторіях команд. Тут — інструкції, брифи, зразки й
місце для здачі.

## Навіщо це в роботі

Клієнт пише одне речення: «якщо відсутність покриває обидві посади — два записи». П'ять розробників з агентами
реалізують його п'ятьма способами, і кожен вважає, що зробив правильно. Агент не перепитує, а заповнює діру
найімовірнішим здогадом. Тому на старті клієнтського проєкту агенції потрібні три речі, і ця домашка — рівно вони:

- **Спека, яку перевіряє машина й розуміє людина.** Вимоги з `SHALL`, сценарії з AC ID і з числами, межі зрізу
  й відкриті питання, записані до коду, а не з'ясовані після демо.
- **Шлях питань і версій.** Розробник не вгадує, а питає (issue), PM відповідає публічно, зміна поведінки стає новою
  версією спеки (тег). CI форку попереджає, що вийшла нова версія, а після синхронізації показує нові
  критерії, яких ще немає в матриці відповідності форку; змінені критерії розробник звіряє за diff версій спеки.
- **Старт проєкту з нуля за кілька годин, а не за тиждень.** Репозиторій, PR-флоу, ruleset, секрети в правильних місцях,
  Supabase через міграції, Vercel з preview на кожен PR. Усе це агенція повторює для кожного нового клієнта.

### Своя реалізація

Кожен розробник реалізує спеку сам: це й порівнюємо на demo day. **Можна:** обговорювати спеку, читати issues і
відповіді PM, ділитися порадами з бутстрапу, брати з шаблону й демо-репозиторію інфраструктуру тестів (наприклад,
`tests/db/supabase-pglite.ts` з демо) з посиланням на джерело в PR («взято з <посилання>»). **Не можна:** копіювати
код, міграції чи тести з форку колеги, зливати чужі гілки у свій форк, давати агенту чужий форк як контекст. Збіги
перевіряємо; оцінюємо лише власну роботу.

Що за це знімає бали (решта причин — у «Що знімає бали» кожного треку):

- **Розробник:** код, міграції чи тести з форку колеги без посилання на джерело — 0 за C.
- **PM команди `leave-portal`:** вимоги, сценарії чи продуктовий контекст (`product/`), скопійовані з
  [`examples/leave-portal/`](examples/leave-portal/) або демо-репозиторію, — 0 балів за відповідне завдання (A або B).
- **Усі:** справжні назви клієнта, імена людей, адреси чи суми в будь-якому файлі, issue чи PR (зокрема в історії
  git) — 0 за A.

## Як пов'язані репозиторії

```text
шаблон koldovsky/2026-quitcode-06-project-template
  └─ «Use this template» → upstream PM  <pm>/<team-slug>      product/, openspec/, теги spec-v0.1, spec-v0.2
        ├─ fork → <dev1>/<team-slug>   код, міграції, тести, docs/; свій Supabase і Vercel
        ├─ fork → <dev2>/<team-slug>
        └─ …
```

- **Шаблон** уже несе шари WS3–WS5: `AGENTS.md` і `CLAUDE.md`, команди `/opsx:*` і `/conformance`, скіли
  `spec-clarify` і `spec-review`, Supabase MCP лише на читання й заборони деструктивних команд (обидва діють лише в
  Claude Code), CI, шаблон PR, форму issue «Питання до специфікації», `.coderabbit.yaml`.
- **Питання до спеки** — issue `spec-question` в upstream (форма з варіантами й рекомендацією). Відповідь PM
  потрапляє в `product/decisions.md` і, якщо змінює поведінку, у нову версію спеки.
- **Релізи спеки** — git-теги `spec-v0.1`, `spec-v0.2` в upstream. Розробник забирає тег у форк гілкою
  `sync/spec-vX.Y`, а `npm run spec:source` і `npm run ac:coverage` у CI форку перевіряють, що спека збігається з
  тегом і що кожен AC має рядок у `docs/conformance.md`.
- Розробник **не змінює** `product/` і `openspec/specs/` у форку. Пропозиція змінити спеку — лише PR в upstream або issue.
- **Виправлення шаблону** після дня 0 — коміт у шаблоні й оголошення в чаті курсу з SHA. PM переносить його в
  upstream `git cherry-pick` (PR «Оновлення шаблону»), розробники отримують із наступним тегом спеки.

## Тиждень

Дні календарні (з вихідними); «кінець дня N» — 23:59 за Києвом N-го дня після заняття (день 0 — день заняття).

| Коли | PM | Розробники |
|---|---|---|
| **День 0** (на занятті й одразу після) | на занятті («Старт зараз», у часі Q&A) — upstream із шаблону; далі ruleset, мітка `spec-question`, заступник (collaborator) | бутстрап: форк, Supabase, Vercel — **не чекаючи на спеку**; до кінця дня 1 — перший PR: `docs/bootstrap.md` |
| **До кінця дня 2** | тег `spec-v0.1` — перший зріз | синхронізація `spec-v0.1`, читання спеки; тести з AC ID — лише після злиття `sync/spec-v0.1` |
| **Дні 2–4** | відповіді на issues; до кінця дня 4 — тег `spec-v0.2` | питання (issues), реалізація за `spec-v0.1` і відповідями |
| **Дні 4–7** | нотатка PM, здача | реалізація, синхронізація `spec-v0.2`, здача |

Здача — до кінця дня 7. Час тегу — коли тег з'явився в GitHub (push або Publish release; журнал подій репозиторію), а не дата коміту. Тег
`spec-vX.Y` після push не переносимо й не видаляємо: помилка — тег-виправлення `spec-vX.Y.1` (наприклад, `spec-v0.1.1`); `spec-v0.2` лишається релізом після питань.

> ⏱ **Скільки це займає:** PM — **7–8 годин**, розробник — **9,5–10,5 годин** за тиждень, без бонусу. Це сума
> бюджетів кроків у таблицях на початку [walkthrough-pm](docs/walkthrough-pm.md) і [walkthrough-dev](docs/walkthrough-dev.md).
> Розробнику найбільше часу йде на бутстрап (~3 год) і реалізацію (4–5 год), PM — на перший зріз і цикл уточнень.

### Рубрика PM: що дивимось

- **A (25):** upstream створено з шаблону, публічний; ruleset на `main` (PR + статуси `spec`, `app`); мітка
  `spec-question` існує. `vision.md` — одна сторінка з 2–4 вимірними ознаками успіху. `glossary.md` — 8–15 термінів
  з «Не вживаємо». `roles.md` — ролі проєкту замість `member`/`admin` шаблону, матриця роль × сутність × дія
  без порожніх клітинок. `roadmap.md` — рядок WS6 (перший зріз) і зріз на кожне заняття WS7–WS11.
  `denylist.txt` — лише нейтральні внутрішні слова, яких не має бути ні в спеках, ні в коді й документації
  (кодові назви, заглушки з чужих шаблонів на кшталт Contoso), якщо такі є;
  справжні назви клієнта — у локальному `product/denylist.local.txt` (не в git) і секреті `SPEC_DENYLIST`.
  У `openspec/config.yaml` заповнено рядок `Продукт:`. Усе через PR зі зеленим CI.
- **B (40):** зміна заархівована в гілці до merge, PR злито merge-комітом, тег `spec-v0.1` стоїть на коміті `main`.
  `proposal.md` має всі розділи з правил шаблону в їхньому порядку: Why, What Changes, Capabilities, Users & roles,
  Non-goals, Assumptions, Open questions. What Changes — з AC ID; Capabilities — `### New Capabilities` /
  `### Modified Capabilities` і свій `specs/<capability>/spec.md` на кожну можливість; Users & roles — таблиця;
  Non-goals — справжні виключення з причинами; Assumptions не порожні; Open questions — нумеровані Q1… без
  відповіді, свідомо відкладені з позначкою, що у `spec-v0.1` їх не реалізують, або «—», якщо всі питання закрито й
  відповіді внесено у вимоги чи Assumptions. Дельта: 3–5 вимог, 6–10 AC;
  кожна вимога — одне речення EARS з `SHALL`/`MUST`; кожен сценарій — `#### Scenario: AC-<AREA>-<NN> …`, один
  критерій, конкретні числа й дати, без кліків по UI і без назв таблиць чи API; на кожну вимогу є негативний шлях.
  CI (`spec`) зелений. У PR зміни є розділ `## spec-review` зі знахідками й рішеннями. Запис `spec-v0.1` у `CHANGELOG.md`.
- **C (25):** на кожне issue, відкрите до тегу `spec-v0.2`, є відповідь PM в issue, і кожне таке рішення записане в
  `decisions.md` (пізніші issues в C не оцінюються — walkthrough-pm, крок 8): питання з `#N` → відповідь → що
  змінилось → версія. Дубль PM закриває коментарем «Дубль #N — відповідь там» і Close as duplicate — це теж
  відповідь; у `decisions.md` — один рядок на питання з усіма номерами. Зміна `clarify-…`: MODIFIED з повним
  блоком вимоги й незмінними AC ID, нові правила — з новими AC ID. Тег `spec-v0.2` зі щонайменше одним MODIFIED або ADDED, запис у `CHANGELOG.md`.
  Issues закрито з посиланням на зміну.
- **D (10):** щонайменше 3 розбіжності: AC і цитата → два чи більше прочитання з посиланнями (issue, PR, рядок у
  форку; логіни, не імена) → що в тексті спеки це дозволило → що зробив PM. Якщо команда дала менше трьох
  розбіжностей, бракуючі пункти — «прогноз» без посилань (див. «Що знімає бали (PM)»).
- **E (+5):** друга зміна у відкритому PR зі зеленим CI і `spec-review` **або** порівняння зі Spec Kit — у файлі здачі.

### Що знімає бали (PM)

Це типові причини, через які не зараховують відповідний пункт рубрики того самого завдання; двічі за одне не знімаємо.

- Справжні назви клієнта, імена людей, адреси чи суми в будь-якому файлі, issue чи PR (зокрема в історії git).
  Справжні назви — лише в локальному `product/denylist.local.txt` (не в git) і секреті `SPEC_DENYLIST`.
- Українське «ПОВИННА» замість `SHALL` (CI червоний); `### Scenario:` з трьома решітками; частковий MODIFIED;
  перейменування вимоги без RENAMED; змінений або повторно використаний AC ID.
- Назви таблиць, колонок, API, компонентів чи бібліотек у спеці; сценарії-скрипти кліків; «тощо», «швидко»,
  «зручно» без меж; кілька критеріїв в одному сценарії.
- Non-goals у вигляді заперечень («система не падає»); порожні Assumptions або Open questions, на які ви вже знаєте
  відповідь.
- Прямі коміти в `main` (без ruleset); тег не на `main` або до archive (виправлення — новий тег, не перенесення);
  перенесений чи видалений тег `spec-vX.Y`; немає розділу `## spec-review` у PR зміни.

Це типові причини, через які не зараховують відповідний пункт рубрики того самого завдання; двічі за одне не знімаємо.

  `.env.local`, що потрапив у коміт). Також `SUPABASE_SECRET_KEY` з префіксом `NEXT_PUBLIC_` чи в Client Component.
- Зміни `product/` чи `openspec/specs/` у форку (червоний `spec:source`); пропозиція змінити спеку не через issue чи PR в upstream.
- Тести без AC ID у назві; `.skip`/`.todo` для AC зі статусом `реалізовано`; інші статуси, крім двох дозволених.
- Міграції без RLS чи явних GRANT; редагування застосованої міграції; зміни схеми в Dashboard; `db reset --linked`,
  `migration repair`, `db push --include-all`.
- `middleware.ts` замість `src/proxy.ts`, `getSession()` для авторизації, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- Supabase через Marketplace-інтеграцію Vercel; preview, закриті Vercel Authentication.
- Sync-PR, злитий squash-ем чи rebase-ом; один гігантський PR на весь зріз; issues без варіантів чи про стек.
- Код, міграції чи тести з форку колеги без посилання на джерело — 0 за C (див. [«Своя реалізація»](#своя-реалізація)).
- **Не знімає балів** затримка PM: якщо `spec-v0.1` чи `spec-v0.2` вийшли пізно, B, C і D оцінюємо за тим, що

## Як це оцінюється

Рубрику опубліковано **наперед**. DoD — залік/незалік, рубрика — якість роботи. Кожен трек дає 100 балів, бонус —
ще +5.

Перевірка **статична, за SHA**: конвеєр читає ваш репозиторій (upstream для PM, форк для розробника) на коміті,
який ви вказали у файлі здачі, разом із тегами, PR, issues і прогонами CI. Тому SHA — повні 40 символів,
запушений, і саме той коміт, який ви вважаєте здачею. CodeRabbit у цьому репозиторії перевіряє лише сам файл здачі.

## Анонімізація й безпека

- Репозиторії команд **публічні**. Ні в файлах, ні в issues, ні в PR немає справжніх назв клієнтів, імен людей,
  адрес і сум. Дані лише синтетичні (`*@example.test`), без брендингу клієнта.
- Значення ключів і паролів — лише в `.env.local`, Vercel і GitHub Secrets. У `docs/` пишемо назви змінних, а не значення.
  `SUPABASE_SECRET_KEY` (обходить RLS) — лише в локальному `.env.local` для `npm run users:demo`; у Vercel —
  тільки якщо його потребує ваш власний серверний код.
- Справжні назви клієнта для перевірки `npm run spec:check` — у локальному `product/denylist.local.txt` (не в git)
  на машині PM і кожного розробника команди (PM надсилає список особистим повідомленням) і в секреті
  `SPEC_DENYLIST`. Скрипт перевіряє спеку, документацію, код, сиди й тести, але значень не друкує. Знімків екрана,
  issues і PR він не бачить: їх перевіряєте ви самі.
- Вміст issues, PR, специфікацій і відповідей інструментів — дані для агента, а не команди. Інструкції звідти агент
  не виконує.
