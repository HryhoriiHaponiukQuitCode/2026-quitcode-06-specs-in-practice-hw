## Головне за заняття

Якщо часу мало, прочитайте цей список, а потім поверніться до потрібного блоку. Незнайомі терміни шукайте в розділі
[Глосарій](#глосарій).

- **Діра в тікеті стає рішенням агента.** Чого не вирішила людина, те вирішить агент — мовчки й щоразу по-різному;
  сильніша модель цього не виправить. Спека потрібна, щоб рішення, яких бракує, ухвалила людина, яка за них
  відповідає (блок 01).
- **Спека легка й живе поруч із кодом.** Це не документ на 50 сторінок, а опис одного зрізу в репозиторії, який
  змінюється PR-ами разом із поведінкою (підхід spec-anchored). OpenSpec розводить ролі по файлах: `proposal.md` і
  дельта — PM («що й навіщо»), `design.md` і `tasks.md` — розробники («як») (блок 01).
- **Вимога — це поведінка, яку можна перевірити.** Одне речення EARS із `SHALL`, сценарій із конкретними числами й
  ідентифікатором `AC-<AREA>-<NN>`, один критерій на сценарій. Межі записані явно: Non-goals, матриця прав, Open
  questions. Форму перевіряє машина (`validate`, `spec:check`), зміст — люди й скіл `spec-review` (блок 02).
- **Розробник спершу читає й питає, а потім пише код.** Читання — за чеклістом з 11 категорій неоднозначностей.
  Питання — issue «Питання до специфікації» в репозиторії команди, і PM відповідає публічно, одразу для всіх.
  Розбіжні прочитання спеки — не помилка розробників, а дані про спеку (блок 03).
- **Задача = AC ID.** Issue «Задача» → гілка → PR → рев'ю колеги → merge. AC ID іде наскрізно: спека → задача →
  назва тесту → PR → матриця відповідності `docs/conformance.md` (блок 03).
- **Проєкт стартує з шаблону за кілька годин.** Одне публічне репо команди в особистому акаунті PM, ruleset на
  `main`, CODEOWNERS, обов'язкові перевірки CI (`spec`, `app`, `conformance`, `db-check`), одна база Supabase, Vercel з preview на кожен
  PR. Кожен секрет має одне місце: у Vercel — лише `NEXT_PUBLIC_SUPABASE_URL` і
  `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` там не буває ніколи; пароль бази — лише в PM і в
  environment `production` для CI, розробникам він не потрібен. Схему бази змінюють лише
  міграції: PR → `db-check` → merge → `db-deploy`; жодного `supabase db push` з ноутбука й жодного DDL (команд `create`, `alter`, `drop`, що змінюють схему) у SQL Editor
  (блок 04).
- **Спека живе далі.** Нова версія — PR у тому самому репо й тег `spec-vX.Y` (помилку виправляє тег-виправлення
  `spec-vX.Y.Z`). Кожен новий AC отримує рядок матриці «відкладено (новий AC — чекає задачі)» і стає задачею. Знайшли
  хибу в спеці — PR в `openspec/changes/` на рев'ю PM, а не тихий фікс у коді (блок 05).
- **Ворота й порадники.** Merge блокують лише детерміновані перевірки й approve людей. LLM-інструменти
  (`/opsx:verify`, `spec-review`, `spec-clarify`, CodeRabbit) — друга думка, підказка для людини (блок 05).

### Про що це заняття (слайд 1)

Шосте заняття з дванадцяти — «Специфікації на практиці: старт командного проєкту». З нього починається командний
проєкт, який триватиме до кінця курсу: чотири команди, чотири продукти. У кожної команди один репозиторій, одна
**специфікація** («спека» — опис того, що саме має робити продукт, з критеріями, які можна перевірити) і одна спільна
реалізація через **PR** (pull request — запит на злиття змін у головну гілку `main`) з рев'ю колег. Сьогодні вчимося
писати спеку, читати її, уточнювати й тримати живою, а проєкт стартуємо з нуля за кілька годин.

**Навіщо в роботі.** На попередніх заняттях агент навчився працювати як член команди: правила, скіли, доступ до
систем. Але йому досі бракує головного — точного опису того, що будувати. У проєктах агенції це зазвичай бриф, дзвінок
і тікет на три рядки, і агент мовчки заповнює діри. Відтепер PM пише спеку, розробники реалізують її разом, а розбіжні
прочитання спеки стають даними в issues і рев'ю, а не сюрпризом на демо.

### Карта курсу: кожне заняття — шар у проєкті (слайд 2)

З сьогоднішнього дня в кожної команди є свій продукт. Кожна наступна тема додає в нього один шар, і до demo day
(останнього заняття) він доростає до робочої версії.

| # | Тема | Шар у командному проєкті |
|---|---|---|
| 1–5 | пройдено: стан індустрії, промпти й безпека, правила й команди, скіли, MCP | уже в шаблоні: `AGENTS.md`, команди й скіли, MCP з мінімальними правами |
| **6** | **Специфікації на практиці + старт проєкту** (це заняття) | **спека v0.x, репо, PR-флоу, секрети, CI, Vercel, Supabase, перший зріз** |
| 7 | Fullstack з AI: фронт і бек | UI, API, БД, auth і RLS наступних зрізів; ADR і архітектурні правила в CI |
| 8 | Якість: тести, evals, AI code review | тестова піраміда, e2e за AC, рев'ю в PR |
| 9 | Software Factory: багатоагентний конвеєр | конвеєр «спека → PR» для зрізу; спільні скіли й шаблони між проєктами |
| 10 | AI-функції в продукті (Claude Agent SDK) | вбудований AI: парсинг документів, чернетки |
| 11 | DevOps та експлуатація | CI/CD, observability, інциденти, вартість |
| 12 | Demo day: PM презентують продукти команд і порівнюють підходи | фінальна версія |

Скорочення з таблиці: **CI** — автоматичні перевірки, які GitHub Actions запускає на кожен PR і на `main`; **AC** —
критерій приймання (acceptance criterion); **RLS** — правила доступу до рядків таблиці, які виконує сама база; **ADR** —
короткий запис архітектурного рішення з причинами; **e2e** — наскрізні тести через інтерфейс; **evals** — оцінювання
якості відповідей AI; **observability** — логи, метрики й трасування, щоб бачити, що відбувається в проді.

Перші п'ять занять уже лежать у шаблоні проєкту, з якого стартує кожна команда:

| Шар курсу | Де в шаблоні |
|---|---|
| Правила й команди (заняття 3) | `AGENTS.md`, `CLAUDE.md`, `.claude/commands/`, `.cursor/commands/` |
| Скіли (заняття 4) | `.claude/skills/` (Cursor читає цю ж теку): `spec-clarify` для розробника, `spec-review` для PM |
| MCP з мінімальними правами (заняття 5) | `.mcp.json` (Supabase MCP лише на читання) і `.claude/settings.json` — діють лише в Claude Code |
| Специфікації (заняття 6) | `product/`, `openspec/`, `scripts/check-*.mjs`, `docs/conformance.md` |
| Командна робота (заняття 6) | `.github/` (CI, CODEOWNERS, шаблони PR та issues), `docs/bootstrap.md`, `docs/onboarding.md`, `docs/team.md` |

**Навіщо в роботі.** Це не «ще одна тема», а початок продукту, який ваша команда доведе до demo day. Рішення, які ви
ухвалюєте цього тижня (ролі, межі зрізу, правила злиття), житимуть у тому самому репозиторії до кінця курсу.

### Чотири команди — один процес (слайд 3)

На слайді — чотири картки команд, під ними потік із чотирьох кроків і головне правило ролей.

| Команда (слаг) | Продукт | Бриф |
|---|---|---|
| `property-workflows` | процеси (шаблони, запуски, задачі) для агенції з управління нерухомістю | [бриф](../materials/briefs/property-workflows.md) |
| `therapy-scheduling` | шлях клієнта практики психотерапії: анкета, підбір, розклад | [бриф](../materials/briefs/therapy-scheduling.md) |
| `school-purchasing` | заявки на закупівлю й компенсацію витрат у школі | [бриф](../materials/briefs/school-purchasing.md) |
| `leave-portal` | портал відсутностей персоналу школи; на ньому зроблено всі демо заняття | [бриф](../materials/briefs/leave-portal.md) |

**Слаг** — коротка нейтральна назва латиницею; вона ж — назва репозиторію команди. Репозиторії публічні, тому
справжніх назв клієнтів, імен людей, адрес і сум у них немає, а дані лише вигадані (`*@example.test`).

**Ролі.** У кожній команді один PM і 4–6 розробників. Одного з розробників команда обирає **техлідом**.

| Роль | Хто | Що робить |
|---|---|---|
| **PM** | власник репо команди, організації й проєкту Supabase, проєкту Vercel | налаштування команди, продуктовий контекст і спека (`product/`, `openspec/`), відповіді на питання, релізи-теги, задачі разом із техлідом; код не пише |
| **Техлід** | один із розробників | співвласник спеки в CODEOWNERS: рев'ю й approve PR-ів PM; план реалізації `impl-<зріз>` разом із командою; рев'ю міграцій; `npm run users:demo` (створює синтетичних користувачів) |
| **Розробник** | **collaborator** репо команди (учасник із правом запису) | онбординг, питання до спеки, задачі (кожна — окремий PR), рев'ю PR-ів колег |

**Процес — чотири кроки потоку на слайді:**

1. **PM: репо команди.** PM створює його з шаблону одразу після заняття. У ньому `product/` (продуктовий контекст:
   vision, глосарій, ролі, roadmap), `openspec/` (спека у форматі **OpenSpec** — інструмента, де спека лежить у
   репозиторії й змінюється дельтами) і git-теги `spec-vX.Y` — опубліковані версії спеки.
2. **Розробники: задачі.** **Зріз** — вертикальний шматок продукту (інтерфейс, дія, дані й тест), цінний сам по собі
   (у демо — «подання заявки на відсутність і рішення менеджера»). Його ділять на задачі, і кожна йде шляхом
   гілка → PR → рев'ю колеги → merge. На команду одна база Supabase й один проєкт Vercel.
3. **AC ID наскрізно.** Кожен критерій приймання має ідентифікатор `AC-<AREA>-<NN>`, наприклад `AC-LEAVE-01`. Він
   проходить крізь усе: спека → задача → назва тесту → PR → матриця відповідності `docs/conformance.md` (таблиця «AC →
   код → тест → статус»).
4. **Demo day.** PM показує, де команда прочитала спеку по-різному.

Головне правило: **PM пише «що й навіщо», розробник з агентом — «як».** Розбіжні прочитання — у питаннях, у рев'ю, у
двох PR-ах, що не стикуються, — не помилка розробників, а дані про спеку. Саме їх PM збирає в нотатку для demo day
(трек PM, завдання D у [README](../README.md)).

Як пов'язані репозиторії (у кутових дужках тут і далі — те, що ви підставляєте самі: `<pm>` — логін PM на GitHub,
`<techlead>` — логін техліда, `<team-slug>` — слаг команди, `<зріз>` — коротка назва зрізу, як `leave-request` в
`add-leave-request`, `<login>` — ваш логін, `<N>` — номер issue):

```text
шаблон koldovsky/2026-quitcode-06-project-template
  └─ «Use this template» → репо команди <pm>/<team-slug>  (публічне, в особистому акаунті PM)
        ├─ collaborators (Write): розробники, зокрема техлід, і викладач
        ├─ main ← лише PR-и: спека PM (product/, openspec/) і задачі розробників (src/, supabase/, tests/, docs/)
        ├─ Supabase: організація <team-slug> PM, один проєкт; розробники — роль Developer
        └─ Vercel: проєкт PM; preview на кожен PR, прод — з main
```

**Хто що змінює і хто схвалює:**

- Автор не може схвалити власний PR — так влаштований GitHub. Тому PR-и PM зі спекою схвалює техлід, а PR розробника
  — будь-хто з колег.
- `product/` і `openspec/specs/` веде PM. Якщо PR чіпає `product/`, `openspec/` чи `.github/`, approve дає PM або
  техлід; міграції в `supabase/migrations/` — техлід або PM. Це задає файл `.github/CODEOWNERS` (власники коду для
  шляхів у репо).
- Розробник спеку напряму не змінює. Пропозиція — issue «Питання до специфікації» або PR лише в
  `openspec/changes/<id>/`; рішення — за PM.
- **Міграції** (SQL-файли, що змінюють схему бази) — лише через PR. У хмарну базу їх застосовує CI: job `db-deploy`
  після merge у `main`. З ноутбука в базу ніхто нічого не пушить.

**Як ці правила тримаються технічно.** Не на дисципліні, а на **ruleset** — наборі правил GitHub для гілки `main`.
Його опис лежить у [`materials/rulesets/team-main.json`](../materials/rulesets/team-main.json), але сам файл нічого не
вмикає. У день 0, останнім кроком налаштування (після першого зеленого прогону CI і злитого CODEOWNERS: обов'язкові перевірки в ruleset прив'язані до GitHub Actions, і GitHub приймає таку прив'язку, лише коли Actions уже звітували ці перевірки в репо), PM
застосовує його до репо команди: завантажує JSON у файл `ruleset.json` командою
`curl -sLo ruleset.json https://raw.githubusercontent.com/koldovsky/2026-quitcode-06-specs-in-practice-hw/main/materials/rulesets/team-main.json`
(у PowerShell — `curl.exe`) і виконує `gh api repos/<pm>/<team-slug>/rulesets --method POST --input ruleset.json`
або імпортує файл у Settings → Rules → Rulesets ([walkthrough-pm](walkthrough-pm.md), крок 8; точні назви пунктів
перевірте в інтерфейсі). Відтоді GitHub сам відхиляє прямий push у
`main` і не дає злити PR без approve колеги (і власника коду, якщо PR чіпає його шляхи), без approve після останнього
push, без розв'язаних розмов і без зелених перевірок `spec`, `app`, `conformance`, `db-check`; видалити `main` чи зробити в нього force push теж не вийде. Усе це діє, бо репо публічне: на GitHub Free ruleset діє лише в публічних репозиторіях. Список обходу (bypass)
порожній, тож правила діють і для PM; якщо GitHub таки дасть власнику злити свій PR без approve — не користуйтеся
цим і напишіть у чат курсу: рубрика A перевіряє, що кожен PR у `main` має approve колеги. Детальніше — у розділі [«Як працює ruleset»](#як-працює-ruleset) блоку 04.

**Форків немає** (fork — власна копія чужого репо у вашому акаунті). Уся команда працює в одному репо як collaborators. Єдиний fork — fork репозиторію домашки,
щоб відкрити PR із файлом здачі ([submissions/README.md](../submissions/README.md)).

**Демо — на `leave-portal`.** Для інших команд це зразок формату, а не готова відповідь. Для PM команди
`leave-portal` діє окреме правило: вимоги, сценарії чи `product/`, скопійовані з
[`examples/leave-portal/`](../examples/leave-portal/) або демо-репозиторію, дають 0 балів за відповідне завдання
([README](../README.md), «Своя робота в спільному репозиторії»).

**Навіщо в роботі.** В агенції проєкти так і працюють: PM тримає вимоги клієнта, розробники будують одну систему в
одному репозиторії, з однією базою й одним деплоєм. Кожне місце, де спеку можна прочитати двома способами, проявиться
як питання, суперечка в рев'ю чи два PR-и, що не стикуються, — ще до merge, поки це дешево виправити.

**Що зробити.** Прочитайте розділ «Як працює `main` команди» у своєму walkthrough: [PM](walkthrough-pm.md) або
[розробник](walkthrough-dev.md). Бриф своєї команди прочитайте до першої зустрічі команди.

закриття. Кожен блок починається з робочої ситуації й закінчується тим, що зробити в роботі завтра.

**Практика блоку 03 (слайд 25) — після заняття, силами команди.** Це перший раунд питань до брифу. У день 0 або 1,
ще до `spec-v0.1`, PM призначає зустріч команди на 15–20 хвилин: PM коротко називає мету зрізу й три ключові правила з
брифу; кожен розробник — одну діру в брифі, її категорію з одинадцяти (слайд 21) і 2–3 варіанти поведінки; PM
відповідає або записує питання як відкрите. Хто не зміг прийти, пише свою діру в чат команди до кінця дня 1. Не
вдається зібратися — та сама розмова асинхронно в чаті команди. Покроково: [walkthrough-pm](walkthrough-pm.md),

вчимося перевіряти, що він виконав саме його.

**Навіщо в роботі.** Результат дня — не ще один інструмент, а робочий процес команди: хто пише спеку, як її читають,
як питають, як вона змінюється і як CI ловить розбіжності між спекою й кодом.

### Що підготувати (слайд 5)

Тиждень проєкту стартує в день заняття: одразу після нього PM створює репо команди й запрошує розробників, а
розробники того ж дня приймають інвайти. Тому акаунти й інструменти мають бути готові заздалегідь.

**Акаунти — лише особисті.** Робочі акаунти агенції мають доступ до клієнтських організацій, а навчальний проєкт їх
не торкається.

| Сервіс | PM | Розробники (зокрема техлід) |
|---|---|---|
| GitHub | так; репо команди — у вашому особистому акаунті (не в організації), публічне | так |
| Supabase Free | так, з **вільним слотом**: на Free активних може бути лише 2 проєкти на всі організації, де ви Owner або Administrator; зайві (наприклад, з WS5) — на паузу або видалити | акаунт без власного проєкту: PM запросить вас в організацію команди роллю **Developer**, яка слота не займає |
| Vercel Hobby (вхід через GitHub) | так: імпортувати особисте репо у Vercel може лише його власник | не потрібен |
| CodeRabbit (AI-рецензент PR, застосунок GitHub) | так: підключає до репо команди | не потрібен; у PR просіть рев'ю окремим коментарем `@coderabbitai review` |

Ще три правила зі слайда:

- **Репо — публічне з першої хвилини.** На GitHub Free ruleset, CODEOWNERS і секрети environment діють лише в
  публічних репозиторіях. А Vercel Hobby не деплоїть коміти колег, запушені, поки репо було приватним, і вони
  лишаються заблокованими навіть після відкриття.
- **Supabase через Marketplace-інтеграцію Vercel не встановлюємо.** Вона створює окрему організацію Supabase під
  керуванням Vercel, а проєкт команди має бути у власній організації PM.
- **CodeRabbit сам не прийде.** Публічні репо з менш ніж 10 зірками він автоматично не рецензує, тому після створення
  PR напишіть окремий коментар `@coderabbitai review`.

**Інвайти — в день 0.** Без прийнятого інвайту GitHub ви не запушите гілку, не схвалите PR і не потрапите в
CODEOWNERS. Техлід приймає першим: поки він не має доступу, PR-и PM зі спекою нікому схвалити. Інвайт Supabase
приходить листом на email вашого акаунта Supabase; не прийшов — напишіть PM, з яким email ви там зареєстровані.

**Інструменти на машині (Windows і macOS):**

```bash
node -v                      # v24.x
git --version
gh auth status               # якщо не ввійшли — gh auth login
npm i -g @fission-ai/openspec@1.14.1
openspec --version           # 1.14.1
openspec config set telemetry.enabled false
claude --version             # або Cursor
```

- **Node 24 LTS.** Node 20 уже EOL — його підтримку завершено.
- **OpenSpec CLI — глобально й саме 1.14.1**, тієї ж версії, що в шаблоні. Команди агента `/opsx:*` (у Cursor —
  `/opsx-*`) викликають просто `openspec`, а теки `node_modules/.bin` проєкту в PATH агента немає. З іншою версією
  `/opsx:*` поводитимуться інакше, ніж на занятті. Скрипти `npm run spec:*` і CI беруть версію з `devDependencies`.
- **Claude Code або Cursor** — обидва бачать команди й скіли шаблону.
- **Supabase CLI** окремо не ставимо: він у `devDependencies` проєкту й запускається через `npx`.
- **Docker не потрібен.** Локально ви запускаєте лише `npm run dev` проти спільної бази команди, а міграції на
  одноразовій базі перевіряє CI: job `db-check` піднімає її на раннері GitHub (тимчасовій машині, на якій GitHub Actions виконує jobs CI).
- **Windows.** Команди у walkthrough-ах написано для Git Bash. У Windows PowerShell 5.1 немає `&&` — виконуйте
  команди по черзі; на «running scripts is disabled» пишіть `npx.cmd`, `npm.cmd`, `openspec.cmd`. GitHub CLI без
  прав адміністратора: `winget install --id GitHub.cli --scope user --silent`, потім перезапустіть термінал.

**Навіщо в роботі.** На старті клієнтського проєкту найдорожче — день, коли «у мене не ставиться». Перевірка до
старту економить команді цей день.

**Що зробити.** Пройдіть крок 0 у [walkthrough-pm](walkthrough-pm.md) або [walkthrough-dev](walkthrough-dev.md) і
розділ [«Перш ніж почати»](../README.md#перш-ніж-почати) README домашки: там же обмеження безкоштовних тарифів (сон
проєкту Supabase після ~7 днів без активності, ліміт листів Supabase Auth, cron на Vercel Hobby). Техліда команда
обирає на занятті або в чаті команди до вечора дня 0: його логін потрібен PM для CODEOWNERS.

## Блок 01 — Навіщо спека, коли код пише агент (слайди 6–10)

> **Одна ідея блоку:** чого не вирішила людина, те вирішить агент — мовчки й щоразу по-різному. Специфікація (далі —
> «спека») потрібна, щоб рішення, яких бракує в брифі, ухвалила людина, яка за них відповідає. Незнайомі терміни
> шукайте в розділі [Глосарій](#глосарій).

### Історія, яку ви точно бачили (слайд 6)

На слайді великий заголовок: «Клієнт написав одне речення. Агент написав модуль.» Під ним коротка історія, знайома
кожній агенції:

1. Бриф (опис задачі від клієнта) прийшов листом.
2. PM переклав його в тікет на три рядки.
3. Розробник віддав тікет агенту (Claude Code або Cursor).
4. Через тиждень демо, і клієнт каже: «Ми мали на увазі інше».

Агент не помилився. Він мовчки вирішив те, чого не вирішив ніхто. З агентом така історія стала **швидшою, а не
кращою**. Раніше розробник, наткнувшись на дірку в тікеті, хоча б питав. Агент не питає: він обирає один варіант і
впевнено звітує «done».

**Навіщо в роботі.** Спека — це не формальність «для порядку» і не документ «для агента». Це спосіб зробити так, щоб
відсутні рішення ухвалила людина, яка за них відповідає (PM разом із клієнтом), і щоб це сталося **до** того, як агент
напише код.

### Одне речення — п'ять реалізацій (слайд 7)

На слайді одне речення з демо-проєкту `leave-portal` (заявки працівників школи на відсутність і рішення менеджера):

> «Якщо відсутність **покриває обидві посади** — у заявці два записи: `main` і `additional`.»

Це стислий переказ критерію приймання `AC-LEAVE-02` з першої версії спеки демо (`spec-v0.1`). Фраза «покриває обидві
посади» там дослівна. Неоднозначність у ній лишили свідомо: на цьому реченні далі в занятті показано, як працюють
уточнення. Повний текст сценарію є у [зразку spec-v0.1](../examples/leave-portal/1-spec-v0.1/specs/leave-requests/spec.md).

Спробуйте самі, перш ніж читати далі: скільки записів буде в заявці і за якої умови? Якщо відповідь здається очевидною,
перечитайте речення ще раз. Її там немає, ви додали щось своє.

Тепер уявіть, що це речення отримали п'ять розробників і кожен віддав його своєму агенту:

| # | Як прочитав розробник (і його агент) | Що вийде |
|---|---|---|
| 1 | Є дві посади, тож **завжди** два записи | записи з'являться й там, де людина в ці дні не працює |
| 2 | Два записи, лише якщо **в ці дні є розклад** за обома посадами | потрібен розклад, а в цьому зрізі розкладу немає |
| 3 | Працівник **сам обирає** посади галочками | у формі з'являється нове поле |
| 4 | **Дві окремі заявки** замість однієї з двома записами | менеджер ухвалює два рішення замість одного |
| 5 | Один запис із позначкою «обидві посади» | інша модель даних |

Що з цього випливає:

- **Кожне прочитання чесне.** Жодне не суперечить тексту, тож тікет пропустить будь-яке з них.
- **Кожне дає інший продукт:** іншу модель даних, інший інтерфейс, інші тести.
- **Агент обирає мовчки.** Фрази «я обрав варіант 2» у його відповіді не буде. Буде готовий код і зелені тести, але ці
  тести написав той самий агент, тож вони підтверджують *його* прочитання, а не ваше.
- **У новій сесії агент може обрати інший варіант.** Двоє розробників однієї команди отримають несумісний код.
- **Сильніша модель цього не виправить.** Бракує не розуму, а вхідних даних: потрібного рішення в тексті просто
  немає. Дослідження ClarifyGPT і досвід Thoughtworks з інструментом Tessl доходять того самого висновку: розбіжні
  реалізації — симптом неоднозначної вимоги, а не слабкої моделі.

**«А як правильно?»** Правильно те, що вирішить PM. У демо 2 (блок 03) це речення стає питанням Q1 до PM, а відповідь
PM і нову версію спеки показано в демо 4 (блок 05).

**Навіщо в роботі.** Діра в тексті стає рішенням агента. У командному проєкті курсу всі працюють в одному репозиторії
над однією спільною реалізацією, тож два прочитання однієї вимоги перетворюються на два PR, які не стикуються між собою.
Спитати до коду дешевше, ніж переробляти після рев'ю чи демо.

**Що з цим робити:**

- **PM.** У [шпаргалці PM](spec-guide.md#7-антипатерни-ac) саме ця фраза наведена як антипатерн «термін не з
  глосарію». Перед релізом спеки запустіть скіл `spec-review`: він шукає такі місця
  ([walkthrough-pm](walkthrough-pm.md), крок 11).
- **Розробник.** Побачили речення, яке можна прочитати двома способами, — не дозволяйте агенту вибирати мовчки.
  Відкрийте issue «Питання до специфікації» в репозиторії команди з варіантами поведінки; допоможе скіл `spec-clarify`
  ([walkthrough-dev](walkthrough-dev.md), крок 4).

### Три рівні SDD — і наш (слайд 8)

**Spec-driven development (SDD)**, розробка на основі специфікацій, — це не одна практика, а три різні домовленості
про те, що головне: спека чи код. Класифікацію запропонувала Бригітта Бекелер (Birgitta Böckeler) з Thoughtworks
у статті на martinfowler.com.

| Рівень | Як працює | Наслідок |
|---|---|---|
| **spec-first** | спеку пишуть перед кодом, а після реалізації кидають | через місяць спека бреше; так працює більшість інструментів |
| **spec-anchored — наш вибір** | спека живе в репозиторії поруч із кодом і **змінюється в тому самому PR**, що й поведінка | код — джерело правди, спека — контракт; CI перевіряє, що вони не розійшлися |
| **spec-as-source** | люди правлять лише спеку, код генерується | схоже на model-driven development і має ті самі проблеми; це не наша ціль |

Що spec-anchored означає на практиці:

- Спека команди лежить у теці `openspec/` вашого репозиторію, а ворота CI перевіряють її в кожному PR.
- Змінюєте поведінку і не чіпаєте спеку — це сигнал, що щось пішло не так.
- Змінили спеку, а коду ще немає — значить, реалізація наздоганяє. Для цього є матриця відповідності
  `docs/conformance.md`: новий AC з'являється там зі статусом «відкладено (новий AC — чекає задачі)» і стає
  «реалізовано» в PR задачі разом із тестом (детально — в наступних блоках).

**Що каже Thoughtworks Technology Radar** (стан на 09.10.2026). Радар розкладає техніки й інструменти по кільцях:
**Adopt** — беріть за замовчуванням, **Assess** — вивчайте, як це вплине на вас, **Caution** — обережно.

| Випуск | Що там про SDD |
|---|---|
| Vol 33, листопад 2025 | SDD — окрема техніка в кільці **Assess**; застереження про ризик важкої специфікації наперед і релізів «великим вибухом» |
| Vol 34, квітень 2026 | окремого пункту про SDD немає; **OpenSpec** і **Spec Kit** — у кільці Assess, OpenSpec відзначають за роботу дельтами, а не повною спекою наперед; **agent instruction bloat** (роздуті інструкції для агента) — у кільці **Caution** |

Ще одне застереження: Кент Бек у матеріалах на сайті Мартіна Фаулера заперечує проти підходу «вся спека до коду».
Тому в нас спека не пишеться раз і назавжди: вона має версії (теги `spec-v0.1`, `spec-v0.2`…) і змінюється через цикл
уточнень. `spec-v0.1` достатньо добра, щоб почати, а `spec-v0.2` вже пройшла зустріч із реальністю
([шпаргалка PM](spec-guide.md#11-розмір-зрізу), «Розмір зрізу»).

**Висновок слайда:** SDD — **Assess, не Adopt**. Ми беремо легку ітеративну спеку на один зріз (вертикальний шматок
функціональності, який можна показати користувачу), а не документ на весь продукт. І головне правило курсу:
**PM — що й навіщо, розробник з агентом — як.**

**Навіщо в роботі.** Рано чи пізно клієнт або колега скаже: «SDD — це водоспад з новою назвою». Точна відповідь: ні.
Спека пишеться на один зріз, лежить у репозиторії, змінюється в тому самому PR, що й поведінка, і має версії-теги.

### OpenSpec за один слайд (слайд 9)

**OpenSpec** — інструмент командного рядка (npm-пакет `@fission-ai/openspec`), у якому зберігаємо спеку в курсі.
Версія зафіксована: **1.14.1**. Головна ідея — **дельти**. Кожна зміна спеки описує лише різницю: що додає, змінює
чи прибирає. Після `archive` ця різниця зливається в чинну спеку.

Структура теки `openspec/` у репозиторії команди:

```text
openspec/
├─ config.yaml                       контекст продукту й правила формату (агент бере їх у кожен запит)
├─ specs/<capability>/spec.md        чинна поведінка, по файлу на можливість (capability)
└─ changes/
   ├─ <id>/                          активна зміна: одна зміна — один намір
   │  ├─ proposal.md                 навіщо й що (PM)
   │  ├─ specs/<capability>/spec.md  дельта: вимоги, які додаємо, змінюємо чи прибираємо (PM)
   │  └─ design.md, tasks.md         як реалізувати (техлід із розробниками)
   └─ archive/YYYY-MM-DD-<id>/       зміни після archive, з датою
```

У нашому процесі «що» і «як» розведені ще й по різних змінах. У зміні PM (`add-<зріз>`, `clarify-<зріз>`…) лежать лише
`proposal.md` і дельта. `design.md` і `tasks.md` живуть в окремій зміні команди `impl-<зріз>`, яку веде техлід
([README шаблону](https://github.com/koldovsky/2026-quitcode-06-project-template#шлях-розробника), «Шлях розробника»).

**Приклад із демо.** Зміна `add-leave-request` після archive стала чинною спекою
`openspec/specs/leave-requests/spec.md`, і на цьому стані PM поставив тег `spec-v0.1`. Подивитися можна в
[репозиторії демо](https://github.com/koldovsky/2026-quitcode-06-leave-portal-demo): тека
`openspec/changes/archive/` і тег `spec-v0.1`.

**Розділи дельти** (докладно — у [шпаргалці PM](spec-guide.md#10-пастки-формату-openspec-1141)):

| Розділ | Коли |
|---|---|
| `## ADDED Requirements` | нова вимога |
| `## MODIFIED Requirements` | змінена вимога; копіюєте **весь** блок вимоги з усіма сценаріями й правите копію |
| `## REMOVED Requirements` | вимогу прибрано; пишіть `**Reason**` і `**Migration**`, щоб розробники знали, що робити з наявним кодом |
| `## RENAMED Requirements` | перейменування: назва вимоги — це її ID, тож перейменовують лише тут |

**Команди агента.** У Claude Code вони мають вигляд `/opsx:<назва>`, у Cursor — `/opsx-<назва>` (через дефіс,
наприклад `/opsx-propose`).

| Команда | Що робить | Як ми її використовуємо |
|---|---|---|
| `/opsx:propose <опис>` | створює нову зміну й генерує її файли | PM — чернетка першого зрізу; попросіть «лише proposal.md і specs/, без design.md і tasks.md» ([walkthrough-pm](walkthrough-pm.md), крок 10) |
| `/opsx:explore` | режим обдумування: агент читає й уточнює, але код не пише | щоб розібратися до того, як щось змінювати |
| `/opsx:apply <id>` | реалізує задачі зміни | розробник — одна задача за раз із `impl-<зріз>` ([walkthrough-dev](walkthrough-dev.md), крок 6); галочок у `tasks.md` не ставимо, а якщо агент їх поставив — `git restore` цього файлу ([README шаблону](https://github.com/koldovsky/2026-quitcode-06-project-template#шлях-розробника), «Шлях розробника», крок 4) |
| `/opsx:verify <id>` | звіряє реалізацію з файлами зміни, видає знахідки CRITICAL / WARNING / SUGGESTION | порадник, а не ворота: merge не блокує |
| `/opsx:update` | переглядає файли вже створеної зміни й тримає їх узгодженими, коду не чіпає | коли треба поправити зміну, яка ще не в архіві |
| `/opsx:sync` | агент сам переносить дельти зміни в чинну спеку | у релізі команди не потрібен: дельти переносить `archive` (наступний рядок) |
| `/opsx:archive` | архівує завершену зміну: дельти детерміновано зливаються в `openspec/specs/`, тека зміни переїжджає в `changes/archive/` | у процесі команди — командою `npx openspec archive <id> -y` у гілці PR, до merge: PM — для своєї зміни спеки; автор останнього PR зрізу — для `impl-<зріз>` (approve — PM або техлід) |

Що ще важливо знати:

- **`verify` не входить у стандартний профіль `core`** (профіль — набір команд `/opsx:*`, які OpenSpec генерує для агента). Шаблон команди зібрано з профілем `custom`, і файли всіх
  команд уже закомічені в `.claude/` і `.cursor/`. Профіль зберігається на машині, а не в репозиторії, а
  `npx openspec update` з профілем `core` видалить `/opsx:verify`. Тому за `AGENTS.md` шаблону агент запускає
  `npx openspec update` лише після вашого дозволу.
- **`openspec validate --all --strict`** (у шаблоні — `npm run spec:validate`) повертає код виходу 0 або 1, тож це
  ворота в CI (job `spec`). Але він перевіряє лише **структуру**, а не зміст. Розмиту вимогу на кшталт «SHALL швидко
  завантажувати» він пропустить. Тому людське рев'ю й скіли (`spec-review` для PM, `spec-clarify` для розробників)
  нікуди не зникають.
- **`openspec show <id> --diff`** показує, що змінює зміна, але лише поки вона активна. Після archive дивіться теку
  `openspec/changes/archive/<дата>-<id>/` або `git log -p openspec/specs`.
- **Легасі.** Команди на зразок `/openspec:proposal` і файл `openspec/AGENTS.md` належать до старих версій. Якщо
  їх радить стаття чи агент — це не про нашу версію.

**Встановлення** (те саме для PM і розробників, [walkthrough-pm](walkthrough-pm.md) і
[walkthrough-dev](walkthrough-dev.md), крок 0):

```bash
npm i -g @fission-ai/openspec@1.14.1
openspec --version                          # 1.14.1
openspec config set telemetry.enabled false # вимикає телеметрію; у CI вона вимкнена сама
```

Глобально й саме тієї ж версії тому, що команди `/opsx:*` і скіли викликають просто `openspec`, а `node_modules/.bin`
у PATH агента немає. Скрипти `npm run spec:*` і CI беруть версію з `devDependencies` проєкту. Інша глобальна версія —
і `/opsx:*` поводитимуться не так, як на занятті.

**Чому OpenSpec, а не інші інструменти.** У нас одна спека PM, яка змінюється вже за тиждень, поки команда в тому
самому репозиторії пише за нею код. Кожна зміна спеки — окремий PR, який рев'юїть техлід, і з дельти видно, що саме
змінилося і які задачі з цього виростуть.

| Інструмент | Чому не основний |
|---|---|
| **OpenSpec** (беремо) | першокласні дельти, детермінований `archive` у гілці PR, валідатор із кодом виходу для CI, встановлення через npm |
| Spec Kit (GitHub) | механізму дельт немає: як спека змінюється з часом, команда домовляється сама. Від нього беремо **протокол уточнень** (блок 03) |
| BMAD | важкий і потребує Python-інструмента `uv` |
| Kiro | прив'язаний до своєї IDE; від нього беремо лише нотацію вимог **EARS** (блок 02) |

**Навіщо в роботі.** Команда чи клієнт обов'язково спитають: «А чому не Spec Kit / Kiro / BMAD?». Коротка відповідь —
через дельти. Спека, яка щотижня змінюється PR-ом поруч із кодом, потребує інструмента, де кожна зміна видна окремо й
перевіряється в CI.

### Що з цього важливо (слайд 10)

На підсумковому слайді три тези:

| # | Теза | Суть |
|---|---|---|
| 01 | **Діра в тікеті — рішення агента** | чого не вирішила людина, вирішить агент — мовчки й щоразу по-різному; сильніша модель цього не виправить |
| 02 | **Spec-anchored, а не водоспад** | спека на один зріз, а не документ на 50 сторінок; вона в репозиторії й змінюється разом із кодом; SDD — Assess: легко й ітеративно |
| 03 | **Що — PM, як — розробник** | OpenSpec розводить це по файлах: `proposal.md` і дельта — PM, `design.md` і `tasks.md` — розробник (техлід із командою) |

**Завтра в роботі.** Візьміть останню задачу, яку агент зробив «не так», і знайдіть у тікеті речення, яке допускало
два прочитання. Це і є перше питання, яке хтось мав поставити до написання коду.

**Що робити далі в проєкті:**

- Те саме вміння команда тренує на зустрічі «перший раунд питань до брифу». Її проводите самі після заняття: PM
  призначає зустріч на 15–20 хвилин у день 0 або 1, ще до `spec-v0.1` ([walkthrough-pm](walkthrough-pm.md), крок 9а;
  [walkthrough-dev](walkthrough-dev.md), крок 3а). Хто не може прийти, пише свою «діру» в чат команди.
- **PM:** як написати спеку, у якій таких речень немає, — блок 02 і [шпаргалка PM](spec-guide.md).
- **Розробник:** як знаходити такі речення й перетворювати їх на питання до PM — блок 03.

## Блок 02 — PM: спека для людини й агента (слайди 11–19)

> **Одна ідея блоку:** спека — це поведінка, яку можна перевірити без доступу до коду, плюс явно записані межі й
> відкриті питання. Блок для PM, але розробникам теж варто його прочитати: у цьому форматі ви читатимете спеку,
> ставитимете питання й називатимете тести. Незнайомі терміни — у розділі [Глосарій](#глосарій).

### Бриф клієнта — ще не спека (слайд 11)

Теза слайда: «Бриф клієнта — ще не спека. Тікет на три рядки — теж.» Після дзвінка з клієнтом у PM є запис розмови, лист
і дві таблиці, а вимоги живуть у голові PM, у листах і в Jira. Розробник ще може перепитати, агент — ні: він бачить лише
записане. Тому з брифу треба зробити документ, який двоє розробників прочитають однаково, агент — однаково в кожній
сесії, а клієнт упізнає в ньому свої правила.

**Навіщо в роботі.** У блоці 01 одне речення дало п'ять реалізацій. Тут — як писати, щоб реалізація була одна.

### З чого складається спека і де живе кожна частина (слайд 12)

Ліворуч на слайді — тека `product/`: контекст продукту, який пишуть раз і потім доповнюють. Праворуч — один **зріз**
(частина продукту на тиждень), тобто окрема **зміна OpenSpec**: тека `openspec/changes/<id>/` з пропозицією й дельтою.

| Де | Файл | Що там |
|---|---|---|
| `product/` (раз на продукт) | `vision.md` · `glossary.md` · `roles.md` | мета й межі продукту · словник термінів (у демо: посада, підрозділ, заявка, запис, заблокований день) · ролі й матриця прав |
| | `roadmap.md` · `decisions.md` · `CHANGELOG.md` | WS6 — перший зріз, далі по зрізу на кожне заняття WS7–WS11 · «питання → відповідь → що змінилось» · журнал версій спеки |
| `openspec/changes/<id>/` (на зріз) | `proposal.md` | навіщо й що змінюється (розділи — нижче) |
| | `specs/<capability>/spec.md` | **дельта**: вимоги з `SHALL` і сценарії з AC ID (слайд 13) |
| `openspec/` (один на репо) | `config.yaml` | правила формату: агент отримує їх у кожному запиті, тож формат тримається сам |

Розділи `proposal.md` ідуть саме в такому порядку: його задає `openspec/config.yaml`, а `npm run spec:check` перевіряє.

| Розділ | Що писати |
|---|---|
| `## Why` | біль користувача й цінність зрізу, 2–5 речень, без реалізації |
| `## What Changes` | зміни поведінки, біля кожної — AC ID |
| `## Capabilities` | `### New Capabilities` / `### Modified Capabilities`; на кожну можливість — свій `specs/<capability>/spec.md` |
| `## Users & roles` | таблиця роль × сутність × дія для цього зрізу |
| `## Non-goals` | що могло б бути метою, але свідомо виключено, і чому |
| `## Assumptions` | що ви вирішили самі: часовий пояс, валюта, хто створює дані |
| `## Open questions` | нумеровані `Q1`, `Q2`, … — лише питання без відповіді |

`## Impact` — необов'язковий: лише вплив на продукт, без коду. **Non-goals** — не заперечення («система не падає»), а
правдоподібна мета, яку ви свідомо відклали. Без них кожен із 4–6 розробників «на всяк випадок» добудує свою зайву
фічу. (Non-goals, Assumptions і Open questions взято зі Spec Kit і дизайн-доків Google.) Стеку в спеці PM **немає**: він
записаний в `AGENTS.md` шаблону, а `config.yaml` забороняє в спеці таблиці, API, компоненти й бібліотеки — це рішення
розробника в `design.md`.

**Навіщо в роботі.** Зазвичай у клієнтському проєкті все змішано в Confluence, листах і коментарях до тікетів. Тут у
кожної частини одне місце в репозиторії команди. `product/` і `openspec/` PM змінює лише через PR, а рев'ю робить
техлід — у `.github/CODEOWNERS` він разом із PM власник цих тек.

**Що зробити:** `product/` — [walkthrough-pm](walkthrough-pm.md), крок 9; розділи зміни — [шпаргалка](spec-guide.md),
розділи 1, 2 і 5.

### Вимога в EARS, критерій — сценарієм з ID (слайд 13)

На слайді — фрагмент дельти з демо (зміна `add-leave-request`, файл `specs/leave-requests/spec.md`) і правила формату:

```markdown
## ADDED Requirements

### Requirement: Подання заявки

WHEN працівник подає заявку на відсутність …, the system SHALL створити одну заявку зі статусом `pending`
і окремий запис для кожної посади, на яку припадає відсутність.

#### Scenario: AC-LEAVE-01 Заявка на одну посаду

- **WHEN** працівник, який має лише основну посаду, подає заявку типу «хвороба» на 03.11.2026–04.11.2026
- **THEN** створено одну заявку зі статусом `pending`
- **AND** заявка має один запис — для посади `main`

### Requirement: Некоректний діапазон дат

IF дата кінця раніша за дату початку, THEN the system SHALL відхилити заявку з кодом `INVALID_RANGE`.

#### Scenario: AC-LEAVE-03 Дата кінця раніша за дату початку

- **WHEN** … початок 12.11.2026, кінець 10.11.2026
- **THEN** заявку відхилено з кодом `INVALID_RANGE`
- **AND** не збережено жодної заявки чи запису
```

1. **Вимога — одне речення EARS** (Easy Approach to Requirements Syntax: тригер, система, `SHALL`, реакція). Шаблони:
   завжди (`The system SHALL …`), подія (`WHEN …`), стан (`WHILE …`), небажана ситуація (`IF … THEN …`), опція
   (`WHERE …`). Кожна відмова з кодом помилки — окрема вимога `IF … THEN`, як «Некоректний діапазон дат».
2. **Проза українською, але `SHALL`/`MUST` і заголовки — англійською.** «ПОВИННА» замість `SHALL` валить
   `validate --strict` (і CI). Опис вимоги, довший за 500 символів, — теж.
3. **Сценарій — рівно `####`.** З `###` він мовчки зникає, і вимога падає як «без сценаріїв». Кроки — лише
   `- **WHEN**`, `- **THEN**`, `- **AND**`.
4. **Один сценарій — один AC** (критерій приймання). ID `AC-<AREA>-<NN>` (AREA — 2–12 великих латинських літер, NN — дві
   цифри) стоїть на початку назви сценарію, а потім — у назві тесту (`it("AC-LEAVE-01: …")`) і в рядку матриці
   відповідності `docs/conformance.md`. Це нитка, за яку CI тягне спеку, тест і матрицю. ID не змінюють і не
   використовують повторно.
5. **Назва вимоги — це її ID:** перейменування лише через `## RENAMED Requirements`.

Сценарії декларативні, з датами й кодами помилок, щоб їх перевірив тестувальник, який не бачив коду. На кожну вимогу —
хоча б один негативний сценарій (некоректні дані, чужі дані, заборонена роль). Приклади для ваших проєктів:
`therapy-scheduling` — «WHEN планувальник бронює слот, the system SHALL тримати його за клієнтом 24 години» (і AC з
годиною бронювання та моментом через 24 години); `property-workflows` — «WHEN менеджер запускає процес, the system
SHALL зафіксувати шаблон на момент запуску»; `school-purchasing` — «IF у заявці немає жодної позиції, THEN the system
SHALL відхилити її з кодом `NO_ITEMS`». Пишіть, як на слайді: демо-спека в [`examples/leave-portal/`](../examples/leave-portal/)
у кількох місцях порушує правила «одне речення» й «один критерій», про це сказано в її README.

**Навіщо в роботі.** У цьому форматі PM пишуть уже цього тижня. Один шаблон речення на команду прибирає розбіжності
«через стиль», а AC ID простежує кожне правило до тесту. Автори EARS кажуть, що він особливо допомагає тим, хто
пише англійською як другою мовою. У нас проза українська, а ключові слова англійські, бо так перевіряє валідатор.

**Що зробити:** [шпаргалка](spec-guide.md), розділи 3–4, [скелет зміни](spec-guide.md#скелет-зміни) і
[пастки формату OpenSpec](spec-guide.md#10-пастки-формату-openspec-1141).

### Матриця ролей і дій (слайд 14)

На слайді — матриця «роль × сутність × дія» з демо (спрощена копія `product/roles.md` демо-репозиторію):

| Сутність | `employee` | `manager` | `admin` |
|---|---|---|---|
| Заявка | створює й бачить власні; змінює лише в статусі `needs_revision` | бачить заявки, записи яких у його черзі | бачить усі |
| Запис заявки | бачить власні | схвалює або повертає записи своєї черги, поки вони на розгляді | бачить усі |
| Заблокований день | бачить | бачить | створює, бачить, видаляє |
| Підрозділ, посада | бачить назви й власні посади | бачить посади свого підрозділу | усе: створює, бачить, змінює, видаляє |

Де матриця живе далі: **у спеці** — розділ `Users & roles` у `proposal.md` і вимога «Доступ» з AC-LEAVE-09; **у
коді** — кожна клітинка стає політикою RLS (Row Level Security: правила Postgres у Supabase, які рядки користувач бачить
і змінює) на конкретну операцію, і що не дозволено політикою, те заборонено; **у тестах** — «не бачить чужих» теж AC, і
тест на заборону важить стільки ж, скільки на дозвіл. Видалення й скасування заявки та зміни рішення після схвалення
у зрізі 1 немає ні в кого — це рішення PM у Non-goals, а не діра.

**Навіщо в роботі.** Права найчастіше вирішує розробник «за здоровим глуздом», і тут найдорожчі баги: менеджер бачить
заявки чужого підрозділу. OWASP ASVS (стандарт вимог безпеки вебзастосунків) вимагає документувати правила доступу на рівні функцій і даних — матриця і є
такою документацією, тільки мовою PM.

**Що зробити:** у `product/roles.md` замініть ролі шаблону (`member`/`admin`) своїми й заповніть матрицю **без порожніх
клітинок**: дія з областю («власні», «свого підрозділу», «усі») або «—», якщо доступу немає. Клітинка, яку не можете
заповнити, — питання клієнту. Деталі — [walkthrough-pm](walkthrough-pm.md), крок 9, і [шпаргалка](spec-guide.md), розділ 6.

### Зріз за зрізом: одна зміна — один намір (слайд 15)

Перший зріз демо — `add-leave-request`, «Подання заявки на відсутність і рішення менеджера»: 5 вимог (подання,
заблоковані дні, маршрутизація, рішення менеджера, доступ), 9 AC (AC-LEAVE-01…09) і два відкриті питання: Q4 — чи
обов'язково вказувати заміну, Q5 — чи можна подати заявки з датами, що перетинаються. Поруч — Non-goals v0.1:
email-сповіщення (вбудована пошта Supabase надсилає 2 листи на годину на проєкт і лише членам організації), пряме
редагування заявки менеджером, експорт у таблицю, відсутність на кілька годин, скасування, документи, залишок відпусток.

Внизу слайда — **INVEST** Білла Вейка, парами: **I·V** — незалежний і цінний сам по собі; **N·E** — обговорюваний,
оцінюваний; **S·T** — малий і тестований. Плюс **вертикально**: інтерфейс + дія + дані + тест, а не «спершу вся база,
потім усі екрани». Решта продукту — у `product/roadmap.md`, по зрізу на заняття: агенту — один зріз, а не весь PRD (повний документ вимог до продукту).

**Навіщо в роботі.** Найчастіша помилка PM, який уперше пише для агента, — віддати весь продукт одним документом. Тоді
агент намагається зробити все за раз і рано оголошує перемогу (так Anthropic описує типові збої довгих агентних
сесій), а Thoughtworks Radar попереджає про роздуті інструкції для агента. Одна зміна — один намір, який можна сказати
одним реченням; не виходить — розбийте на дві зміни.

**Що зробити:** перший зріз беріть із розділу «Рекомендований перший зріз (WS6)» свого брифу
([брифи](../materials/briefs/)), але своїми словами. Орієнтир на тиждень — 3–5 вимог і 6–10 AC. Команда `leave-portal`:
у вашому брифі інший перший зріз, а скопійоване з демо чи `examples/` дає 0 балів ([README](../README.md#що-знімає-бали-pm)).

### Демо 1: агент інтерв'ює PM (слайд 16)

На слайді — Claude Code у репозиторії команди, створеному з шаблону (`product/` уже заповнено). PM не просить «напиши
спеку», а просить спершу розпитати:

```text
> Ось бриф зрізу «Подання заявки на відсутність і рішення менеджера».
  Спершу проінтерв'юй мене: по одному питанню, з варіантами. Нічого не вигадуй —
  чого я не знаю, пиши в Open questions.
> /opsx:propose add-leave-request
  → openspec/changes/add-leave-request/proposal.md
  → openspec/changes/add-leave-request/specs/leave-requests/spec.md
```

- **Що питає агент:** ролі й посади, хто погоджує, що із заблокованими днями, які помилки бачить працівник — по
  одному питанню, з варіантами відповіді.
- **Що бере з `config.yaml`:** порядок розділів, EARS із `SHALL`, AC ID у назві сценарію, жодних таблиць і API.
- **Що лишає PM:** Q4 і Q5 — в Open questions, а не вигадані відповіді. Q1–Q3 тут свідомо немає: їх знайде розробник
  у демо 2 (блок 03). У своїй зміні нумеруйте питання з Q1.

**Навіщо в роботі.** Агент не пише за PM, а витягує з нього рішення. Claude Code у best practices прямо радить: для
великої фічі нехай Claude спершу проінтерв'ює вас, а потім пише спеку. Сам `/opsx:propose` питає лише про «суттєві»
неоднозначності, тому інтерв'ю треба попросити явно.

**Що зробити у своєму репозиторії** ([walkthrough-pm](walkthrough-pm.md), крок 10):

```bash
git switch main
git pull
git switch -c spec/add-<зріз>
```

Далі в Claude Code — запит на інтерв'ю й `/opsx:propose <опис зрізу одним-двома реченнями>` (у Cursor — `/opsx-propose`),
з приміткою «пиши лише proposal.md і specs/, без design.md і tasks.md». Ці два файли (як реалізувати) належать окремій
зміні `impl-<зріз>` техліда з командою; якщо агент їх створив, видаліть до коміту, бо в зміні PM вони — блокер у
`spec-review`. Потім **прочитайте й виправте кожен рядок**: агент охоче вигадує правила й пише «тощо». Результати
зустрічі команди ([walkthrough-pm](walkthrough-pm.md), крок 9а) теж ідуть сюди: у вимоги, Assumptions або Open
questions. Без агента: `npx openspec new change add-<зріз>` і файли за [скелетом](spec-guide.md#скелет-зміни).

### Демо 1: перевірка й реліз спеки (слайд 17)

На слайді — конвеєр релізу в гілці `spec/add-<зріз>` і чотири пояснення:

| Крок | Що перевіряє | Роль |
|---|---|---|
| `npm run spec:validate` (`openspec validate --all --strict`) | структуру: `SHALL`/`MUST`, `####`, хоча б один сценарій, повний блок у `MODIFIED` | ворота: job `spec` у CI |
| `npm run spec:check` | AC ID на початку кожного сценарію, без повторів (`DUPLICATE-CHANGE` — дубль ID після archive), порядок розділів `proposal.md`, жодного слова з denylist | ворота: той самий job `spec` |
| скіл `spec-review` | зміст: розмиті слова, сценарії без чисел, порожні клітинки матриці | порадник, не ворота |

**Denylist** (список заборонених слів) — для анонімізації. Репозиторії публічні, тож справжніх назв клієнта немає ні в
`product/denylist.txt` (там лише загальні внутрішні слова), ні в іншому файлі, issue чи PR. Вони лежать у локальному
`product/denylist.local.txt` (у `.gitignore`) і в секреті репозиторію `SPEC_DENYLIST` для CI. `spec:check` їх читає, але
не друкує — лише номер слова («слово #2 із …»). Він також зупиниться з помилкою `STRAY-DENYLIST`, якщо Провідник Windows сховав розширення і файл
став `denylist.local.txt.txt`.

**Зелений `validate` не означає добру спеку:** «SHALL швидко завантажувати» проходить `--strict`. У демо так проходять
AC-LEAVE-02 («відсутність покриває обидві посади» — терміна немає в глосарії) і AC-LEAVE-04 («заблоковані дні не рахуються» — THEN без вимірного результату), хоча обидва неоднозначні.
Форму перевіряє машина, зміст — людина й скіл. `spec-review` запускає `validate` і `spec:check`, проходить чекліст AC і
11 категорій неоднозначностей, видає таблицю знахідок (БЛОКЕР / ВАЖЛИВО / ДРІБНИЦЯ) і питання, які, найімовірніше,
поставлять розробники. Правки вносить лише після вашого «так»; на кожному прогоні формулювання інші.

**Реліз у репозиторії команди** — однаковий для кожної версії ([walkthrough-pm](walkthrough-pm.md), кроки 11–12;
`spec-v0.1` — до кінця дня 2):

1. Перевірки: `npx openspec validate add-<зріз> --strict`, `npm run spec:validate`, `npm run spec:check`, потім «Запусти
   скіл spec-review для зміни add-<зріз>».
2. Коміт, push, PR типу «Зміна специфікації» (тип позначаєте галочкою в розділі «Тип PR» шаблону опису PR) з розділом `## spec-review` в описі (знахідки, що виправили, що лишили й
   чому; без нього трек B втрачає бали). Окремим коментарем — `@coderabbitai review`. Техліда запросить CODEOWNERS.
3. Кілька годин на коментарі команди: відповідь до релізу дешевша за `spec-v0.2`. Кожну розмову — Resolve conversation.
4. **У тій самій гілці, до merge:** `npx openspec archive add-<зріз> -y` (зміна йде в `openspec/changes/archive/`, а
   вимоги зливаються в чинну спеку `openspec/specs/<capability>/spec.md`), запис `## spec-v0.1 — <дата>` у
   `product/CHANGELOG.md` за форматом із коментаря у файлі, **рядок на кожен новий AC** у `docs/conformance.md`. Далі
   `npm run spec:validate`, `npm run ac:coverage`, коміт і push.
5. CI зелений → техлід схвалює **зараз**, після вашого останнього push → merge (squash — усі коміти PR одним комітом у `main`, або merge commit — окремий коміт злиття).
6. Тег на `main`:

```bash
git switch main
git pull
git tag spec-v0.1
git push origin spec-v0.1
```

Рядок матриці для нового AC (статус — дослівно):
`| AC-<AREA>-01 | <що перевіряє> | — | — | відкладено (новий AC — чекає задачі) |`. Без нього job `conformance`
(`npm run ac:coverage`) червоний з `NO-ROW` (AC у спеці є, рядка немає), і PR не злити; потім рядки змінюють розробники в
PR задач. Archive й рядки — у гілці, бо прямий коміт у `main` ruleset не пустить. Approve техліда рахується лише після цих комітів (раніший approve не діє), бо ruleset
вимагає approve **останнього** push від людини, яка його не робила: спершу всі коміти, потім approve, потім merge.

Тег можна поставити й через Code → Releases → Draft a new release, новий тег на `main` (точні назви кнопок перевірте в
інтерфейсі). Перевірка: на `https://github.com/<pm>/<team-slug>/tree/spec-v0.1/openspec/specs` є тека вашої можливості,
а в `openspec/changes/` немає `add-<зріз>`. Тег після push не переносять і не видаляють: помилку виправляють PR-ом і
тегом-виправленням `spec-vX.Y.Z` (наприклад, `spec-v0.1.1`) тим самим порядком.

> **Що таке ruleset і хто його вмикає.** Ruleset — правила GitHub для гілки `main` репозиторію команди. Файл
> [`team-main.json`](../materials/rulesets/team-main.json) сам нічого не вмикає — це опис. Активує його PM у день 0
> ([walkthrough-pm](walkthrough-pm.md), крок 8), коли CI вже пройшов на `main` і в першому PR (інакше GitHub не прийме
> прив'язку перевірок до GitHub Actions): завантажує JSON у `ruleset.json` і виконує
> `gh api repos/<pm>/<team-slug>/rulesets --method POST --input ruleset.json` (або задає ті самі правила вручну в
> Settings → Rules → Rulesets). Далі їх виконує сам GitHub: `"enforcement": "active"` і порожній `bypass_actors` —
> винятків не дано нікому, зокрема власнику. Прямий push у `main` відхиляється, а PR зливається лише з approve
> колеги після останнього push (для `product/`, `openspec/`, `.github/` і міграцій — від власника коду з
> `.github/CODEOWNERS`), розв'язаними розмовами й зеленими `spec`, `app`, `conformance`, `db-check` з GitHub Actions.
> На GitHub Free це діє лише в публічному репозиторії. Детально — розділ [«Як працює ruleset»](#як-працює-ruleset) блоку 04.

**Навіщо в роботі.** Цей конвеєр PM повторює щотижня. Машина ловить форму ще до людини, рев'ю техліда й команди —
зміст, а тег дає всім одну точку відліку: «робимо за `spec-v0.1`».

### Добрий AC проти поганого (слайд 18)

| Погано | Добре | Чому |
|---|---|---|
| «Заявка обробляється коректно» | AC-LEAVE-06: після схвалення — статус `approved`, записано, хто і коли вирішив | «коректно» — діра, а не критерій |
| «Менеджер може повернути заявку з коментарем» | AC-LEAVE-07: повернення з порожнім коментарем → `COMMENT_REQUIRED`, статус лишається `pending` | названо помилку й стан; «з коментарем → `needs_revision`» — окремий AC |
| «Натискає "Подати", бачить модалку, тисне ОК…» | «WHEN працівник подає заявку … THEN створено одну заявку `pending`» | декларативно: переживе будь-який інтерфейс |
| «Обробляє некоректні дати й перетини» | `INVALID_RANGE` — свій сценарій і ID, перетин — свій AC | один сценарій — один AC |
| «Записує в таблицю `leave_items`» | «у заявці два записи: `main` і `additional`» | поведінка, а не реалізація |

Найважливіша — третя пара: скрипт кліків прив'язує спеку до одного інтерфейсу, а його переробить уже наступний зріз, і
форму й тест писатимуть різні розробники. Декларативний сценарій описує бізнес-результат і переживе будь-який UI (так
радить і Cucumber). П'ята — пастка конкретності: назва таблиці здається точною, але ламається від першого
рефакторингу й забирає в розробника його рішення. Для ваших доменів: «слот тримається якийсь час» — погано, «через 24
години без підтвердження слот знову вільний» — добре; для грошей валюту й точність запишіть в Assumptions.

Дві перевірки внизу слайда: **тест для AC** — чи скаже тестувальник, який не бачив коду, пройдено чи ні (числа, дати,
коди помилок — так); **перевірка агентом** — попросіть агента «Напиши тест на цей AC і скажи, чого тобі бракує». Якщо
агент перепитує, AC ще не готовий. Це працює вже сьогодні, без жодного інструмента.

**Навіщо в роботі.** З цим чеклістом PM перечитує зміну перед релізом, а розробник — перед питаннями. Кожен рядок
таблиці — типова причина, чому двоє розробників реалізують «ту саму» вимогу по-різному.

**Що зробити:** [шпаргалка](spec-guide.md), розділ 7, і [чекліст перед релізом](spec-guide.md#8-чекліст-перед-релізом);
повна версія — `.claude/skills/spec-review/references/ac-quality-checklist.md` у репозиторії команди. Ці пункти дивиться
й рубрика B ([README](../README.md#трек-pm--100--5-балів)).

### Що з цього важливо (слайд 19)

1. **Поведінка, яку можна перевірити:** EARS із `SHALL`, сценарій із числами й кодами помилок, один AC — один сценарій.
2. **Межі записані явно:** Non-goals, матриця прав, Open questions. Чого PM не знає — питання, а не вигадка агента.
3. **Машина — форма, людина — зміст:** `validate` і `spec:check` — ворота; `spec-review` і колеги — рев'ю змісту.

**Завтра в роботі:** перепишіть три вимоги з поточного брифу клієнта як `WHEN … SHALL` зі сценаріями з числами. Кожна
порожня клітинка матриці прав — питання клієнту. Далі спеку отримує розробник, і перше, що він робить, — ставить
питання (блок 03).

## Блок 03 — Dev: прочитати, уточнити, розбити (слайди 20–26)

PM випустив `spec-v0.1`, і спека дісталася розробникам. Ідея блоку одна: розробник читає спеку системно, ставить
питання PM і лише потім розбиває роботу на задачі для агента. Кожна задача має перевірку «Done when». Покроково
все це описано у [walkthrough-dev](walkthrough-dev.md), кроки 3а–6.

### Спека прийшла в понеділок (слайд 20)

На слайді коротка історія. Спека прийшла в понеділок зранку. Розробник віддав її агенту цілою, агент закрив усі
задачі, тести зелені, і до обіду ви чуєте «done». А на демо клієнт питає, чому заблокований день «з'їв» заявку
на відпустку. У спеці відповіді на це не було, її вигадав агент, і вигадав дуже впевнено.

**Навіщо в роботі.** В агенції ми звикли, що розробник цінний своїм кодом. З агентом код дешевий, а дорогими
стають рішення, яких бракує в спеці. Якщо діри не знайде розробник, їх мовчки заповнить агент, і кожен агент
по-своєму. Тому робота розробника починається з питань, а не з коду.

### Де ховаються діри: 11 категорій (слайд 21)

Порада «прочитай уважно» не працює, бо і люди, і агенти бачать у тексті те, що очікують. Тому читаємо за
**таксономією неоднозначностей**, тобто за чеклістом із 11 категорій тих місць, де спека найчастіше буває
неповною або двозначною. Для кожної категорії ставите статус **Ясно**, **Частково** або **Немає** і записуєте,
де саме (AC ID або назва вимоги). AC (критерій приймання) — це сценарій з ID на кшталт `AC-LEAVE-04`
(див. [Глосарій](#глосарій)).

| # | На слайді | Назва у формі issue | Що шукати |
|---|---|---|---|
| 1 | Обсяг | Функціональний обсяг | що входить у зріз, що свідомо винесено в Non-goals, хто з ролей що робить |
| 2 | Ролі й доступ | Ролі й доступ | матриця «роль × сутність × дія», хто бачить і змінює чужі дані |
| 3 | Домен і дані | Домен і модель даних | сутності, зв'язки, унікальність, стани й переходи між ними |
| 4 | Потік (UX) | Потік взаємодії (UX) | що людина бачить після помилки, на порожньому екрані, після дії |
| 5 | Нефункціональні | Нефункціональні вимоги | обсяги, аудит «хто і коли», часові пояси, приватність |
| 6 | Інтеграції й платформа | Інтеграції й обмеження платформи | пошта, розклад задач, зовнішні сервіси й ліміти безкоштовних тарифів |
| 7 | Граничні випадки | Граничні випадки й збої | перетини, повторні дії, порожні й некоректні дані, паралельні зміни |
| 8 | Обмеження | Обмеження й компроміси | технічні й бізнесові обмеження, варіанти, які вже відкинули |
| 9 | Термінологія | Термінологія | чи є кожен термін у `product/glossary.md`, синоніми, слова без визначення |
| 10 | Завершеність | Сигнали завершеності | чи можна перевірити AC, не бачачи коду: числа, дати, коди помилок |
| 11 | Розмиті слова | Заглушки й розмиті слова | «тощо», «швидко», «зручно», «за потреби», TODO без кількісної межі |

Основа таблиці — таксономія з команди `/speckit-clarify` інструмента Spec Kit. У неї десять категорій, а ми
додали «Ролі й доступ». Ліміти безкоштовних тарифів ми записали в категорію 6, бо спеки клієнтів часто
ламаються першими саме там. Вбудований SMTP Supabase надсилає лише 2 листи на годину на проєкт і лише членам організації, а cron
на Vercel Hobby запускається щонайбільше раз на добу. Повна таблиця з прикладами питань лежить у репо вашої
команди: `.claude/skills/spec-clarify/references/ambiguity-taxonomy.md`. Коротка версія є в
[spec-guide, розділ 9](spec-guide.md#9-таксономія-неоднозначностей).

**Правило питання** (дванадцята картка слайда):

- питаєте про **поведінку** («система відхиляє заявку»), а не про реалізацію («додати колонку»);
- одне питання стосується однієї неоднозначності й має посилання на AC ID або вимогу;
- даєте 2–5 взаємовиключних варіантів, свою **рекомендацію** з коротким «чому» і **вплив**, тобто які AC,
  тести, дані чи екрани зміняться залежно від відповіді;
- не питаєте про те, що вже вирішено (у `product/decisions.md`, в issues, журналах колег), і не питаєте про стек та
  архітектуру, бо це рішення розробника (ADR у `docs/decisions/`).

Із варіантами й рекомендацією PM відповідає за хвилину, а не за день.

**Навіщо в роботі.** Чекліст перетворює читання на прохід по категоріях: так ви не пропустите цілий клас дір,
наприклад «а що бачить користувач, у якого ще немає жодного запису?».

### Демо 2: скіл `spec-clarify` (слайд 22)

**Скіл** — це записана інструкція для агента, яку він виконує на ваше прохання. Скіл `spec-clarify` уже є в
шаблоні: `.claude/skills/spec-clarify/SKILL.md`. Протокол ми взяли в Spec Kit (`/speckit-clarify`).

У демо розробник у репо команди на версії `spec-v0.1` попросив агента уточнити спеку. Скіл зробив таке:

1. Пройшов 11 категорій і склав таблицю статусів. У шаблоні, з яким працюєте ви, скіл записує цю таблицю в розділ
   `## Скан за таксономією` вашого особистого журналу `docs/spec-reading/<login>.md`.
2. Склав чергу питань за принципом «вплив × невизначеність». Питання, які не змінюють ні код, ні тести, він
   відкинув.
3. Ставив **не більше п'яти питань, по одному**. До кожного давав варіанти, рекомендацію й вплив, а потім питав
   розробника, чи ставити це питання PM: залишити, змінити чи пропустити.
4. Для прийнятих питань видав готові тексти issues і додав рядки в журнал.

П'ять питань із демо (спека порталу відсутностей):

| Q | Де | Питання до PM |
|---|---|---|
| Q1 | `AC-LEAVE-02` | Що означає «покриває обидві посади»? |
| Q2 | `AC-LEAVE-04` | Заблокований день у діапазоні: відхилити заявку чи виключити цей день? |
| Q3 | `AC-LEAVE-05` | Посади у двох підрозділах: два менеджери? |
| Q4 | Open questions | Чи обов'язкова заміна? |
| Q5 | Open questions | Чи можна подати дві заявки з датами, що перетинаються? |

Q4 і Q5 PM сам записав у розділ Open questions своєї спеки, і скіл їх підхопив, а не вигадав нових. Q2 добре видно
завдяки категорії «Сигнали завершеності». Фраза «заблоковані дні не рахуються» здається очевидною, але не каже, чи
заявку взагалі прийнято, і тест на неї не напишеш.

Головне правило на слайді: **відповідає PM, а не скіл і не розробник.** У Spec Kit відповіді записують прямо в
спеку. У нас спека належить PM, тому скіл не змінює `product/` і `openspec/specs/`, а питання йдуть до PM як issues
у репо команди. Скіл недетермінований: формулювання питань щоразу будуть інші, тож ваші питання не збігатимуться з таблицею слово
в слово.

**Як це зробити у вашому репо** ([walkthrough-dev, крок 4](walkthrough-dev.md#4-читання-спеки-й-питання-1-год--трек-b)):

```bash
git switch main
git pull                                              # після тегу spec-v0.1 спека — в openspec/specs/
gh issue list --label spec-question --state all       # які питання вже поставили колеги
```

Потім у Claude Code або Cursor напишіть: «Уточни спеку spec-v0.1 скілом spec-clarify». Але спершу **перечитайте
спеку самі** й запишіть свої питання. У журналі має бути видно, що знайшли ви, а що скіл (розділ «Що пропустив би
без скіла / що скіл знайшов зайве»). Як виглядає готовий журнал, дивіться в
[зразку з демо](../examples/leave-portal/2-clarify/spec-reading.md).

**Навіщо в роботі.** Так ви за 10–15 хвилин проходите будь-яку нову спеку клієнта ще до старту робіт.

### Питання — issues у репо команди, рішення — в журнал (слайд 23)

**Куди йде питання.** Питання в чаті губляться, а відповідь PM на дзвінку чує одна людина. **Issue** (картку
обговорення на вкладці Issues у GitHub) у репо команди бачать усі, тож одне питання отримує одну відповідь для всієї
команди й усіх її задач.

- Issue створюєте **ви, у вебформі**: `https://github.com/<pm>/<team-slug>/issues/new/choose` → «Питання до
  специфікації». Поля вставляєте з тексту, який видав скіл. Сам скіл issues не створює: агент не пише в GitHub від
  вашого імені (це правило курсу ще з WS2 і WS5).
- Поля форми (`.github/ISSUE_TEMPLATE/spec-question.yml`): версія специфікації, вимога / AC, категорія (список із
  тих самих 11), питання, варіанти відповіді, рекомендований варіант, вплив. Заголовок виглядає як
  `[spec-question] AC-…: <коротко>`. Зразок заповненого issue є в [issue-Q2.md](../examples/leave-portal/2-clarify/issue-Q2.md).
- Форма сама ставить мітку `spec-question`, якщо PM створив мітки `spec-question` і `task` у день 0. Якщо мітки
  немає, нагадайте PM ([walkthrough-pm, крок 2](walkthrough-pm.md)).
- **Без дублікатів.** Бачите своє питання в issue колеги? Допишіть туди коментар із новим випадком, варіантом чи
  впливом. В issues і PR того самого репо на інше issue можна послатися просто `#N`.
- Поки зміна PM ще у відкритому PR (дні 1–2), питання можна залишати коментарями до рядків цього PR: це
  найдешевший момент для відповіді.

**Журнал** `docs/spec-reading/<login>.md` у кожного свій, щоб паралельні PR-и не конфліктували. Структуру описано в
`docs/spec-reading/README.md`. Таблиця питань у журналі виглядає так (рядки з демо, поки PM ще не відповів):

| # | AC / вимога | Питання | Рекомендація | Issue | Відповідь PM | Рішення (що зробили) |
|---|---|---|---|---|---|---|
| Q1 | `AC-LEAVE-02` | «покриває обидві посади»? | A: працівник позначає посади галочками | `<pm>/<team-slug>#1` | очікуємо | робоче припущення A |
| Q2 | `AC-LEAVE-04` | заблокований день у діапазоні? | B: приймаємо, день виключаємо з кількості | `<pm>/<team-slug>#2` | очікуємо | робоче припущення B |

**Робоче припущення** — це рішення, за яким ви працюєте, поки PM не відповів. Команда не чекає без потреби. Якщо є
розумне типове значення (у демо Q1, Q2, Q3), працюєте за записаним припущенням і переробите, якщо PM відповість
інакше. Якщо такого значення немає (Q4 — поле заміни, Q5 — перевірка перетину), цю частину не робите й чекаєте. У
матриці відповідності `docs/conformance.md` такий AC має статус «відкладено» з посиланням на питання, наприклад
`відкладено (чекаємо відповідь PM на Q4, <pm>/<team-slug>#N)`.

Що далі відбувається з відповіддю. PM відповідає в issue і записує рішення в `product/decisions.md`. Якщо відповідь
змінює поведінку, PM випускає нову версію спеки (`spec-v0.2`) і в тому самому PR додає в матрицю рядки нових AC зі
статусом `відкладено (новий AC — чекає задачі)`. Задачу за новою поведінкою не починайте до цього тегу. У назвах
тестів мають бути лише ті AC ID, що вже є в `openspec/specs/` на `main`, інакше `npm run ac:coverage` покаже
`ORPHAN` (тест посилається на AC, якого немає в спеці).

**Що зараховується в домашці (трек B розробника, [README](../README.md#трек-розробника--100--5-балів)):**

- щонайменше 3 питання: власні issues `spec-question` або коментарі з новим варіантом чи впливом у наявному issue
  колеги; з них щонайменше 1 має бути власним issue;
- журнал `docs/spec-reading/<login>.md` у `main`: скан за 11 категоріями, таблиця питань з посиланнями
  `<pm>/<team-slug>#N`, відповіддю PM і рішенням, розділ «Власні припущення», що знайшли ви, а що скіл;
- журнал додаєте окремим PR типу «Онбординг» (гілка `onboarding/<login>-spec-reading`), потім рев'ю колеги й
  Squash and merge.

**Навіщо в роботі.** Журнали й issues усіх розробників разом складаються в карту неоднозначностей спеки. PM
бере її в підсумкову нотатку й на demo day: де одна й та сама спека прочиталась по-різному.

### Задачі для агента: вертикально й з «Done when» (слайд 24)

Питання поставлено, припущення записано, тепер команда перетворює спеку PM на план для агента. Спека каже, **що**
має робити система, а **як** це зробити й як поділити роботу, вирішує команда.

**1. Зміна команди `impl-<зріз>`.** План оформлюють як окрему OpenSpec-зміну. Її готує техлід (один із розробників,
якого обрала команда) разом із командою, окремим PR-ом
([walkthrough-dev, крок 5](walkthrough-dev.md#5-план-impl-зріз-і-задачі-разом-із-техлідом-3045-хв--трек-c)):

```bash
git switch main
git pull
git switch -c spec/impl-<зріз>
npx openspec new change impl-<зріз>
# у openspec/changes/impl-<зріз>/.openspec.yaml допишіть рядок: skip_specs: true
npx openspec validate impl-<зріз> --strict
```

Ця зміна не змінює поведінку, описану в спеці, а реалізує її. Тому потрібен прапорець `skip_specs: true`. Без нього
`validate --strict` падає з помилкою «at least one delta» (зміна без дельт спеки). Пишіть назву точно: `skip_spec`
без «s» OpenSpec мовчки ігнорує. PR має тип «Зміна специфікації», а схвалює його PM, бо техлід тут автор. PM
перевіряє, що кожен AC зрізу покрито задачею і що в `design.md` немає нових правил поведінки.

**2. `design.md`** містить технічні рішення, яких PM свідомо не приймав: таблиці й міграції з GRANT (дозволи ролей
бази на таблицю) і RLS (Row Level Security, правила Postgres про те, хто які рядки бачить і змінює), server actions
(серверні функції, які викликають форми застосунку) і сторінки. Кожне рішення посилається на AC ID. Назви таблиць і
функцій команда обирає тут один раз, і всі задачі далі їх тримаються. Рішення, яких спека не дає (модель даних,
бібліотеки), записуйте як ADR (Architecture Decision Record, короткий запис рішення) у `docs/decisions/`.

**3. `tasks.md`** містить задачі, кожна з яких закінчується рядком `Done when: AC-…`. На слайді були дві задачі з демо:

- **2.1** Таблиці заявок і записів, функція бази для подання, валідація, сторінка `/requests/new` (тип, дати,
  галочки посад) і тести. *Done when: AC-LEAVE-01, AC-LEAVE-02 — тести зелені, заявка на дві посади дає два записи.*
- **2.2** Перевірка «дата кінця ≥ дати початку» в базі й валідація з помилкою `INVALID_RANGE` ще до запису в базу,
  плюс тест. *Done when: AC-LEAVE-03.*

Повний зразок плану є в [tasks.md](../examples/leave-portal/3-impl/tasks.md) і
[design.md](../examples/leave-portal/3-impl/design.md). Це формат, а не відповідь, бо у вашої команди свій зріз.

Головні принципи зі слайда:

- **Вертикальний зріз.** Інтерфейс, дія, таблиця з RLS і тест в одній задачі, а не «спершу вся база, потім усі
  екрани». Задач має вистачити кожному розробнику, щонайменше по дві, тому задача може бути одним AC або однією
  областю одного AC (міграція й RLS, дія, UI).
- **Done when = AC ID.** Агент знає, що перевірити, а рев'юер знає, що приймати. Те саме радять OpenAI для Codex
  (Goal, Context, Constraints, Done when) і GitHub для задач агенту.
- **Задача → issue → гілка → PR → рев'ю.** Після merge плану техлід або PM заводить issues за формою «Задача»
  (мітка `task`): AC ID, що зробити, Done when, область. Кожен призначає собі свої (Assignees). Далі гілка
  `task/<N>-<коротко>`, PR з рядком `Closes #N` (issue закриється саме після merge), рев'ю колеги, Squash and merge.
  Деталі описано у [walkthrough-dev, крок 6](walkthrough-dev.md).
- **Одна задача — одна сесія агента.** Дайте агенту одну задачу, а не всю спеку: тоді він не намагається зробити все
  за раз і не оголошує перемогу зарано. У Claude Code може допомогти `/opsx:apply impl-<зріз>`. Галочок у `tasks.md`
  у PR задачі не ставте: прогрес видно із закритих issues.
- **RLS, auth і міграції** завжди проходять рев'ю людиною. Міграції за CODEOWNERS схвалює техлід або PM.

**Архітектуру агенту задають файли, а не промпт:** `design.md` зміни й ADR у `docs/decisions/`. `AGENTS.md` шаблону
велить агенту читати їх і не переписувати мовчки. У спільному репо це критично, бо інакше агенти п'ятьох розробників
збудують п'ять несумісних шматків.

Порада щодо гілок. Ruleset на `main` вимагає approve після останнього push, тож оновлюйте гілку з `main`, лише
коли GitHub показує конфлікт. Після оновлення попередній approve втрачає силу, і потрібне повторне рев'ю.

**Навіщо в роботі.** На цьому кроці спека перетворюється на план, який можна роздати людям і агентам і перевірити за
AC, а не за словами «зроблено».

### Практика: перший раунд питань до брифу (слайд 25)

Цю практику **команда проводить сама після заняття**. PM призначає коротку зустріч (дзвінок на 15–20 хвилин) у
день 0 або 1, ще до `spec-v0.1`, і кличе всіх розробників. Матеріал — бриф вашої команди в
[брифах](../materials/briefs/), розділ «Рекомендований перший зріз (WS6)». Агента тут не запускаємо, бо спершу
треба відчути таксономію руками.

| Хвилини | Хто | Що робить |
|---|---|---|
| 2 хв | PM | читає вголос мету зрізу і три ключові правила з брифу |
| 4 хв | розробники | кожен називає одну діру: що неясно, категорію з одинадцяти і 2–3 варіанти поведінки |
| 3 хв | PM | відповідає або записує питання як відкрите |
| 1 хв | усі | підсумок: одне питання, яке найбільше здивувало PM |

**Що лишається після зустрічі:** список «питання → відповідь» або «питання → відкрите». PM переносить відкриті
питання в Open questions свого `proposal.md` до `spec-v0.1`. Розробники оформлюють свої питання як issues після
релізу спеки. Хто не зміг прийти, пише свою діру в чат команди до кінця дня 1. Якщо зібратися не вдається взагалі,
ту саму розмову ведіть асинхронно в чаті команди: PM публікує мету й три правила, кожен розробник до кінця дня 1
пише одну діру з категорією, а PM відповідає там само або записує її в Open questions. Окремих балів за зустріч
немає, але її результат потрапляє в Open questions PM і у ваші питання після релізу.

**Правила:** питання стосуються поведінки й мають 2–3 варіанти. Жодних назв клієнтів і реальних даних у нотатках,
бо репозиторії публічні.

Приклади дір (у кожному взято одне правило з брифу команди):

- `property-workflows`, «Запуск завершено, коли виконано всі обов'язкові задачі» → *Граничні випадки*: шаблон без
  жодної обов'язкової задачі. Запуск завершено одразу, ніколи чи такий шаблон не запускається?
- `therapy-scheduling`, «Слот тримається 24 години з моменту бронювання» → *Граничні випадки*: клієнт підтверджує
  рівно на 24-й годині. Слот ще його чи вже вільний?
- `school-purchasing`, «Повернення на доопрацювання й відхилення вимагають коментаря» → *Потік*: після доопрацювання
  заявка йде тому самому затверджувачу чи знову за правилами підрозділу?
- `leave-portal`, «Менеджер бачить посади працівників свого підрозділу» → *Ролі й доступ*: працівник має посади у
  двох підрозділах. Менеджер бачить обидві посади чи лише свою? Зверніть увагу: перший зріз `leave-portal` за
  брифом — календар і заблоковані дні, а не подання заявки, як у демо.

Покроково: [walkthrough-pm, крок 9а](walkthrough-pm.md#9а-зустріч-команди-перший-раунд-питань-до-брифу-1520-хв) і
[walkthrough-dev, крок 3а](walkthrough-dev.md#3а-зустріч-команди-перший-раунд-питань-до-брифу-1520-хв).

**Навіщо в роботі.** Саме такої розмови бракує на старті клієнтського проєкту: PM і розробники разом шукають діри
до коду, а не після демо.

### Що з цього важливо (слайд 26)

1. **Читання — за чеклістом.** 11 категорій і статус кожної. Діра, знайдена до коду, коштує одне питання, а знайдена
   після демо коштує переробки.
2. **Питання — до PM і публічно.** Issue в репо команди дає одну відповідь для всіх. Поки чекаєте, у журналі
   записано робоче рішення, а в матриці стоїть «відкладено».
3. **Задача = AC ID.** Вертикальний зріз, «Done when» з AC, далі issue → гілка → PR → рев'ю колеги.

**Завтра в роботі:** перед наступною задачею для агента приділіть спеці 10 хвилин і поставте PM три питання до
першого рядка коду. Записуйте, що вирішили самі.

## Блок 04 — Старт з нуля (слайди 27–35)

Спеку прочитали й розбили на задачі. Тепер питання: куди писати код, щоб CI бачив кожен AC? Ідея блоку одна:
**проєкт стартує з шаблону**, у якому вже зашиті шари курсу й «ворота» (автоматичні й людські перевірки перед
`main`). Команда працює в **одному репозиторії** за правилами, які тримає не дисципліна, а ruleset, CODEOWNERS і CI.
Покроково все це описано у [walkthrough-pm](walkthrough-pm.md) (кроки 1–8) і [walkthrough-dev](walkthrough-dev.md)
(кроки 1–3, 6). Терміни шукайте в розділі [Глосарій](#глосарій).

### Новий клієнт — новий репо (слайд 27)

На слайді знайома історія: новий клієнт, новий репозиторій і тиждень на «налаштувати». Репозиторій, база, деплой,
секрети, CI щоразу ті самі, але кожен розробник робить їх трохи інакше. Ключ від бази їде в чат. Preview (тимчасова
копія сайту для гілки чи PR) відкривається лише автору, тож PM не бачить результату без розробника.

**Навіщо в роботі.** Ви просили саме про це: практичний старт із репо, структурою, першими спеками, Vercel і
Supabase. З шаблону новий проєкт стартує за кілька годин і однаково в кожного. Для агенції це ще й заготовка для
кожного наступного клієнтського проєкту.

### Шаблон і репо команди (слайд 28)

Шаблон — [`koldovsky/2026-quitcode-06-project-template`](https://github.com/koldovsky/2026-quitcode-06-project-template):
Next.js 16 + Supabase + OpenSpec, готовий до Vercel. Це публічний GitHub template, тобто репозиторій, з якого
кнопкою **Use this template** створюють новий. Усе з попередніх занять уже лежить у ньому:

| Шар курсу | Де в шаблоні |
|---|---|
| WS3 · правила | `AGENTS.md` (межі always / ask / never — розділ «Межі»: що агент робить завжди, що лише спитавши, а чого ніколи); `CLAUDE.md`, який імпортує `AGENTS.md` (`@AGENTS.md`; коли поруч є `CLAUDE.md`, Claude Code сам `AGENTS.md` не читає) і додає кілька коротких правил; команди в `.claude/commands/` |
| WS4 · скіли | `spec-clarify` (розробник), `spec-review` (PM), `/conformance`, `/opsx:*` |
| WS5 · MCP | `.mcp.json`: Supabase MCP лише на читання (`read_only=true`); `.claude/settings.json` забороняє агенту читати `.env*` і запускати `supabase db push` та інші деструктивні команди Supabase CLI |
| WS6 · спека | `product/`, `openspec/`, скрипти перевірок `scripts/check-*.mjs`, `docs/` |
| Ворота | `ci.yml`, `CODEOWNERS`, форми issues «Питання до специфікації» і «Задача», шаблон PR, `.coderabbit.yaml` |

> `.mcp.json` і `.claude/settings.json` читає лише Claude Code. Cursor бере MCP з `.cursor/mcp.json`, а заборону
> відкривати `.env*` агентом у Cursor тримає тільки ваша дисципліна. Скіли з `.claude/skills/` Cursor читає з тієї ж теки.

**Репо команди одне на всіх.** PM натискає **Use this template** у своєму особистому акаунті й одразу ставить
**Public**. Виходить `<pm>/<team-slug>`: одна спільна реалізація, без форків.

```text
шаблон
  └─ Use this template → <pm>/<team-slug>   (особистий акаунт PM, публічний з першого push)
        ├─ main             ← лише через PR: 1 approve, Code Owners, зелений CI; теги spec-vX.Y
        ├─ spec/<id>        ← PM: зміна специфікації (рев'ю техліда)
        ├─ task/<N>-…       ← розробник: задача з issue #N (рев'ю колеги)
        └─ onboarding/<login>
  Supabase: організація <team-slug> у PM, один проєкт; розробники з роллю Developer; міграції застосовує CI
  Vercel: проєкт PM; прод з main, preview на кожен PR
```

| Роль | Хто | Що робить |
|---|---|---|
| PM | власник репо, організації й проєкту Supabase, проєкту Vercel | налаштування, `product/` і зміни спеки, відповіді на питання, теги `spec-vX.Y`, задачі разом із техлідом |
| Техлід | один із розробників (обирає команда) | співвласник спеки в CODEOWNERS, рев'ю PR-ів PM зі спекою, план `impl-<зріз>` разом із командою, `npm run users:demo` |
| Розробник | collaborator, тобто учасник репо з правом запису (Write) | онбординг, питання до спеки, задачі через PR, рев'ю PR-ів колег |

Чому саме так:

- **Особистий акаунт, а не організація GitHub.** Імпортувати особисте репо у Vercel Hobby може лише його власник, а
  про організації на Hobby документація Vercel суперечить сама собі. Ціна: в особистому репо немає teams і ролі
  Maintain. Усі розробники — однакові collaborators, а налаштування є лише в PM.
- **Public з першого push.** На GitHub Free ruleset, CODEOWNERS і секрети environment діють лише в публічних репо.
  А коміти колег, запушені, поки репо було приватним, Vercel Hobby блокує, і вони лишаються заблокованими навіть
  після відкриття. Тому в репо лише вигадані дані, а справжні назви клієнта зберігаються окремо (слайд 31).
- **Автор не схвалює власний PR.** Так влаштований GitHub. Тому PR PM зі спекою схвалює техлід, а PR розробника —
  колега. У `.github/CODEOWNERS` на кожному «чутливому» шляху записано двох: на `/product/`, `/openspec/` і `/.github/`
  стоять PM і техлід, на `/supabase/migrations/` — техлід і PM. Якщо власник на шляху один, він свій PR не зіллє ніколи.
- **CODEOWNERS не гарантує, що спеку схвалить саме PM.** GitHub достатньо approve будь-кого зі списку власників
  шляху. «Спеку вирішує PM» — це домовленість команди, а не технічний замок.
- **Bypass у ruleset порожній.** Через PR іде навіть PM, і в день 0 він це перевіряє (див. «Як працює ruleset» нижче).

README шаблону — покроковий рецепт того, як шаблон зібрано і як повторити це для нового клієнта. Це перший випадок
повторного використання між проєктами: правила, скіли, ворота й рецепт переходять у кожен новий проєкт. Про спільні
скіли й компоненти між проєктами поговоримо на WS9.

### Як працює ruleset

Ruleset — це набір правил GitHub для гілки: що можна і чого не можна робити з `main`. Файл
[`materials/rulesets/team-main.json`](../materials/rulesets/team-main.json) у курсовому репо **сам нічого не
вмикає**. Це лише опис правил у форматі GitHub, «рецепт». Діяти він починає тоді, коли PM імпортує його в репо команди
([walkthrough-pm](walkthrough-pm.md), крок 8):

```bash
curl -sLo ruleset.json https://raw.githubusercontent.com/koldovsky/2026-quitcode-06-specs-in-practice-hw/main/materials/rulesets/team-main.json
gh api repos/<pm>/<team-slug>/rulesets --method POST --input ruleset.json
rm ruleset.json
```

У PowerShell пишіть `curl.exe` замість `curl` і `Remove-Item ruleset.json` замість `rm`. Можна й без терміналу:
Settings → Rules → Rulesets → New ruleset → Import a ruleset і вибрати цей файл. Або виставити ті самі пункти вручну
за walkthrough-pm. Точні назви пунктів перевірте в інтерфейсі.

Після імпорту правила **тримає сам GitHub на своєму боці**. Він перевіряє кожен push у `main` і кожну спробу merge,
хоч би хто натискав кнопку, з якого ноутбука і з агентом чи без. Ось що саме є у файлі:

| Правило в JSON | Що це означає для команди |
|---|---|
| `conditions` → `~DEFAULT_BRANCH` | правила діють на гілку за замовчуванням, тобто на `main` |
| `enforcement: active`, `bypass_actors: []` | правила ввімкнені, і винятків немає ні для кого, зокрема для власника репо |
| `deletion`, `non_fast_forward` | `main` не можна видалити чи переписати force push |
| `pull_request` → `required_approving_review_count: 1` | у `main` можна потрапити лише через PR з approve щонайменше однієї людини, яка не є автором |
| `require_code_owner_review: true` | PR, що чіпає шлях із `.github/CODEOWNERS`, має схвалити хтось із власників цього шляху |
| `require_last_push_approval: true` | approve має стояти після останнього push і бути від когось, хто цей push не робив. Новий коміт, кнопка **Update branch** чи злиття `main` у гілку вимагають нового approve |
| `dismiss_stale_reviews_on_push: false` | approve не знімається, коли в `main` щось злили; інакше кожен merge знімав би approve з усіх відкритих PR. Рядку вище це не суперечить: після нового push у вашу гілку для merge однаково потрібен свіжий approve |
| `required_review_thread_resolution: true` | усі обговорення рев'ю, зокрема коментарі CodeRabbit, мають бути розв'язані (Resolve conversation) |
| `allowed_merge_methods: squash, merge` | задачі зливаємо через Squash and merge; merge commit — запасний шлях, якщо Vercel блокує коміти колеги |
| `required_status_checks`: `spec`, `app`, `conformance`, `db-check` | ці jobs CI мають бути зеленими. `integration_id` прив'язує їх до GitHub Actions, а `strict_required_status_checks_policy: false` означає, що гілку не треба оновлювати після кожного чужого merge |

Ruleset лише **вимагає**, щоб перевірки були зеленими. Самі перевірки запускає `ci.yml` (слайд 32), тому назви
jobs у ньому не змінюйте. Зміни в `.github/` (зокрема в `ci.yml` і самому `CODEOWNERS`) схвалює PM або техлід як
власники коду, тож тихо послабити перевірки в PR задачі не вийде. Хто є власником коду, визначає `.github/CODEOWNERS`, а ruleset робить approve власника
обов'язковим.

Ruleset запрацює лише за чотирьох умов:

1. **Репо публічне.** На GitHub Free rulesets діють тільки в публічних репо.
2. **CI вже був зеленим.** Ruleset створюють після першого зеленого прогону CI на `main` і в першому PR
   (`setup/codeowners`). GitHub приймає прив'язку обов'язкових перевірок до GitHub Actions лише тоді, коли Actions уже
   звітували ці перевірки в цьому репо. Якщо `gh api` відповідає помилкою про `integration_id` або перевірка не
   знаходиться в пошуку, дочекайтеся зеленого прогону й повторіть.
3. **Потрібні методи злиття ввімкнені.** У Settings → General → Pull Requests увімкніть **Allow merge commits** і
   **Allow squash merging** (за замовчуванням вони вже ввімкнені).
4. **У CODEOWNERS — логіни людей, які вже прийняли інвайт.** Логін без доступу GitHub мовчки ігнорує, і PR PM зі
   спекою не буде кому схвалити.

**Перевірка в день 0.** Команда `gh api repos/<pm>/<team-slug>/rulesets` показує ruleset, а на власному PR PM кнопка
merge заблокована, доки немає approve. Якщо GitHub таки дає власнику злити свій PR без approve (хоч не повинен), не користуйтеся цим і напишіть у чат курсу.
Рубрика A перевіряє approve колеги на кожному PR у `main`. Послаблений ruleset (0 approve, без Code Owners, з bypass,
без обов'язкових перевірок) теж знімає бали ([README](../README.md)).

### Дев'ять перевірених пасток (слайд 30)

**Навіщо в роботі.** Саме ці пастки з'їдають перший тиждень кожного командного проєкту. Шаблон і його чеклісти
обходять кожну з них. Але агент, якого ви попросите «налаштувати проєкт», наступить на половину. Перші чотири
пастки — нові саме для роботи в одному репо, решта стосується стеку.

| Пастка | Що відбувається | Як обходимо |
|---|---|---|
| Свій PR не схвалити | GitHub не дає автору схвалити власний PR | PR PM зі спекою схвалює техлід; у `CODEOWNERS` на кожному шляху двоє |
| Міграції — лише через PR | `db push` з ноутбука лишає в базі версію, якої немає в `main`. DDL (команди зміни схеми: `create`, `alter`, `drop`) у SQL Editor змінює схему без міграції. Після цього `db-deploy` падає в усієї команди | `migration new` → PR → `db-check` → рев'ю → merge → `db-deploy`. Роль Developer бачить SQL Editor, тож це правило команди, а не замок |
| Developer, не Administrator | ліміт Supabase Free — 2 активні проєкти на всі організації, де ви Owner або Administrator | розробників запрошуємо роллю **Developer**, вона слота не займає |
| Public з першого push | коміти колег із часів, коли репо було приватним, Vercel Hobby блокує й після відкриття; ruleset на Free діє лише в публічних репо | репо публічне з першої хвилини |
| Grants | Supabase прибирає автоматичні `GRANT` для нових таблиць: на нових проєктах — уже (приблизно з 30.05.2026), на всіх — з 30.10.2026. Без явного `GRANT` отримаєте `42501 permission denied` | кожна міграція містить явні `GRANT`; у `config.toml` шаблону стоїть `auto_expose_new_tables = false`, щоб CI поводився так само, як хмара |
| Ключі | тепер ключі мають вигляд `sb_publishable_…` і `sb_secret_…`. Агент за звичкою пише `ANON_KEY`, а це застаріле: від legacy-ключів Supabase відмовляється до кінця 2026 | імена беремо з шаблону й документації; Connect-сніпет у Dashboard досі показує старі імена |
| Next.js 16 | `middleware.ts` перейменовано на `proxy.ts`, а кореневий `proxy.ts` при `--src-dir` мовчки ігнорується. Cache Components (у 16.4 ввімкнені за замовчуванням) ламають build сторінки, що читає сесію через `getClaims()` | файл `src/proxy.ts`; шаблон зібрано з `--no-cache-components`. Доказ — рядок `ƒ Proxy (Middleware)` у виводі `npm run build` |
| Пошта | вбудований SMTP Supabase надсилає 2 листи на годину і лише членам організації | Confirm email і реєстрацію вимкнено, користувачів створює скрипт через Admin API (`npm run users:demo`); email-сповіщення винесено в Non-goals |

**Чому реєстрацію вимкнено.** Publishable-ключ лежить у JS-бандлі прод-URL, тож з увімкненою реєстрацією будь-хто
створить собі акаунт. `[auth] enable_signup = false` у `supabase/config.toml` — це конфігурація CLI, у хмару вона

Authentication → Users → Add user (точні назви полів перевірте в інтерфейсі). Інший шлях — запис у
`supabase/demo-users.json` через PR, після якого PM або техлід запускає `npm run users:demo`.

### Де живе кожен секрет і що робить Vercel (слайд 31)

**Навіщо в роботі.** У клієнтських проєктах секрети найчастіше течуть двома шляхами: через чат і через префікс
`NEXT_PUBLIC_`, доданий «щоб запрацювало». Усе з таким префіксом потрапляє в браузер. Таблиця відповідає на одне
питання: де живе кожен ключ і хто його бачить.

| Змінна | Де задаємо | Хто бачить і використовує |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | у `.env.local` кожного; у Vercel для Production і Preview | браузер. Це нормально: доступ до даних тримає RLS (Row Level Security, правила доступу до рядків у Postgres) |
| `SUPABASE_SECRET_KEY` | лише `.env.local` PM або техліда; у Vercel **ніколи**, ні в Production, ні в Preview | `npm run users:demo` (Admin API). Ключ **обходить RLS**, а код застосунку його не читає |
| `SUPABASE_DB_URL` | GitHub → Settings → Environments → `production` (deployment branches = `main`); рядок **Session pooler**, порт 5432 | лише job `db-deploy` на `main`; розробники пароля бази **не отримують** |
| справжні назви клієнта | локальний `product/denylist.local.txt` (не в git) у PM і в кожного розробника — PM надсилає список лише особистим повідомленням, не в загальний чат і не в issue; секрет репо `SPEC_DENYLIST` | `npm run spec:check` і job `spec`; значень вони не друкують |

Що варто розуміти:

- **Чому `SUPABASE_DB_URL` — секрет environment, а не звичайний секрет репо.** У спільному репо кожен, хто має право
  запису, може запушити гілку з workflow, який надрукує будь-який секрет репо. Секрет environment `production`
  отримує лише job, що оголошує це environment, і лише на `main`. `SPEC_DENYLIST`, навпаки, зберігають як секрет
  репо: він потрібен job `spec` у PR з будь-якої гілки, і це лише назви, а не доступ.
- **Чому Session pooler і порт 5432.** Пряме підключення на Free працює лише через IPv6, а раннери GitHub мають IPv4.
  Transaction pooler (порт 6543) для зміни схеми не годиться. Скинути пароль бази може лише Owner, тобто PM.
- **Запасний шлях міграцій**, якщо `--db-url` не спрацює: той самий job `db-deploy` у CI (не ноутбук) переходить на
  офіційний `supabase link` + `db push` з трьома секретами в тому самому environment (`SUPABASE_ACCESS_TOKEN` — токен із правами лише на проєкт команди,
  `SUPABASE_DB_PASSWORD`, `SUPABASE_PROJECT_ID`). `SUPABASE_DB_URL` тоді видаляють. Деталі — walkthrough-pm, крок 4.
- Роль Developer технічно бачить secret key у Dashboard. Тож «розробникам він не потрібен» — це правило команди, а
  не замок.
- **Межа denylist.** `spec:check` перевіряє спеку, документацію, код, сиди й тести. Знімків екрана, issues і PR він
  не бачить: там назви клієнта, імена людей і значення ключів перевіряєте ви самі.

**Ніколи** не кладіть ключі й паролі:

- у git (`.env*` уже в `.gitignore`);
- у чат з агентом (у Claude Code діє deny на `Read(.env*)`);
- у секрети репо (їх прочитає workflow будь-якої гілки).

Якщо ключ потрапив у репо, навіть лише в історію git, ключі обов'язково ротують, а для розробника це ще й 0 за трек A
([README](../README.md)).

**Vercel Hobby.** Імпортує проєкт лише PM, власник особистого репо. Дві змінні `NEXT_PUBLIC_…` додаємо вручну, а не
через Marketplace-інтеграцію Supabase. Та інтеграція створює окрему організацію Supabase, займає слот і може
принести старі імена `ANON_KEY`. Після зміни змінних потрібен **Redeploy**, бо змінні діють лише на нові деплої.
Preview створюється на кожен PR. Dashboard і логи Vercel бачить тільки PM. Розробникам статус збірки й preview видно
в PR, а помилки збірки — у job `app` CI.

Hobby дозволяє лише некомерційне особисте використання. Тому наш застосунок навчальний: дані вигадані, брендингу
клієнта немає. Cron на Hobby спрацьовує щонайбільше раз на добу. Чому відкриті preview прийнятні лише за трьох
правил, читайте у [walkthrough-dev](walkthrough-dev.md#ризики-відкритих-preview).

Схему бази змінюємо лише міграціями через PR, кожна таблиця має RLS і явні `GRANT`. Чекліст міграції й порядок
зміни набору ролей є в [додатку цього конспекту](#supabase-без-docker-міграції-через-pr-слайд-46) (слайд 46), в `AGENTS.md` шаблону і в [walkthrough-dev](walkthrough-dev.md) (крок 6.1).
Детальніше про базу поговоримо на WS7.

### CI: один workflow, п'ять jobs (слайд 32)

**Навіщо в роботі.** CI прив'язує спеку до коду і захищає спільну базу від «швидко поправлю». Jobs однакові для
кожного PR і кожної гілки, без особливих умов. Сам файл —
[`.github/workflows/ci.yml`](https://github.com/koldovsky/2026-quitcode-06-project-template/blob/main/.github/workflows/ci.yml)
шаблону.

| Job | Коли | Що перевіряє |
|---|---|---|
| `spec` | завжди | `openspec validate --all --strict` (структура специфікацій) і `spec:check`: AC ID у кожному сценарії, їх унікальність, слова з denylist |
| `app` | завжди | `lint` (0 попереджень), `next typegen` + `tsc`, тести Vitest, `build` |
| `conformance` | завжди | `ac:coverage`: кожен AC спеки має рядок у матриці `docs/conformance.md`, а кожне «реалізовано» підтверджене тестом, назва якого починається з AC ID |
| `db-check` | завжди, без секретів | піднімає одноразову базу прямо в раннері GitHub (там є Docker, тож на ваших ноутбуках він не потрібен) і застосовує всі міграції й сид. На PR ще й перевіряє, що нова міграція новіша за останню на `main` |
| `db-deploy` | push у `main` (після merge) або вручну | в environment `production` виконує `supabase db push --db-url`, спершу з `--dry-run` для журналу. Прогони йдуть по одному. Без `--include-all`, щоб порушений порядок міграцій падав голосно. Якщо секрету немає, крок пропускається з повідомленням |

**Обов'язкові для merge** (їх вимагає ruleset): `spec`, `app`, `conformance`, `db-check`. Vercel обов'язковою
перевіркою не робимо: якщо Hobby заблокує деплой, merge застряг би.

`conformance` падає з такими кодами:

- `NO-ROW` — AC є в спеці, а рядка в матриці немає (типово PM заархівував зміну без рядків нових AC);
- `MISSING` — статус «реалізовано», а тесту з цим AC ID немає;
- `ORPHAN` — тест посилається на AC, якого немає в спеці на `main`;
- `BAD-STATUS` — статус не «реалізовано» і не «відкладено (причина)»;
- `WRONG-REF` — шляху з колонок «Код» чи «Тест» не існує або тест лежить в іншому файлі.

Формат рядків матриці (приклад із шаблону):

```text
| AC-LEAVE-02 | заявка на дві посади дає два записи main і additional | `src/app/requests/actions.ts` (createRequest) | `tests/requests.test.ts` | реалізовано |
| AC-LEAVE-04 | заблоковані дні не рахуються | — | — | відкладено (чекаємо відповідь PM на Q2, #5) |
```

**Межі перевірки.** `ac:coverage` бачить, що тест з AC ID існує й не пропущений. Чи перевіряє він справді цей AC,
скрипт не знає. Тест без жодного `expect` Vitest шаблону вважає проваленим, але тест із формальною перевіркою
«покриє» AC. Тому рев'ю колеги потрібне. AC ID ставимо саме в назву тесту (`it("AC-LEAVE-01: …")`), бо така назва
працює і з `vitest -t`, і з `playwright --grep`.

**Типи бази без доступу до бази.** `db-check` кладе згенерований зі схеми вашого PR файл `database.types.ts` у
Summary свого прогону (Actions → прогін CI → Summary). Скопіюйте його у свій PR як `src/lib/supabase/database.types.ts`.

### Міграції: шлях через PR і відновлення (слайди 30–32)

Міграція — це SQL-файл у `supabase/migrations/` з міткою часу в назві (`<14 цифр>_<назва>.sql`). Supabase CLI
застосовує міграції в порядку цих міток. База в команди одна, тож схема змінюється тільки так
([walkthrough-dev](walkthrough-dev.md), крок 6.1):

```bash
npx supabase migration new <назва>
# SQL: enable row level security; revoke all … from anon, authenticated; явні grant;
#      політика на кожну операцію
```

Далі файл іде в PR → `db-check` (усі міграції й сид на одноразовій базі плюс порядок відносно `main`) → рев'ю
власника з CODEOWNERS (техлід або PM) → merge → `db-deploy` застосовує міграцію до спільної бази. Локально без Docker
міграцію не запустити, її перевіряє `db-check`. Застосовані міграції не редагуємо: будь-яка зміна — новим файлом.

**Чому ніколи `supabase db push` з ноутбука і DDL у SQL Editor.** Ваша невлита міграція стане в базі версією, якої
немає в `main`, а правка в SQL Editor — зміною схеми без міграції. Після цього кожен наступний `db-deploy` падатиме в
усієї команди, доки PM не полагодить історію міграцій. Перевірити, чи міграція працює, — завдання `db-check` у PR.

Скрипт `scripts/check-migration-order.mjs` у `db-check` ловить такі проблеми:

| Код | Що сталося | Що робити |
|---|---|---|
| `OLDER` | колега злив свою міграцію раніше, і ваша мітка тепер ≤ найновішої на `main` | у своїй гілці виконайте `git pull origin main`, потім команду `git mv` з логу `db-check` (файл отримує нову мітку, SQL не змінюється) → commit → push. Після цього потрібен новий approve власника з CODEOWNERS |
| `NAME`, `DUPLICATE` | назва не за форматом або дві міграції з однаковою міткою | створюйте файли лише командою `npx supabase migration new <назва>` |
| `CHANGED`, `DELETED` | уже застосовану міграцію змінено чи видалено | поверніть файл (`git checkout origin/main -- supabase/migrations/<файл>`), а зміну оформіть новою міграцією |

**Відновлення через `RENAMED`** (це попередження `db-check` про перейменовану міграцію, а не розділ дельти OpenSpec). Перевірки не вимагають, щоб гілка була «up to date», тому два PR з міграціями
можуть пройти паралельно й злитися у зворотному порядку. Тоді `db-deploy` на `main` падає з «Found local migration
files to be inserted before the last migration on remote database». Виправлення робимо окремим PR:

1. `git mv` файлу зі старшою (ранішою) міткою, ще **не застосованого** (звірте з журналом `db-deploy`), на нову мітку без зміни SQL.
2. `db-check` покаже попередження `RENAMED`, а не FAIL.
3. Рев'ю власника з CODEOWNERS → merge → `db-deploy` застосує міграцію.

`--include-all` не використовуйте ніколи. Якщо перейменований файл уже був застосований, `db-deploy` після merge
впаде з «Remote migration versions not found», тому рев'юер звіряє журнал `db-deploy`. Таку саму помилку дає
міграція, застосована в обхід `main` (наприклад, `db push` з ноутбука). Полагодити її може лише PM (README шаблону,
розділ «Міграції в прод», абзац «Збої й відновлення»). Скасований (cancelled) `db-deploy` після кількох merge поспіль — не проблема: наступний
прогін застосує всі міграції з `main`.

### Демо 3: як виглядає репо команди (слайди 33–34)

**Навіщо в роботі.** Це перша година командного проєкту. Перший зелений PR із preview — момент, коли проєкт
«оживає» і PM може дивитися результат без розробника. Демо-репо
[`koldovsky/2026-quitcode-06-leave-portal-demo`](https://github.com/koldovsky/2026-quitcode-06-leave-portal-demo)
на занятті грало роль «репо команди» `leave-portal`: один репозиторій, у якому і спека PM, і код.

**Частина 1 — налаштування й база (слайд 33).** У Settings налаштування лише відкрили, нічого не змінюючи: кожне
з них ваш PM зробить сам за `docs/bootstrap.md`.

- **Collaborators.** У вашій команді тут будуть усі розробники з прийнятими інвайтами.
- **Rules → ruleset на `main`** з обов'язковими `spec`, `app`, `conformance`, `db-check` і порожнім bypass. У демо автор
  сам грав усі ролі, тому ruleset демо обходиться без обов'язкового approve і Code Owners. **У команді — 1 approve і
  CODEOWNERS.**
- **`.github/CODEOWNERS`.** У команді: `@<pm> @<techlead>` на `/product/`, `/openspec/` і `/.github/`;
  `@<techlead> @<pm>` на `/supabase/migrations/`.
- **Environments → `production`.** Видно лише назву секрету `SUPABASE_DB_URL` і гілку `main`, значення не видно
  ніколи. Якщо в списку є `Production` з великої літери, його створив Vercel. GitHub не розрізняє регістр у назвах, тож
  це те саме середовище, що в `ci.yml`: налаштуйте його, а нового не створюйте.
- **Actions → CI → job `db-deploy`** на `main`. Крок «Dry run (list of migrations to apply)» показує, що буде
  застосовано, а крок «Apply migrations» застосовує. Якщо база актуальна, застосовувати нічого. Якщо секрету ще немає,
  job зелений, але кроки пропущено з повідомленням «Секрет SUPABASE_DB_URL в environment production не задано —
  міграції не застосовано (db push пропущено).» До кроку 4 walkthrough-pm так і має бути.
- **Supabase Dashboard → Database → Migrations** (точну назву розділу перевірте в інтерфейсі) — список застосованих
  міграцій. У демо їх шість. У вашій команді нові рядки там з'являтимуться лише через CI.

Шлях розробника той самий, що в розділі «День 0» вище: клон, `npm ci`, `.env.local`, `npm run dev`. Після входу як
`admin@example.test` стартова сторінка шаблону показує email і роль із таблиці `profiles`. Ні пароль бази, ні Docker
не потрібні, лише URL і publishable key. Ключі в `.env.local` вставляйте з вимкненою демонстрацією екрана,
щоб значення не потрапили в кадр.

**Частина 2 — Vercel і перший PR з AC (слайд 34).** Vercel-проєкт один на команду, і створює його PM:

- Vercel → **Add New → Project** → репо команди; дві змінні `NEXT_PUBLIC_…` для Production і Preview.
- Settings → Deployment Protection → **Require Log In** — вимкнено.
- Supabase → Authentication → **URL Configuration**: Site URL = прод-URL; Redirect URLs — `http://localhost:3000/**`
  і `https://*-<slug>.vercel.app/**` (slug — остання частина адреси будь-якого preview). Без них вхід на preview
  перекидає на localhost.

Далі показали PR із першим AC: гілка, тест `it("AC-LEAVE-01: дата початку в минулому дозволена …")`, потім
`npm test`, `npm run ac:coverage` і `gh pr create`. У PR видно:

- зелені `spec`, `app`, `conformance`, `db-check` — ті самі чотири, яких вимагає ruleset. `db-deploy` у списку має
  статус skipped, і це нормально: він працює лише на `main`;
- рядок `ƒ Proxy (Middleware)` у лозі job `app`;
- рядок `AC-LEAVE-01` у `docs/conformance.md` зі статусом «реалізовано» і посиланням на тест;
- коментар бота Vercel із preview-посиланням, яке відкривається **без входу у Vercel**.

Що далі у вашій команді: approve колеги (і власника коду, якщо PR зачіпає `product/`, `openspec/`, `.github/` чи
міграції) → **Squash and merge** → прод-деплой Vercel. `Closes #N` в описі PR закриває issue задачі.

Порядок у команді не такий, як у демо. Ваш перший PR — рядок у `docs/team.md`. Тести з AC ID з'являються в PR-ах
задач лише **після тегу `spec-v0.1`**: тест з AC, якого ще немає в `openspec/specs/` на `main`, `conformance`
позначить як `ORPHAN`. PR задачі виглядає так ([walkthrough-dev](walkthrough-dev.md), крок 6):

```bash
git switch main
git pull
git switch -c task/<N>-<коротко>
# код + тест it("AC-<AREA>-<NN>: …"); рядок свого AC у docs/conformance.md → «реалізовано»
npm run lint
npm run typecheck
npm test
npm run build          # у виводі має бути ƒ Proxy (Middleware)
npm run ac:coverage
npm run spec:check
git add -A
git commit -m "AC-<AREA>-<NN>: <що зроблено>"
git push -u origin task/<N>-<коротко>
gh pr create --web     # тип «Реалізація задачі», Closes #<N>; окремим коментарем — @coderabbitai review
```

### Що з цього важливо (слайд 35)

1. **Старт — із шаблону**, а не з порожньої теки. Шари курсу, ворота й обхід пасток уже всередині, а README
   шаблону — рецепт, як зібрати його знову.
2. **У кожного секрету одне місце**: `.env.local`, Vercel або environment `production`. Пароль прод-бази є лише в
   CI, розробники його не знають.
3. **Правила тримає репо, а не дисципліна**: PR, 1 approve, CODEOWNERS, CI бачить кожен AC, а схема змінюється лише
   міграціями через PR.

**Завтра в роботі.** Перевірте на поточному клієнтському проєкті три речі. Чи можна злити PR без рев'ю? Чи знають
розробники пароль прод-бази? Чи йдуть міграції лише через CI?

## Блок 05 — Спека живе далі (слайди 36–39)

Перший зріз уже стоїть, і PR із першим AC зелений. Цей блок про те, що буває далі, коли вимоги змінюються посеред
тижня. Відповіді PM стають новою версією спеки, CI помічає, що реалізація відстала, нові AC перетворюються на
задачі, а розробник може запропонувати зміну спеки сам. Наприкінці блоку всі перевірки поділено на «ворота», які
блокують merge, і «порадників», які лише підказують. Терміни (AC, матриця відповідності, archive, ruleset,
CODEOWNERS) пояснено в розділі [Глосарій](#глосарій).

### Клієнт відповів у середу (слайд 36)

На слайді: «Клієнт відповів у середу. Код команди має це помітити.» Приклад: клієнт пише «заблоковані дні просто
не рахувати», і вимога змінилась посеред тижня. У звичайному проєкті про таку зміну дізнаються з чату, а дехто не
дізнається ніколи.

**Навіщо в роботі.** Вимоги клієнта змінюються завжди. Найдорожча тут не сама зміна, а розробник, який про неї не
знав і далі пише код за старим правилом. Тому в нашій моделі зміна спеки — не повідомлення в чаті, а подія в
репозиторії, яку неможливо пропустити. Уся ідея блоку в чотирьох пунктах:

- **Зміна спеки — це PR PM у тому самому репо команди** і нова версія з тегом (`spec-v0.2`, далі `spec-v0.3`…).
- **CI не дасть злити цей PR**, доки кожен новий AC не матиме рядка в матриці `docs/conformance.md`.
- **Команда перетворює нові й змінені AC на задачі**, тобто issues «Задача».
- **У зворотний бік теж іде PR.** Розробник, який бачить хибу в спеці, пропонує зміну PR-ом в `openspec/changes/<id>/`,
  а рішення ухвалює PM.

### Демо 4, бік PM: відповіді стають `spec-v0.2` (слайд 37)

**Що показали.** У демо-репозиторії порталу відсутностей PM відповів на п'ять питань розробників (Q1–Q5). Відповіді
записано в `product/decisions.md` у форматі «питання → відповідь → що змінилось у спеці → версія». Відповіді, які
змінюють поведінку, оформлено окремою OpenSpec-зміною `clarify-leave-rules`, а реліз позначено тегом `spec-v0.2`.

| Питання | Відповідь PM | Що змінилось у спеці |
|---|---|---|
| Q1 | «покриває обидві посади» означає, що в ці дати в людини є розклад за обома посадами; посади працівник позначає галочками | MODIFIED «Подання заявки», `AC-LEAVE-02` |
| Q2 | заявку із заблокованим днем приймаємо, а заблоковані дні не рахуємо в кількості днів відсутності; діапазон лише із заблокованих днів відхиляємо | MODIFIED «Заблоковані дні», `AC-LEAVE-04`; новий `AC-LEAVE-10` з кодом `ONLY_BLOCKED_DAYS` |
| Q3 | кожен запис іде менеджеру підрозділу своєї посади | MODIFIED «Маршрутизація», `AC-LEAVE-05` |
| Q4 | заміна необов'язкова, це лише текстове поле для інформації менеджеру | MODIFIED «Подання заявки», `AC-LEAVE-01` |
| Q5 | нова заявка не може перетинатися із заявкою на розгляді (`pending`) чи схваленою (`approved`) | ADDED нова вимога «Перетин заявок», `AC-LEAVE-11` з кодом `OVERLAPPING_REQUEST` |

Як читати цю таблицю:

- **MODIFIED** означає, що змінилась чинна вимога. AC ID лишаються ті самі (`AC-LEAVE-02` так і лишається
  `AC-LEAVE-02`), змінюється лише текст.
- **Новий AC** з'являється двома способами: як новий сценарій у зміненій вимозі (так `AC-LEAVE-10` з'явився в
  «Заблокованих днях») або як нова вимога в розділі `## ADDED Requirements` (так з'явився `AC-LEAVE-11`). Новий AC
  завжди отримує наступний номер, старі номери повторно не використовуємо.

Дві деталі зі слайда, на яких часто спотикаються:

1. **`npx openspec show <id> --diff` працює лише для активної зміни.** Команда показує пострічковий diff (рядки `-`
   і `+`) змінених вимог проти чинної спеки. Дивіться його **до** archive. Після archive команда відповість
   «Unknown item», і історію змін можна буде побачити лише в теці `openspec/changes/archive/<дата>-<id>/` або через
   `git log -p openspec/specs`.
2. **MODIFIED копіює блок вимоги повністю**, з усіма сценаріями, навіть тими, що не змінились. Якщо скопіювати лише
   частину, валідатор видасть помилку, а archive відмовиться зливати зміну, бо інакше сценарії загубились би.
   Типові помилки зі змінами описано в [spec-guide](spec-guide.md).

Що таке archive: команда `npx openspec archive <id> -y` вливає дельту зміни в чинну спеку `openspec/specs/` і переносить
теку зміни в `openspec/changes/archive/`. Після цього нова версія спеки — це просто вміст `openspec/specs/`.

**Як це зробити у вашому репо (PM).** Повний порядок описано у
[walkthrough-pm, крок 14](walkthrough-pm.md#14-цикл-уточнень-і-spec-v02-152-год-за-дні-24--трек-c). Коротко:

1. Відповідайте на кожне issue «Питання до специфікації» протягом доби і записуйте рішення в `product/decisions.md`.
2. Якщо відповідь змінює поведінку, створіть гілку `spec/clarify-<зріз>` і нову зміну. `openspec new change` створює
   лише теку зміни, а `proposal.md` з усіма розділами й дельту `specs/<capability>/spec.md` пишете ви або агент.
3. Перевірте diff і структуру, запустіть скіл `spec-review`, потім коміт, push і PR типу «Зміна специфікації» з
   розділом `## spec-review`. Рецензент — техлід.
4. **У тій самій гілці, до approve:** archive, запис `## spec-v0.2` у `product/CHANGELOG.md` (що MODIFIED, що ADDED, на
   які питання відповідає) і рядки матриці для нових AC (про них ідеться в розділі про слайд 38 нижче).
5. CI зелений → техлід схвалює **після вашого останнього push** → merge → тег на `main`, а не на гілці.
6. Закрийте issues з посиланням на зміну й напишіть команді: «`spec-v0.2`: нові AC — …, змінені — …».

```bash
# крок 2: гілка й зміна
git switch main
git pull
git switch -c spec/clarify-<зріз>
npx openspec new change clarify-<зріз>   # або /opsx:propose у Claude Code (/opsx-propose у Cursor)
# крок 3: перевірки перед PR
npx openspec show clarify-<зріз> --diff
npx openspec validate clarify-<зріз> --strict
npm run spec:check
# крок 3, далі: коміт, push і PR (тип «Зміна специфікації», розділ ## spec-review)
git add openspec product
git commit -m "Propose clarify-<зріз>"
git push -u origin spec/clarify-<зріз>
gh pr create --web
# крок 4: у гілці PR, до approve
npx openspec archive clarify-<зріз> -y
npm run spec:validate
npm run ac:coverage                      # без рядків для нових AC буде NO-ROW
git add openspec product/CHANGELOG.md docs/conformance.md
git commit -m "Archive clarify-<зріз>, log spec-v0.2, add conformance rows"
git push
# крок 5: після merge — тег на main
git switch main
git pull
git tag spec-v0.2
git push origin spec-v0.2
```

Чому approve має бути саме після останнього push: ruleset вимагає approve останнього push. Approve, поставлений до
archive, уже не діє, і кожен новий коміт у гілці потребує нового approve. Термін для `spec-v0.2` — кінець дня 4
(розділ «Тиждень» у [README](../README.md)). На питання, що надійшли після тегу, відповідайте в issue й записуйте їх
у `decisions.md` зі статусом «наступна версія».

> Таблиця Q1–Q5 — це лише приклад формату з демо. Команда `leave-portal` пише власну спеку своїми словами:
> скопійовані з демо вимоги не зараховуються ([README](../README.md)).

Де подивитися: тег `spec-v0.2` (чинна спека після релізу), а `product/decisions.md` і `product/CHANGELOG.md` — на `main` у
[демо-репозиторії](https://github.com/koldovsky/2026-quitcode-06-leave-portal-demo). Копії виводу `show --diff`,
`CHANGELOG.md` і червоного `ac:coverage` лежать у [`examples/leave-portal/4-spec-v0.2/`](../examples/leave-portal/4-spec-v0.2/).

**Навіщо в роботі.** Так виглядає «клієнт передумав» у дисциплінованому проєкті. Відповідь записано, зміну поведінки
видно як diff, реліз має ім'я. І все це відбувається в тому самому репо, де команда пише код, тож у рев'ю PR техлід
бачить, які AC змінились і які задачі з цього виростуть.

### Тег-виправлення `spec-vX.Y.Z` (слайд 37)

Що робити, якщо тег поставили не на той коміт (наприклад, до archive чи не на `main`) або в релізі знайшлась помилка?

- Тег `spec-vX.Y` після push **не переносимо й не видаляємо**.
- Виправляємо `main` через PR і випускаємо **тег-виправлення** `spec-vX.Y.Z`, наприклад `spec-v0.1.1`. Порядок релізу
  той самий.
- `spec-v0.2` лишається релізом «після питань». Третя цифра — лише для виправлень.

Приклад є в демо-репо: тег `spec-v0.2.1`. Поведінка в ньому не змінилась (оновлено лише коментарі-підказки в
`product/`), тому нових задач і рядків матриці цей тег не додає.

Перевірка тегу: відкрийте `https://github.com/<pm>/<team-slug>/tree/spec-v0.2/openspec/specs`. Там має бути оновлена
спека, а в `openspec/changes/` не має бути теки вашої зміни `clarify-<зріз>` (вона вже в `archive/`; активна зміна `impl-<зріз>` розробників там може лишатися). Тег можна створити й без термінала,
через Releases ([walkthrough-pm, крок 12](walkthrough-pm.md#12-реліз-spec-v01-з-рядками-матриці-30-хв--трек-b-до-кінця-дня-2));
точні назви кнопок перевірте в інтерфейсі.

**Навіщо в роботі.** Тег — це домовленість «ось за цією версією ми працюємо». Якщо тихо його перенести, у людей, які
вже завантажили старий тег, і в PR, що на нього посилаються, `spec-v0.1` означатиме різне. Перенесений чи видалений
тег знімає бали («Що знімає бали (PM)» у [README](../README.md)).

### Демо 4, бік команди: червоний `conformance` і задачі (слайд 38)

**Що показали.** Гілка PM після archive `clarify-leave-rules`, але ще без рядків для нових AC у матриці. Запуск
перевірки покриття дав таке:

```text
$ npm run ac:coverage
ac:coverage — AC у специфікаціях: 11, рядків у матриці: 9, «реалізовано»: 9, AC у назвах тестів: 9

NO-ROW: AC зі специфікації без рядка в docs/conformance.md (2):
  - AC-LEAVE-10 (openspec/specs/leave-requests/spec.md:44)
  - AC-LEAVE-11 (openspec/specs/leave-requests/spec.md:97)

FAIL: проблем — 2. Оновіть docs/conformance.md і тести.
```

Повний вивід лежить у [`examples/leave-portal/4-spec-v0.2/drift-ci.txt`](../examples/leave-portal/4-spec-v0.2/drift-ci.txt).

Це і є **дрейф**: спека пішла вперед (11 AC), а реалізація й матриця лишились позаду (9 рядків). У вашому репо цю
саму перевірку на кожному PR запускає job `conformance` у CI, і ruleset вимагає, щоб вона була зеленою. Тому PR PM
зі `spec-v0.2` **не зіллється**, доки кожен новий AC не матиме рядка. Дрейф ловиться ще до merge спеки, а не на demo day.

**Виправлення робиться в тому самому PR.** PM додає на кожен новий AC рядок зі статусом, записаним дослівно
`відкладено (новий AC — чекає задачі)`, а в колонках «Код» і «Тест» ставить `—`:

```markdown
| AC-LEAVE-10 | діапазон лише із заблокованих днів | — | — | відкладено (новий AC — чекає задачі) |
```

Далі все йде звичним порядком: `conformance` зелений → техлід схвалює → merge → тег `spec-v0.2`. Рядки змінених
(MODIFIED) AC PM не чіпає.

**Далі працює команда:**

1. Техлід разом із командою (або PM) заводить на нові AC issues за формою «Задача» (мітка `task`): AC ID, що зробити,
   Done when.
2. Розробник призначає задачу собі, створює гілку `task/<N>-<коротко>` і PR з рядком `Closes #<N>`.
3. У цьому PR є код, тест, назва якого починається з AC ID, і **оновлений рядок матриці**: шляхи в колонках «Код» і
   «Тест» і статус `реалізовано`.
4. Колега робить рев'ю → merge.

У демо-репо на `main` так уже зроблено. У рядку `AC-LEAVE-10` стоїть статус `реалізовано`, у колонці «Тест»
серед інших файлів є `tests/leave/calendar.test.ts`, а тест у ньому називається
`it("AC-LEAVE-10: заявка 05.11–05.11.2026 лише із заблокованих днів — ONLY_BLOCKED_DAYS", …)`. Коли обидва нові AC
реалізовано, `ac:coverage` пише `OK`: 11 AC, 11 «реалізовано». Покроково це описано у [walkthrough-dev](walkthrough-dev.md),
крок 6.2 «Код, тести, матриця».

Інші коди цієї перевірки (`MISSING`, `ORPHAN`, `BAD-STATUS`, `WRONG-REF`) пояснено в блоці 04, у розділі
«CI: один workflow, п'ять jobs».

**Чесно про межу скрипта.** Змінені `AC-LEAVE-01`, `-02`, `-04` і `-05` зберегли свої ID і свої рядки, тому скрипт їх
**не помітить**: він бачить, що рядок є, але не бачить, що змінився текст сценарію. Такі зміни ловлять люди:

- PM перелічує змінені AC в описі PR релізу.
- Техлід у рев'ю PR PM бачить diff спеки й разом із PM заводить задачі на змінену поведінку там, де код уже не
  відповідає спеці.
- Розробник, який уже реалізував AC, що став MODIFIED, звіряє свій код:

  ```bash
  git diff spec-v0.1 spec-v0.2 -- openspec/specs
  ```

  Якщо код не відповідає новій версії, потрібен новий PR із виправленням коду й тесту (тест, що перевіряв стару
  поведінку, теж оновлюють) або статус `відкладено (причина)` у рядку.

У демо таку звірку записали в журналі розробника, у таблиці «Перехід на spec-v0.2». Для `AC-LEAVE-01` довелося
додати поле заміни. Для `-02`, `-04` і `-05` код уже відповідав новій версії, бо команда раніше працювала за тими
самими робочими рішеннями, тож змінились щонайбільше тести
([журнал на `main` демо](https://github.com/koldovsky/2026-quitcode-06-leave-portal-demo/blob/main/docs/spec-reading/koldovsky.md)).

Часті питання:

- *Чому PM додає «відкладено», а не реалізує AC сам?* PM пише «що і навіщо», а «як» — це задачі розробників. Рядок
  `відкладено (новий AC — чекає задачі)` чесно каже, що AC уже є в спеці, а задача на нього ще попереду.
- *А якщо задача вже йде за старою поведінкою?* Техлід у рев'ю PR PM позначає змінені AC і відкриті задачі, яких це
  стосується. Розробник оновлює свій PR, або для цього заводять нову задачу.

Розробникам: [walkthrough-dev](walkthrough-dev.md), крок 6, абзац «PM випустив `spec-v0.2`».

**Навіщо в роботі.** Заради цього моменту й будувалась уся конструкція: зміна вимоги клієнта сама «стукає» в CI, а не
губиться в чаті. Нове правило не можна забути, бо без рядка в матриці реліз не зіллється, а задача на нього з'явиться
в тому самому репо.

### Зворотний шлях: розробник пропонує зміну спеки (слайд 38)

Бачите хибу в спеці: суперечність, неможливе правило, пропущений випадок? **Не латайте її мовчки в коді.** Після тихого
фіксу код і спека розходяться, PM і колеги про це не знають, а наступна людина чи агент, які працюють за спекою,
зроблять інакше.

Є три законні шляхи:

| Шлях | Коли | Як |
|---|---|---|
| Issue «Питання до специфікації» (мітка `spec-question`) | є питання або кілька можливих варіантів | спершу пошукайте наявні issues, бо дублікатів не створюємо; текст допоможе підготувати скіл `spec-clarify` |
| Коментар у PR PM | спека ще на рев'ю | коментар до рядка в PR зміни |
| PR лише в `openspec/changes/<id>/` | є готова пропозиція | `proposal.md` і дельта, тип PR «Зміна специфікації» |

Правила для PR-пропозиції:

- PR додає **лише** `openspec/changes/<id>/`. `openspec/specs/` і `product/` розробник не чіпає: такі зміни в PR
  розробника знімають бали («Що знімає бали (розробник)» у [README](../README.md)).
- Рев'ю робить PM як власник коду (`/openspec/` у `CODEOWNERS`). Формально GitHub достатньо approve будь-кого з
  власників шляху (там PM і техлід), тож правило «спеку вирішує PM» — це **домовленість команди**: рішення й merge
  за PM.
- CI перевіряє такий PR так само, як PR PM. Гілка лежить у тому самому репо, тож job `spec` перевіряє і структуру
  спеки, і denylist.
- Після merge PM доводить зміну до релізу тим самим порядком: archive, запис у `CHANGELOG.md`, рядки для нових AC,
  новий тег. Задачі з'являються тим самим шляхом, що й для `spec-v0.2`.

Де в домашці: [walkthrough-dev](walkthrough-dev.md), крок 6, абзац «Знайшли помилку в спеці?».

**Навіщо в роботі.** Розробник часто першим бачить, що правило в спеці не працює. PR в `openspec/changes/` робить його
знахідку видимою для всіх і залишає рішення за тим, хто відповідає за вимоги перед клієнтом.

### Порадники й ворота (слайд 39)

**Робоча ситуація.** Команді дали `/opsx:verify`, і вона швидко починає вірити йому як тесту. Це помилка. Усі
перевірки, які ви бачили на занятті, діляться на два види.

**Ворота: детерміновані перевірки, блокують merge.** Той самий вхід завжди дає ту саму відповідь. Це jobs CI, які
ruleset вимагає бачити зеленими:

| Job CI | Що перевіряє |
|---|---|
| `spec` | `openspec validate --all --strict` перевіряє структуру спеки; `spec:check` перевіряє AC ID, їхню унікальність і denylist |
| `conformance` | `ac:coverage`: кожен AC має рядок у матриці, кожне `реалізовано` підтверджене тестом |
| `db-check` | усі міграції й сид застосовуються на одноразовій базі; у PR ще й: нова міграція новіша за ті, що вже є в `main`, а застосовані файли не змінено й не видалено |
| `app` | `lint` (0 попереджень), `typecheck`, тести `npm test` (мають пройти), `build` |

**Порадники: LLM, друга думка, merge не блокують:**

- `/opsx:verify` (у Cursor `/opsx-verify`) звіряє реалізацію зі зміною й видає знахідки рівнів CRITICAL, WARNING і
  SUGGESTION, але archive не блокує;
- `/conformance` перебудовує матрицю `docs/conformance.md`;
- скіли `spec-review` (PM перед релізом) і `spec-clarify` (розробник готує питання до спеки);
- `@coderabbitai review` запускає рев'ю PR від CodeRabbit.

Порадники знаходять корисне, зокрема те, чого скрипт не бачить, наприклад розбіжність змісту коду зі спекою. Але вони
можуть і пропустити баг.

**Чому так суворо.** LLM-рецензент поблажливий. Anthropic описувала експерименти, де агент-оцінювач хвалив посередню
роботу й умовляв себе пропустити справжні баги, які сам щойно знайшов. Тому правило просте: **merge блокують лише
детерміновані перевірки, а порадник дає підказку людині.** Кожну знахідку порадника перевіряє людина.

**Людські ворота.** Окремий рівень — ruleset на `main` (файл [`team-main.json`](../materials/rulesets/team-main.json)):

- потрібен 1 approve колеги (автор не може схвалити власний PR);
- якщо PR чіпає `product/`, `openspec/`, `.github/` чи `supabase/migrations/`, цей самий єдиний approve має дати хтось із власників шляху з
  `CODEOWNERS`;
- approve має стояти після останнього push;
- усі розмови в PR мають бути розв'язані (Resolve conversation);
- `spec`, `app`, `conformance` і `db-check` мають бути зелені;
- `main` не можна видалити чи переписати force-push. Список обходу (bypass) порожній, тож через PR іде й сам PM.

**Хто тримає ці ворота.** Сам файл `team-main.json` нічого не робить, це лише опис правил. PM створює ruleset із цього файлу (завантажує його як `ruleset.json` й імпортує через
`gh api repos/<pm>/<team-slug>/rulesets --method POST --input ruleset.json`; у JSON уже стоїть `"enforcement": "active"`) у
репо команди в день 0 ([walkthrough-pm, крок 8](walkthrough-pm.md#8-ruleset-на-main-і-докази-налаштування-15-хв--трек-a);
подробиці — у розділі [«Як працює ruleset»](#як-працює-ruleset) блоку 04). Відтоді правила виконує сам GitHub: кнопка
merge заблокована, доки не виконано всі умови, а прямий push у `main` GitHub відхиляє. Якщо GitHub усе ж дасть власнику
злити свій PR без approve, не користуйтеся цим і напишіть у чат курсу: рубрика A перевіряє approve колеги на кожному PR
у `main`. Обов'язкові перевірки прив'язані до назв
jobs у `ci.yml`, тому ці jobs не перейменовують і не видаляють.

Що з цього випливає на практиці:

- Коментар CodeRabbit до рядка коду відкриває розмову в PR, а невирішені розмови блокують merge. Тож на кожен такий коментар
  або внесіть виправлення, або дайте відповідь, чому ні, і натисніть Resolve.
- CodeRabbit не замінює approve колеги.
- Один із двох варіантів бонусу E розробника якраз про це: `/opsx:verify` плюс власний розбір. Для кожної знахідки вирішіть, чи це справжня
  проблема, хибна тривога чи питання смаку, і чому ([walkthrough-dev](walkthrough-dev.md), «Бонус E»).

*Навіщо тоді взагалі `/opsx:verify`, якщо йому не можна вірити?* Він знаходить те, чого не бачить скрипт. Але знахідку
перевіряє людина, а merge тримають детерміновані перевірки.

**Навіщо в роботі.** Агентів і LLM-рецензентів у команді ставатиме більше, і з ними легко звикнути до думки «AI
перевірив, отже, все добре». Чіткий поділ на ворота й порадників не дає зручному інструменту непомітно стати єдиною
перевіркою якості.

### Що з цього важливо (слайд 39)

- Спека версіонується PR-ами в тому самому репо, де код. Реліз позначає тег `spec-vX.Y`, виправлення — `spec-vX.Y.Z`.
- Дрейф ловить CI ще до merge спеки: новий AC без рядка в матриці дає червоний `conformance`.
- Нові AC стають задачами через рядок `відкладено (новий AC — чекає задачі)`. Змінені AC ловить людина в рев'ю за
  diff спеки.
- LLM-перевірки допомагають людині, а merge блокують лише детерміновані перевірки й approve людей.
- Зміна спеки з боку розробника — теж PR, в `openspec/changes/`, і рішення за PM.

**Завтра в роботі.** Коли клієнт змінює вимогу, спершу запишіть рядок у `decisions.md` і випустіть нову версію спеки,
а вже потім пишіть код. Знайшли хибу в спеці — відкрийте PR в `openspec/changes/` на рев'ю PM, а не робіть тихий фікс
у коді.

## Домашка й тиждень (слайди 40–44)

> **Одна ідея закриття:** домашка — це і є «що зробити в роботі завтра». Тиждень після заняття ви проживаєте як
> перший спринт клієнтського проєкту: PM налаштовує команду й пише спеку, розробники ставлять питання, ділять зріз на
> задачі й зливають їх PR-ами з рев'ю колег. Рубрику опубліковано наперед — у [README](../README.md) домашки.
> Незнайомі терміни шукайте в розділі [Глосарій](#глосарій).

Кожен трек дає **100 балів + 5 бонусних**. **Рубрика** (таблиця балів) оцінює якість, а **Definition of Done** (DoD,
мінімальний список «зроблено») — це залік або незалік. Техлід проходить трек розробника.

### Трек PM — 100 + 5 балів (слайд 40)

На слайді п'ять карток. Нижче — те саме, але з критеріями з [README](../README.md#трек-pm--100--5-балів):

| | Завдання | Що зробити | Балів |
|---|---|---|---|
| **A** | Репо команди й продукт | репо з шаблону (публічне, collaborators, мітки `spec-question` і `task`, CODEOWNERS, ruleset), Supabase (організація, роль Developer для розробників, Auth), environment `production` із `SUPABASE_DB_URL`, Vercel (дві змінні, Require Log In вимкнено), зелений CI; `product/`: vision, глосарій, ролі з матрицею прав, roadmap, `denylist.txt` | **25** |
| **B** | Перший зріз | зміна `add-<зріз>`: `proposal.md` + дельта з вимогами EARS (`SHALL`) і сценаріями `AC-<AREA>-<NN>`; `validate --strict` зелений; розділ `## spec-review` у PR; approve техліда; рядки матриці; тег `spec-v0.1` | **40** |
| **C** | Цикл уточнень | відповіді на issues `spec-question`; `product/decisions.md` (питання → відповідь → що змінилось); MODIFIED / ADDED → тег `spec-v0.2` з рядками матриці для нових AC; `product/CHANGELOG.md` | **25** |
| **D** | Нотатка PM | щонайменше 3 місця, де команда прочитала спеку по-різному (за issues, рев'ю й PR-ами), — у файлі здачі | **10** |
| **E** | Бонус (одне з двох) | друга OpenSpec-зміна (наступний зріз) **або** порівняння з `/speckit-clarify` (Spec Kit) на одній вимозі | **+5** |

**На що дивляться в кожному завданні (коротко):**

- **A.** `.github/CODEOWNERS` має чотири рядки зі справжніми логінами: `/product/`, `/openspec/`, `/.github/` — PM і
  техлід, `/supabase/migrations/` — техлід і PM. Докази налаштування — у `docs/bootstrap.md`, **без жодного значення**
  ключів. `db-deploy` зелений: один раз вручну з `include_seed`, коли секрет уже задано. `vision.md` — одна сторінка
  з 2–4 вимірними ознаками успіху. `glossary.md` — 8–15 термінів із колонкою «Не вживаємо». `roles.md` — ваші ролі
  замість `member`/`admin` шаблону і матриця роль × сутність × дія без порожніх клітинок. `roadmap.md` — WS6 і зріз на
  кожне заняття WS7–WS11. У `openspec/config.yaml` заповнено рядок `Продукт:`. Усе — через PR з approve техліда.
- **B.** Найбільша вага, бо від цього залежить уся команда. `proposal.md` має розділи в такому порядку: Why, What
  Changes, Capabilities, Users & roles, Non-goals, Assumptions, Open questions. Дельта містить 3–5 вимог і 6–10 AC.
  Кожна вимога — одне речення EARS із `SHALL`/`MUST`. Кожен сценарій має заголовок `#### Scenario: AC-<AREA>-<NN> …`,
  один критерій, конкретні числа й дати, без кліків по UI і без назв таблиць чи API. На кожну вимогу є негативний
  шлях. Зміну заархівовано в гілці до merge, approve техліда стоїть після останнього push, тег — на коміті `main`.
- **C.** На кожне issue, відкрите до тегу `spec-v0.2`, є відповідь PM. Дубль закривають коментарем «Дубль #N —
  відповідь там». Зміна `clarify-…`: у MODIFIED — повний блок вимоги з незмінними AC ID, нові правила — з новими AC ID.
- **D.** Кожна розбіжність має чотири частини: AC і цитата → два прочитання з посиланнями (логіни, не імена) → яке
  слово в спеці це дозволило → що зробив PM. Це заготовка для demo day.

**Два правила зі слайда.** Справжні назви клієнта зберігайте лише в локальному `product/denylist.local.txt` (він не
потрапляє в git) і в секреті `SPEC_DENYLIST`. Репо публічне, тому в `product/denylist.txt` — лише нейтральні
внутрішні слова (кодові назви, заглушки з чужих шаблонів на кшталт Contoso). Перед першим комітом перевірте
`git status --short --ignored product`: `denylist.local.txt` має бути лише в рядку з `!!` (git його ігнорує), і
жодного рядка з `??` ([walkthrough-pm](walkthrough-pm.md), крок 2). Мітки `spec-question` і `task` створіть у день 0
(`gh label create`), бо без них форми issues не поставлять мітку.

**Як вмикається ruleset** (набір правил злиття для `main`). Файл [`team-main.json`](../materials/rulesets/team-main.json)
сам нічого не захищає: це опис правил. PM застосовує його до репо команди в день 0, останнім кроком налаштування
([walkthrough-pm](walkthrough-pm.md), крок 8): спершу завантажує цей JSON у локальний файл
(`curl -sLo ruleset.json https://raw.githubusercontent.com/koldovsky/2026-quitcode-06-specs-in-practice-hw/main/materials/rulesets/team-main.json`;
у PowerShell — `curl.exe`), потім виконує `gh api repos/<pm>/<team-slug>/rulesets --method POST --input ruleset.json`
або Settings → Rules → Rulesets (точні назви полів перевірте в інтерфейсі). Робіть це лише після того, як CI хоча б
раз прозвітував `spec`, `app`, `conformance` і `db-check`, інакше GitHub не прийме їх як обов'язкові перевірки. Далі
правила виконує сам GitHub: ruleset діє одразу (`"enforcement": "active"`) і не має винятків (bypass). Push і force
push напряму в `main` відхиляються. Merge заблоковано, доки немає approve колеги, зелених перевірок і розв'язаних
розмов. Якщо PR чіпає `/product/`, `/openspec/`, `/.github/` чи `/supabase/migrations/`, потрібен approve саме
власника коду з CODEOWNERS. Approve має стояти після останнього push: кожен новий коміт у гілку (зокрема Update
branch) вимагає нового approve. На GitHub Free це працює лише в публічному репо. Перевірка — ваш перший PR під
ruleset-ом, `onboarding/<pm>` (свій рядок у `docs/team.md` і докази налаштування в `docs/bootstrap.md`): без approve
merge має бути заблоковано. Якщо GitHub таки дає вам, власнику, злити свій PR без
approve, не користуйтеся цим і напишіть у чат курсу: рубрика A перевіряє approve колеги на кожному PR у `main`.
Послаблений ruleset знімає бали за A.

**Що знімає і що не знімає бали.** Якщо команда питає мало, завдання C оцінюють за відповідями на те, що надійшло, і за вашими
Open questions. Якщо розбіжностей менше трьох, бракуючий пункт D — ваш AC із двома можливими прочитаннями й поміткою
«прогноз». Команда `leave-portal` бере зразок [`examples/leave-portal/`](../examples/leave-portal/) лише як формат. За
скопійований зміст — 0 за відповідне завдання. Повний список того, що знімає бали, —
[README](../README.md#що-знімає-бали-pm).

**Навіщо в роботі.** Кожне завдання — ситуація на старті клієнтського проєкту. До першого рядка коду команда має
отримати репо, базу й деплой із правилами, а агент — контекст продукту. Розробникам потрібна спека, яку перевіряє
машина. Відповідь, яку ви дали в чаті, забудеться, а відповідь, записана в спеці, дійде до коду. **Що робити:**
[walkthrough-pm](walkthrough-pm.md), кроки 1–16.

### Трек розробника — 100 + 5 балів (слайд 41)

Онбординг не залежить від спеки, тож починайте в день 0. Реалізація спільна, а оцінка особиста: рахують PR-и, рев'ю й
issues, автор яких — ви. Критерії взято з [README](../README.md#трек-розробника--100--5-балів):

| | Завдання | Що зробити | Балів |
|---|---|---|---|
| **A** | Онбординг | прийняти інвайти GitHub і Supabase; запустити застосунок локально проти бази команди під синтетичним користувачем; перший PR — свій рядок у `docs/team.md` з рев'ю колеги й merge | **20** |
| **B** | Читання спеки й питання | скіл `spec-clarify` + власне око → щонайменше 3 питання (власні issues `spec-question` або коментар із новим варіантом у наявному issue, без дублікатів; щонайменше 1 — власне issue); журнал `docs/spec-reading/<login>.md` | **20** |
| **C** | Реалізація | щонайменше 2 злиті PR-и задач із тестами за AC ID і рядками `docs/conformance.md`, зелений CI; міграції — лише через PR; зріз працює на прод-URL | **40** |
| **D** | Code review | щонайменше 2 змістовні рев'ю PR-ів колег: коментарі до рядків, запит змін або обґрунтований approve | **20** |
| **E** | Бонус (одне з двох) | бутстрап без шаблону (агентом з нуля) і порівняння з шаблоном **або** `/opsx:verify` + власний розбір знахідок | **+5** |

**Деталі, яких немає на слайді:**

- **A.** В описі PR додайте знімок екрана локального `npm run dev` після входу синтетичним користувачем (без паролів
  у кадрі) і окремий коментар `@coderabbitai review`. Конфлікт у таблиці `docs/team.md` розв'язуйте так, щоб не
  загубити чужих рядків.
- **B.** Issue створюйте через форму «Питання до специфікації»: варіанти поведінки (не реалізації), рекомендований
  варіант, вплив. У журналі мають бути: скан за 11 категоріями таксономії, таблиця питань із посиланнями `#N`,
  «Власні припущення», а також що знайшли ви, а що скіл.
- **C.** Кожен PR закриває свою задачу (`Closes #N`) і має approve колеги. Задача — один AC або одна область одного AC
  (міграція й RLS, дія, UI). Назва тесту поведінки починається з AC ID. Тест лежить у `*.test.ts(x)` у `src/` чи
  `tests/` і має хоча б один `expect`. Статус у матриці пишіть дослівно: `реалізовано` або `відкладено (причина)`.
  Сесію ведіть у `src/proxy.ts`, авторизацію перевіряйте через `getClaims()`, ключі використовуйте publishable /
  secret. В останньому PR задачі додайте запис екрана на 1–2 хв: ваша задача на прод-URL. Один PR дає щонайбільше
  половину балів C. Рядок `відкладено` без посилання на відкрите питання до PM (`<pm>/<team-slug>#N`) чи на рішення
  PM у proposal, що AC поза зрізом, вважається нереалізованим. Якщо `spec-v0.1` вийшов пізніше кінця дня 3 (тоді його випускає викладач) або задач-issues `task` на команду менше, ніж по дві на розробника, для повного C достатньо одного злитого PR задачі.
- **D.** Рев'ю подавайте через Review changes. Підходить Request changes або Comment щонайменше з одним коментарем до
  рядка, або Approve з одним-двома реченнями про те, що ви перевірили. «LGTM» без змісту не рахується. На зауваження
  до своїх PR відповідайте й розв'язуйте розмови. Рев'ю техліда на PR-и PM зі спекою теж рахуються.

**Правила спільної роботи зі слайда.** Без approve колеги PR не зливаємо. Чужу роботу за свою не видаємо: не
переносимо код із чужого відкритого PR, не забираємо задачу без домовленості, не пушимо в чужу гілку без згоди
автора. Працювати в парі можна, але тоді в описі PR вказують обидва логіни, а PR-и задач у кожного свої.
Інфраструктуру тестів із шаблону чи демо-репо (наприклад, `tests/db/supabase-pglite.ts` з демо) брати можна, з
посиланням на джерело в PR. Чужий код у вашому PR без посилання на джерело — 0 за C, а approve без рев'ю («LGTM» на
PR, якого ви не відкривали) не зараховується в D ([README](../README.md#своя-робота-в-спільному-репозиторії)). Спеку в
своїх PR не правимо: пропозицію оформлюємо як issue, коментар у PR PM або PR лише в `openspec/changes/<id>/`.
**Ключі й паролі в репо (зокрема в історії git) — 0 за трек A і обов'язкова ротація ключів.**

**Навіщо в роботі.** Перший день на клієнтському проєкті виглядає саме так: репо й база вже є, і за годину ви
запускаєте застосунок і зливаєте перший PR за правилами команди. Питання до коду дешевші за питання після демо. Від
вашого рев'ю залежить, чи потрапить у `main` чуже прочитання спеки. **Що робити:**
[walkthrough-dev](walkthrough-dev.md), кроки 1–8.

крок 3а). Хто не може прийти, пише свою діру в чат команди до кінця дня 1. Якщо зібратися не вдається, ту саму
розмову проводять асинхронно в чаті.

Ціль для `spec-v0.1` — кінець дня 2. Якщо наприкінці дня 3 (16.10) тегу немає, викладач (він collaborator у репо
команди) доводить відкритий PR PM до релізу з approve техліда й ставить тег сам. PM утрачає бали за терміни B,
розробники не втрачають нічого. Час тегу — момент, коли тег з'явився в GitHub, а не дата коміту. Тег `spec-vX.Y`
після push не переносимо й не видаляємо. Помилку виправляє тег-виправлення `spec-vX.Y.Z`, наприклад `spec-v0.1.1`.

**Скільки часу:** PM — 9–11 год за тиждень, розробник — 8,5–10,5 год (без бонусу), техлід — ще ~1 год. **Навіщо в
роботі:** це ритм реального спринту. Розробники не чекають спеку, бо онбординг від неї не залежить.

### Definition of Done (слайд 42)

На слайді — мінімум. Повний список — у [README](../README.md); він же стоїть чекбоксами в шаблоні опису PR здачі.

- **Усім:** CI зелений на `main` команди; жодних значень секретів і назв клієнтів, дані — `*@example.test`; файл
  здачі й PR `WS6: Ім'я Прізвище` із заповненим полем «Ім'я та Прізвище».
- **PM:** усе налаштування з завдання A (зокрема ruleset за `team-main.json` і зелений `db-deploy`) з доказами в
  `docs/bootstrap.md`; заповнений `product/` (vision, glossary, roles, roadmap, decisions, CHANGELOG); тег
  `spec-v0.1` і, якщо відповіді змінили поведінку, `spec-v0.2`; у PR кожної зміни — `## spec-review`, approve
  техліда й рядки матриці; нотатка PM у файлі здачі.
- **Розробник:** свій рядок у `docs/team.md`; журнал у `main` і щонайменше 3 питання; щонайменше 2 злиті PR-и задач;
  щонайменше 2 змістовні рев'ю; зріз на прод-URL і запис екрана в останньому PR задачі.

**Як перевіряють.** Перевірка статична, за **SHA** — ідентифікатором коміту. Конвеєр читає репо команди на коміті
`main`, який ви вказали, разом із тегами, PR-ами, рев'ю, issues, прогонами CI і публічними налаштуваннями (ruleset).
Внесок рахують за логіном автора PR, рев'ю чи issue, а не за автором комітів у `main`. Якщо PM злив ваш PR
merge-комітом, ви балів не втрачаєте.

### Як здати (слайд 42)

Здає кожен окремо: PM, техлід і кожен розробник. Здача — PR у **цей** репо домашки з одним новим файлом
`submissions/<team-slug>/<github-login>.md` за [шаблоном](../submissions/_template.md). Заголовок PR —
`WS6: Ім'я Прізвище`. Покроково — у [submissions/README.md](../submissions/README.md).

```bash
gh repo fork koldovsky/2026-quitcode-06-specs-in-practice-hw --clone
cd 2026-quitcode-06-specs-in-practice-hw
git switch -c ws06/<github-login>
cp submissions/_template.md submissions/<team-slug>/<github-login>.md   # заповніть усі поля
git add submissions/<team-slug>/<github-login>.md
git commit -m "WS6 submission: <team-slug>/<github-login>"
git push -u origin ws06/<github-login>
gh pr create --repo koldovsky/2026-quitcode-06-specs-in-practice-hw --web
```

- **Fork** (власна копія чужого репо) — єдиний на курсі, і лише для здачі: права запису в репо домашки у вас немає. До
  роботи команди fork не має стосунку.
- У файлі: роль, команда, логін, репо команди, SHA, версія спеки, прод-URL і посилання на ваші PR-и, рев'ю, issues і
  коментарі. PM додає ще PR-и спеки, теги й задачі. Те, що не стосується вашої ролі, позначте рівно «—».
- **SHA** — повні 40 символів, коміт запушений, це `main` команди на момент здачі: `git fetch origin`, потім
  `git rev-parse origin/main`.
- Ім'я та прізвище пишіть **лише в описі PR** (за ним виписують сертифікат), у файл — ні: репо публічний. Не
  додавайте `--fill`: з ним шаблон опису PR не підставиться.
- CodeRabbit тут сам не стартує: напишіть окремим коментарем `@coderabbitai review`. Він перевіряє лише файл здачі.

### Карта курсу: що вже складено (слайд 43)

Після шести занять у кожної команди є продукт, спека, репо, база, деплой і **ворота** — автоматичні й людські
перевірки перед merge. Кожне заняття додало свій шар:

| Заняття | Шар | Що дає |
|---|---|---|
| WS3 | правила | як у нас заведено |
| WS4 | скіли | знання команди |
| WS5 | MCP | доступ із мінімальними правами |
| WS6 | спека | що саме будуємо і як це перевірити |
| WS7–WS11 | далі | шар за шаром, зріз за зрізом — у той самий проєкт |

За планом далі так: **WS7** — Fullstack з AI (UI, API, база, auth і RLS наступних зрізів; ADR і архітектурні правила
в CI). **WS8–WS9** — якість і рев'ю в PR, конвеєр «спека → PR», спільні скіли й шаблони між проєктами. **WS10–WS12** —
AI-функції в продукті, DevOps і demo day. Теми ще уточнюються, але принцип незмінний: кожне заняття — новий шар у ваш
командний проєкт. Тому `roadmap.md` PM і містить зріз на кожне заняття WS7–WS11.

> Правила кажуть, **як**; скіли — **як саме в нас**; MCP — **до чого**; спека — **що**, і CI перевіряє, що зроблено
> саме це.

### Дякую — і що робимо одразу після заняття (слайд 44)

Наступне заняття — **WS7: Fullstack з AI**. На нього приходьте із зеленим CI на `main` команди. PM приходить із тегом
`spec-v0.2`, розробники — зі злитими PR-ами задач. З цього почнеться наступний зріз.

**Одразу після заняття:**

  Developer, і кидає посилання в чат команди. Подальші кроки — за [walkthrough-pm](walkthrough-pm.md) і
  `docs/bootstrap.md` шаблону.
- **Розробники** того ж дня (день 0) приймають обидва інвайти. Техлід приймає першим: поки інвайт не прийнято, GitHub ігнорує
  його логін у CODEOWNERS, і PR PM зі спекою не буде кому схвалити.

### Supabase без Docker: міграції через PR (слайд 46)

**Міграція** — SQL-файл із міткою часу в `supabase/migrations/`, який змінює схему бази. Головне правило: схему
змінюють **лише міграції в git і лише через PR**. Docker на ноутбуці не потрібен, бо міграцію перевіряє CI. Повний цикл:

```bash
git switch -c task/<N>-<name>
npx supabase migration new <name>      # файл із міткою часу
# пишете SQL: RLS, GRANT, політики
git add supabase/migrations
git commit -m "<що змінює міграція>"
git push -u origin task/<N>-<name>
gh pr create --web
```

1. **`db-check`** у CI піднімає одноразову базу, проганяє **всі** міграції й сид і перевіряє, що ваша мітка часу
   новіша за останню на `main`. Згенеровані типи бази він кладе в Summary прогону: файл
   `src/lib/supabase/database.types.ts` оновлюйте з нього у своєму PR.
2. **Рев'ю** міграції дає техлід або PM — це власники `/supabase/migrations/` у CODEOWNERS. Після рев'ю — merge.
3. **`db-deploy`** після merge застосовує міграцію до спільної бази (`supabase db push --db-url` в environment
   `production`).

**Чого не робимо ніколи:** `supabase db push` з ноутбука і DDL (команди зміни схеми) у SQL Editor Dashboard. База
спільна. Інакше в ній з'явиться версія, якої немає в `main`, і кожен наступний `db-deploy` падатиме всій команді.

**Кожна міграція з таблицею** — за офіційною процедурою Supabase, як стартова міграція шаблону
`supabase/migrations/20261012000000_profiles_and_roles.sql`:

- `enable row level security`. **RLS** — правила доступу до рядків у самій базі.
- `revoke` і явні `GRANT` лише на потрібні операції. Нові проєкти Supabase більше не видають права автоматично.
- Окрема політика на кожну операцію, `to authenticated`, з `(select auth.uid())`. У такій формі Postgres обчислює
  значення раз на запит, а не на кожен рядок.
- Хелпери ролей лежать у схемі `private`, з `security definer` і `search_path = ''`.
- Колонкові `grant update (…)`, щоб працівник не зміг підвищити собі роль.

**Одна міграція — одна зміна.** Застосовану міграцію не редагуємо, лише додаємо новий файл. Буває, що колега злив
новішу міграцію раніше за вас. Тоді `db-check` червоний (`OLDER`) і друкує готову команду `git mv` зі свіжою міткою.
У своїй гілці виконайте `git pull origin main`, потім цю команду (SQL не змінюється), закомітьте, запуште й попросіть
новий approve. `--include-all` не використовуємо ніколи. `migration repair` виконує лише PM (README шаблону, розділ
«Міграції в прод», абзац «Збої й відновлення»). Агенту в `.claude/settings.json` шаблону заборонено будь-який `supabase db push`, `db reset`
проти віддаленої бази, `migration down --linked` і `migration repair`. Ця заборона діє лише в Claude Code.

**Свої ролі замість `member`/`admin`** додаються окремою новою міграцією, і порядок кроків важливий:

```sql
alter table public.profiles drop constraint profiles_role_check;                         -- 1) зняти старе правило
update public.profiles set role = 'employee' where role = 'member';                      -- 2) перевести наявні рядки
alter table public.profiles alter column role set default 'employee';                    -- 3) новий default
alter table public.profiles
  add constraint profiles_role_check check (role in ('employee', 'manager', 'admin'));   -- 4) нове правило
```

Старе правило знімаємо першим, бо воно не пропустить UPDATE на нову роль (помилка 23514). Рядки з `'member'` уже є
після `npm run users:demo` у день 0. Дані й default виправляємо до нового правила, інакше створення користувача впаде
на типовому `'member'`. Ролі тут узято з демо, у вас вони — з `product/roles.md`. Після `db-deploy` техлід оновлює
`supabase/demo-users.json` (PR) і запускає `npm run users:demo`.

**Free-план Supabase.** На всі організації, де ви Owner або Administrator, дозволено 2 активні проєкти. Роль
Developer слота не займає. Після ~7 днів без активності проєкт засинає. Відновити його може лише Owner, тобто PM:
перед заняттям, перед здачею й перед demo day — Restore project (точну назву кнопки перевірте в інтерфейсі). Чи
проходить `db push --db-url` на вашому Free-проєкті, PM перевіряє першим ручним запуском `db-deploy` у день 0.
Запасний шлях описано в [README шаблону](https://github.com/koldovsky/2026-quitcode-06-project-template), розділ
«Міграції в прод».

**Навіщо в роботі.** Помилка в правах на базу коштує найдорожче. До того ж саме базу агент найохочіше «швидко
поправить у дашборді». Міграція через PR дає три речі: рев'ю людини, перевірку на чистій базі й одну історію схеми
для всієї команди. **Що робити:** [walkthrough-dev](walkthrough-dev.md), крок 6.1.

## Глосарій

Терміни йдуть за алфавітом: спершу латиниця, потім кирилиця. У дужках — слайди, де термін пояснюється.

- **AC** (acceptance criterion, критерій приймання) — умова, за якою людина без доступу до коду однозначно скаже «пройдено» чи «ні». В OpenSpec кожен AC — окремий сценарій `#### Scenario:` з кроками **WHEN / THEN / AND** (слайди 13, 18).
- **AC ID** — ідентифікатор AC у форматі `AC-<AREA>-<NN>`, наприклад `AC-LEAVE-02` (AREA — 2–12 великих латинських літер, NN — дві цифри). Стоїть на початку назви сценарію, у задачі, у назві тесту й у рядку матриці. Не змінюється й повторно не використовується (слайди 3, 13).
- **archive** — `npx openspec archive <id> -y`: зливає дельту зміни в чинну спеку `openspec/specs/` і переносить теку зміни в `openspec/changes/archive/<дата>-<id>/`. Робиться в гілці PR, до merge (слайди 9, 17).
- **branch** (гілка) — окрема лінія комітів. У команді: `spec/<id>` — зміна спеки PM, `task/<N>-<коротко>` — задача, `onboarding/<логін>` — онбординг, `product/context` — продуктовий контекст. У `main` усе потрапляє лише через PR.
- **CI** — workflow GitHub Actions `.github/workflows/ci.yml` шаблону з п'ятьма jobs: `spec`, `app`, `conformance`, `db-check`, `db-deploy` (слайд 32). Перші чотири обов'язкові для merge. Назви jobs не змінюють: на них тримається ruleset.
- **CODEOWNERS** — файл `.github/CODEOWNERS` із власниками шляхів: `/product/`, `/openspec/`, `/.github/` — PM і техлід, `/supabase/migrations/` — техлід і PM. PR, що чіпає такий шлях, потребує approve одного з його власників (слайд 28).
- **collaborator** — учасник особистого репо PM із правом запису (Write). Інвайт треба прийняти: без цього ви не запушите гілку, не схвалите PR і не потрапите в CODEOWNERS.
- **conformance** — матриця відповідності `docs/conformance.md` (рядок на кожен AC: що перевіряє, код, тест, статус) і однойменний job CI, що запускає `npm run ac:coverage`. Статус — дослівно `реалізовано` або `відкладено (причина)`. Крім `NO-ROW` і `ORPHAN`, скрипт дає `MISSING` («реалізовано» без тесту з AC ID), `BAD-STATUS` (недозволений статус) і `WRONG-REF` (шлях у колонках «Код» чи «Тест» не існує або тест лежить в іншому файлі) (слайди 32, 38).
- **db-check** — job CI без секретів: застосовує всі міграції й сид до одноразової бази в раннері GitHub (тому Docker на ноутбуці не потрібен), а в PR ще перевіряє порядок міграцій відносно `main`. Згенеровані типи бази кладе в Summary прогону.
- **db-deploy** — job CI лише на `main` (після merge або вручну через Run workflow): в environment `production` виконує `supabase db push --db-url` і застосовує нові міграції до спільної бази. Сид застосовують один раз, вручну, з `include_seed`.
- **delta** (дельта) — файл `openspec/changes/<id>/specs/<capability>/spec.md`, що каже, що зміна робить зі спекою: `## ADDED`, `## MODIFIED`, `## REMOVED` або `## RENAMED Requirements`. У `MODIFIED` копіюють повний блок вимоги з усіма сценаріями (слайди 9, 37).
- **denylist** — список слів, яких не має бути в публічному репо. У `product/denylist.txt` — лише нейтральні внутрішні слова; справжні назви клієнта — у локальному `product/denylist.local.txt` (не в git) і в секреті репо `SPEC_DENYLIST`. `spec:check` ловить ці слова в спеці, документації, коді, сидах і тестах, але значень не друкує (слайди 17, 31).
- **Developer** (роль у Supabase) — роль, з якою PM запрошує розробників в організацію Supabase. Вона бачить URL і ключі проєкту й керує тестовими користувачами, але не змінює налаштувань і, на відміну від Administrator, не займає безкоштовного слота.
- **Done when** — рядок, яким закінчується кожна задача в `tasks.md`: AC ID, які задача закриває (`Done when: AC-LEAVE-03.`). Агент знає, що перевірити, а рев'юер — що приймати (слайд 24).
- **EARS** (Easy Approach to Requirements Syntax) — шаблони речення вимоги: `WHEN …` (подія), `IF … THEN …` (небажана ситуація), `WHILE …` (стан), `WHERE …` (опція) або без умови, а далі `the system SHALL …`. Одна вимога — одне речення (слайд 13).
- **environment `production`** — середовище в GitHub (Settings → Environments), доступне лише гілці `main`. Його секрет `SUPABASE_DB_URL` (рядок Session pooler із паролем бази) отримує тільки job `db-deploy` (слайд 31).
- **impl-<зріз>** — OpenSpec-зміна команди, яку веде техлід із розробниками: `design.md` (як) і `tasks.md` (задачі з рядком `Done when: AC-…`), з `skip_specs: true`. Спеку PM вона не змінює (слайд 24).
- **issue** — запис у вкладці Issues репо команди. Є дві форми: «Питання до специфікації» з міткою `spec-question` і «Задача» з міткою `task`. Мітки PM створює в день 0, бо інакше форма їх не поставить.
- **NO-ROW** — помилка `ac:coverage`: AC є в спеці, а рядка в `docs/conformance.md` немає. Це дрейф: спека пішла вперед, а матриця ні. Виправляється рядком `відкладено (новий AC — чекає задачі)` у тому самому PR (слайд 38).
- **Non-goals** — розділ `proposal.md`: те, що могло б бути метою зрізу, але свідомо виключене, разом із причиною. Це не заперечення на кшталт «система не падає» (слайди 12, 15).
- **OLDER** — помилка `db-check` у PR: мітка часу вашої міграції не новіша за останню на `main`, бо колега злив свою раніше. Виправляється перейменуванням файлу на нову мітку; команду друкує скрипт.
- **OpenSpec** — CLI і формат специфікацій (`@fission-ai/openspec`, версія 1.14.1). `openspec/specs/` — чинна поведінка, `openspec/changes/<id>/` — зміни. Команди агента: `/opsx:propose`, `explore`, `apply`, `verify`, `sync`, `archive` (у Cursor — `/opsx-propose` тощо) (слайд 9).
- **ORPHAN** — помилка `ac:coverage`: тест посилається на AC, якого ще немає в `openspec/specs/` на `main`. Тому тести з AC ID пишуть після того, як PR PM зі спекою злито.
- **PR** (pull request) — запит злити гілку в `main` через рев'ю. У команді для merge потрібні approve колеги після останнього push, approve власника коду для шляхів із CODEOWNERS, розв'язані розмови й зелені перевірки. Автор свій PR не схвалює.
- **preview** — окремий деплой Vercel для кожного PR, посилання на який бот Vercel пише в коментарі. Працює з тією самою базою, що й прод, і відкривається без входу у Vercel, якщо PM вимкнув Require Log In.
- **proposal.md** — файл зміни PM з розділами в такому порядку: Why, What Changes, Capabilities, Users & roles, Non-goals, Assumptions, Open questions. Open questions — це нумеровані питання Q1, Q2…, на які PM ще не має відповіді (слайд 12).
- **publishable key** — ключ `sb_publishable_…` (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`). Він безпечний у браузері, бо доступ до даних тримає RLS. Разом із `NEXT_PUBLIC_SUPABASE_URL` лежить у `.env.local` кожного й у Vercel. Назва `ANON_KEY` застаріла.
- **RLS** (Row Level Security) — політики Postgres у Supabase, що вирішують, які рядки користувач бачить і змінює. Кожна клітинка матриці прав стає політикою RLS на операцію, а кожна таблиця має RLS і явні `GRANT` (слайди 14, 46).
- **ruleset** — правила GitHub для `main` репо команди, описані у файлі [`team-main.json`](../materials/rulesets/team-main.json): лише PR, 1 approve, Code Owners, approve останнього push, розв'язані розмови, обов'язкові `spec`, `app`, `conformance`, `db-check`, без bypass. Сам файл нічого не вмикає: PM створює з нього ruleset у репо команди в день 0 ([walkthrough-pm](walkthrough-pm.md), крок 8), а далі правила виконує сам GitHub. Докладно — у розділі [«Як працює ruleset»](#як-працює-ruleset) блоку 04 і в «Частих питаннях» нижче (слайди 28–29).
- **SDD** (spec-driven development) — розробка на основі специфікацій. Ми працюємо на рівні **spec-anchored**: спека живе в репо поруч із кодом і змінюється в тому самому PR, що й поведінка, а CI перевіряє, що вони не розійшлися (слайд 8).
- **secret key** — ключ `sb_secret_…` (`SUPABASE_SECRET_KEY`), що обходить RLS. Зберігається лише в `.env.local` PM або техліда для `npm run users:demo`. У Vercel і з префіксом `NEXT_PUBLIC_` — ніколи.
- **SHALL** — англійське ключове слово вимоги (можна й `MUST`). Прозу пишемо українською, але «ПОВИННА» замість `SHALL` валить `openspec validate --strict`.
- **skip_specs** — рядок `skip_specs: true` у `.openspec.yaml` зміни `impl-<зріз>`. Дозволяє зміну без дельти; без нього буде помилка «at least one delta». Ключ із помилкою (`skip_spec`) мовчки ігнорується.
- **spec-clarify** — скіл розробника в шаблоні. Проходить 11 категорій таксономії неоднозначностей, ставить до 5 питань по одному, з варіантами й рекомендацією, готує тексти issues і веде журнал `docs/spec-reading/<логін>.md`. `product/` і `openspec/specs/` не змінює (слайд 22).
- **spec-review** — скіл PM. Перевіряє зміну перед релізом за таксономією й чеклістом якості AC і видає таблицю знахідок; правки вносить лише після вашого «так». Результат іде в розділ `## spec-review` опису PR (слайд 17).
- **spec-vX.Y** (тег) — git-тег релізу спеки на `main`: `spec-v0.1`, `spec-v0.2`. Після push його не переносимо й не видаляємо; помилку виправляє тег `spec-vX.Y.Z`, наприклад `spec-v0.1.1`.
- **spec:check** — `npm run spec:check`. Перевіряє AC ID на початку кожного сценарію, унікальність ID (зокрема `DUPLICATE-CHANGE`: активна зміна дасть дубль після archive), розділи `proposal.md` і denylist. Значень із denylist не друкує.
- **validate --strict** — `openspec validate --all --strict` (`npm run spec:validate`). Перевіряє структуру спеки: `SHALL`, рівно `####` у сценаріях, хоча б один сценарій, повний `MODIFIED`. Код виходу 0 або 1. Зміст не перевіряє: «SHALL швидко завантажувати» пройде (слайди 9, 17).
- **ворота й порадники** — ворота: детерміновані перевірки, що блокують merge (`validate`, `spec:check`, `ac:coverage`, `db-check`, тести, `lint`, `typecheck`, `build`), плюс людський approve. Порадники: LLM-перевірки (`/opsx:verify`, `/conformance`, `spec-review`, `spec-clarify`, `@coderabbitai review`). Вони дають другу думку й merge не блокують (слайд 39).
- **дрейф** — розходження спеки й реалізації: спека пішла вперед, а матриця відповідності й код лишились позаду. Новий AC без рядка в `docs/conformance.md` CI ловить як `NO-ROW` ще до merge спеки (слайд 38).
- **зріз** — вертикальний шматок продукту (UI + дія + дані + тест), який можна показати користувачу. Одна OpenSpec-зміна — один зріз і один намір. Орієнтир на тиждень — 3–5 вимог і 6–10 AC (слайд 15).
- **міграція** — SQL-файл у `supabase/migrations/`, створений командою `npx supabase migration new <назва>`. Це єдиний спосіб змінити схему спільної бази: PR → `db-check` → рев'ю власника з CODEOWNERS → merge → `db-deploy` (слайди 30, 46).
- **робоче припущення** — рішення, яке розробник записує в журнал `docs/spec-reading/<логін>.md`, поки PM не відповів, і переробляє, якщо відповідь буде іншою. Де розумного типового варіанта немає, не робимо нічого й чекаємо (слайд 23).
- **сид** (seed) — стартові дані бази з `supabase/seed.sql` шаблону. `db-check` застосовує їх до одноразової бази в кожному прогоні, а в спільну базу їх один раз кладе `db-deploy` з `include_seed`; пізніші довідкові дані додають новою міграцією.
- **техлід** — один із розробників, якого обирає команда. Він співвласник спеки в CODEOWNERS, схвалює PR-и PM зі спекою, веде з командою `impl-<зріз>`, рецензує міграції й запускає `npm run users:demo`. Проходить трек розробника.

## Часті питання

### Репозиторій команди, ruleset і рев'ю

**Як вмикається ruleset із `team-main.json` і що змушує його виконуватися?**
Файл [`materials/rulesets/team-main.json`](../materials/rulesets/team-main.json) сам нічого не вмикає. Це лише опис правил у форматі GitHub API, і лежить він у репо домашки. Діяти правила починають, коли PM створює з цього файлу ruleset у **своєму** репо команди. Це останній крок дня 0: [walkthrough-pm](walkthrough-pm.md), крок 8, і [`docs/bootstrap.md`](https://github.com/koldovsky/2026-quitcode-06-project-template/blob/main/docs/bootstrap.md) шаблону, розділ 6.

```bash
curl -sLo ruleset.json https://raw.githubusercontent.com/koldovsky/2026-quitcode-06-specs-in-practice-hw/main/materials/rulesets/team-main.json
gh api repos/<pm>/<team-slug>/rulesets --method POST --input ruleset.json
rm ruleset.json
```

Те саме можна зробити в браузері: Settings → Rules → Rulesets → New ruleset, а далі імпортувати файл або заповнити ті самі поля вручну (точну назву кнопки перевірте в інтерфейсі).

Після цього правила виконує сам GitHub на своєму боці, а не дисципліна команди. `"enforcement": "active"` вмикає їх, умова `"ref_name": { "include": ["~DEFAULT_BRANCH"] }` застосовує їх до гілки за замовчуванням (`main`), а порожній `"bypass_actors": []` означає, що винятків не дано нікому, зокрема власнику репо. GitHub відхиляє прямий push, force push і видалення `main`. Злити PR він не дасть, доки не буде всього такого:

- approve колеги, даний після останнього push;
- approve власника коду, якщо PR чіпає шляхи з CODEOWNERS;
- розв'язані розмови;
- зелені `spec`, `app`, `conformance` і `db-check`.

Ці чотири перевірки прив'язані в JSON до GitHub Actions (`integration_id`): їхній результат звітують однойменні jobs із `.github/workflows/ci.yml`. Тому перейменовувати jobs не можна.

Щоб усе спрацювало, потрібні чотири умови:

- репо **публічне**: на GitHub Free ruleset і CODEOWNERS діють лише в публічних репо;
- ruleset створено **після** зеленого CI на `main` і в PR `setup/codeowners`: GitHub приймає прив'язку перевірки до Actions, лише коли Actions уже звітували її в цьому репо. Якщо бачите помилку про `integration_id`, дочекайтеся зеленого прогону CI й повторіть команду;
- у Settings → General → Pull Requests увімкнено merge commits і squash merging: метод, вимкнений там, не запрацює й з ruleset-ом;
- у CODEOWNERS стоять логіни людей, які прийняли інвайт.

Перевірка: на своєму PR кнопка merge має бути заблокована, доки немає approve. Якщо GitHub таки дає вам, власнику, злити свій PR без approve, не користуйтеся цим і напишіть у чат курсу. Рубрика A перевіряє approve колеги на кожному PR у `main`, а конвеєр оцінювання читає й публічні налаштування ruleset-у.

Два налаштування послаблені свідомо. Approve не знімається, коли в `main` зливають інший PR: інакше кожен merge знімав би approve з усіх відкритих PR. І гілка не мусить бути «up to date», тож не треба оновлювати її після кожного чужого merge (слайди 17, 28–29).

**Чому один репозиторій на команду, а не кожен у своєму?**
Так працює агенція: одна система, одна база, один деплой, PR-и з рев'ю колег. Розбіжні прочитання спеки проявляються в питаннях, у рев'ю й у PR-ах, що не стикуються. Так їх видно, поки їх ще дешево виправити, а не на demo day, і саме їх PM збирає в нотатку (трек D). Ролі розводять CODEOWNERS і ruleset. Форків у роботі команди немає. Єдиний fork на курсі — fork репо домашки, з якого йде PR здачі ([submissions/README](../submissions/README.md)) (слайд 3).

**Хто схвалює PR PM зі спекою? І чи гарантує CODEOWNERS, що спеку вирішує PM?**
PR PM схвалює техлід. GitHub не дає автору схвалити власний PR, тому на кожному шляху в CODEOWNERS стоять двоє: PM і техлід. Проте GitHub достатньо approve будь-кого з власників шляху. Отже, «спеку вирішує PM» — це домовленість команди, а не технічний замок. Техлід перевіряє форму, зрозумілість і те, які задачі виростуть зі зміни, а вимоги не переписує. Інвайт техлід приймає першим: логін без доступу GitHub у CODEOWNERS ігнорує, і тоді PR PM нікому буде схвалити (слайди 28, 30).

**Чому репо публічне й лежить в особистому акаунті PM, а не в організації?**
Імпортувати особисте репо у Vercel Hobby може лише його власник, а про організації на Hobby документація Vercel суперечить сама собі. Ruleset, CODEOWNERS і секрети environment на GitHub Free діють лише в публічних репо. А коміти колег, запушені, поки репо було приватним, Vercel Hobby блокує й після відкриття. Тому репо публічне з першої хвилини, без варіанту «спершу приватне, потім відкрию». У цього рішення є ціна: в особистому репо немає teams і ролі Maintain. Усі розробники — рівноправні collaborators, а налаштування доступні лише PM. Справжні назви клієнта зберігаються тільки в локальному `product/denylist.local.txt` (не в git) і в секреті `SPEC_DENYLIST` (слайди 28, 30).

**Коли оновлювати свою гілку і що робити, якщо двом потрібен той самий файл?**
Задачі ріжемо вертикально, щоб перетинів було мало. Гілку оновлюйте (Update branch або `git merge origin/main`) лише тоді, коли GitHub показує конфлікт. Будь-який новий push знімає силу попереднього approve, і потрібне повторне рев'ю. До того ж той, хто оновив гілку, уже не зможе її схвалити. Конфлікт у спільній таблиці (`docs/team.md`, `docs/conformance.md`) розв'язуйте так: лишіть обидві зміни й попросіть approve ще раз (слайд 24).

### Спека й OpenSpec

**Чому OpenSpec, а не Spec Kit, Kiro чи BMAD? І чи це не водоспад?**
Спека PM змінюється вже за тиждень, поки команда пише код у тому самому репо, і кожна зміна йде окремим PR. OpenSpec має дельти (ADDED, MODIFIED, REMOVED, RENAMED), детермінований archive у гілці PR, валідатор із кодом виходу для CI і встановлюється через npm. У Spec Kit механізму дельт немає, тож від нього ми беремо протокол уточнень, таксономію неоднозначностей і розділи Non-goals, Assumptions, Open questions. BMAD важкий, а Kiro прив'язаний до IDE, і від нього беремо тільки нотацію EARS. Водоспадом це не є: спека пишеться на один зріз, живе в репо, змінюється в тому самому PR, що й поведінка, і версіонується тегами. Такий підхід називається spec-anchored (слайди 8–9).

**Навіщо ставити OpenSpec глобально і саме версії 1.14.1?**
Команди `/opsx:*` і скіли агента викликають просто `openspec`, а теки `node_modules/.bin` у PATH агента немає. Тому ставимо `npm i -g @fission-ai/openspec@1.14.1`, і `openspec --version` має показати `1.14.1`. З іншою версією команди поводитимуться інакше, ніж на занятті. Телеметрію вимикає `openspec config set telemetry.enabled false`. Node беремо 24 LTS, бо Node 20 уже EOL (слайд 5).

**Чи писати в спеці назви таблиць, API або кроки в інтерфейсі?**
Ні. `openspec/config.yaml` забороняє в спеці таблиці, API, компоненти й бібліотеки: це рішення розробника в `design.md`. Сценарій описує бізнес-результат («створено одну заявку зі статусом `pending`»), а не кліки, тож переживе переробку інтерфейсу. Якщо вимога природно займає два речення, це дві вимоги. Відмова з кодом помилки — завжди окрема вимога `IF … THEN`. Орієнтир для першого зрізу — 3–5 вимог і 6–10 AC (слайди 12, 13, 18; [spec-guide](spec-guide.md)).

**Чому відповіді PM не записують прямо в спеку і чому issue створює людина, а не агент?**
Спека належить PM. Відповідь спершу з'являється в issue, потім у `product/decisions.md`, а якщо вона змінює поведінку — у новій версії спеки. Так вона доходить до всієї команди й до задач. Скіл `spec-clarify` лише готує текст. Issue ви створюєте самі у вебформі `https://github.com/<pm>/<team-slug>/issues/new/choose` → «Питання до специфікації». Це правило безпеки з WS2 і WS5: агент не пише в GitHub від вашого імені без вашого прямого прохання й підтвердження (так у скілі `spec-clarify` і `AGENTS.md` шаблону). Перед новим питанням перегляньте наявні (`gh issue list --label spec-question --state all`). Якщо таке питання вже є, напишіть коментар із новим варіантом чи впливом, а не дубль. Для треку B розробника потрібно щонайменше 3 питання, з них хоча б одне — власне issue (слайди 22–23).

**PM поставив тег не на той коміт. Його можна переставити?**
Ні: тег `spec-vX.Y` після push не переносимо й не видаляємо. Виправте `main` через PR і випустіть тег-виправлення `spec-vX.Y.Z` (наприклад, `spec-v0.1.1`) у тому самому порядку релізу. Тег можна поставити й без терміналу, через Releases → Draft a new release з `main` як ціллю (точну назву кнопки перевірте в інтерфейсі; [walkthrough-pm](walkthrough-pm.md), крок 12).

**Вийшов `spec-v0.2`. Що з ним робить команда і чому PM пише «відкладено», а не реалізує сам?**
У PR релізу PM додає на кожен новий AC рядок `відкладено (новий AC — чекає задачі)`. Інакше `conformance` червоний (`NO-ROW`), і PR не злити. PM пише «що й навіщо», а «як» — це задачі розробників. Техлід із командою заводить на нові AC issues «Задача», і PR задачі переводить рядок у статус `реалізовано` разом із тестом. Змінені (`MODIFIED`) AC мають той самий ID і той самий рядок, тому скрипт їх не помітить. Їх знаходять люди. PM перелічує змінені AC в описі PR, і техлід бачить їх у рев'ю. Після релізу PM із техлідом дивляться `git diff spec-v0.1 spec-v0.2 -- openspec/specs` і заводять задачі там, де код уже не відповідає спеці. Якщо ви вже реалізували такий AC, звірте свій код тим самим diff (слайд 38; [walkthrough-dev](walkthrough-dev.md), крок 6.3).

**Я знайшов хибу в спеці. Можна виправити її у своєму PR?**
Ні: `product/` і `openspec/specs/` веде PM. Поставте питання в issue `spec-question` або в коментарі до PR PM. Готову пропозицію можна оформити PR-ом, що додає лише `openspec/changes/<id>/` (тип «Зміна специфікації»). Його рецензує PM як власник коду, і рішення про merge ухвалює PM (слайди 36, 38).

### База, секрети, Vercel

**Чому розробникам не дають пароль бази і чому не можна просто зробити `supabase db push` своєї міграції для перевірки?**
База одна на всю команду. Ваша ще не злита міграція стала б у базі версією, якої немає в `main`, і зламала б `db-deploy` усій команді. Міграцію перевіряє `db-check` у вашому PR на одноразовій базі, а застосовує `db-deploy` після merge. Пароль зберігається лише в `SUPABASE_DB_URL` в environment `production`, доступному тільки `main`. Звичайний секрет репо міг би надрукувати workflow з будь-якої гілки. Розробнику вистачає URL і publishable key, а типи бази лежать у Summary прогону `db-check`. Роль Developer технічно бачить SQL Editor, тож «жодного DDL у SQL Editor» — правило команди, а не замок (слайди 29–31).

**Колега злив міграцію раніше за мене, і в мене червоний `db-check` (`OLDER`). Що робити?**
Ваша міграція тепер не новіша за останню на `main`. Оновіть свою гілку з `main` (`git pull origin main`) і виконайте команду `git mv`, яку `db-check` друкує в лозі: вона перейменовує файл на нову мітку, SQL при цьому не змінюється. Потім закомітьте, запуште й попросіть новий approve; для міграції — у власника з CODEOWNERS. `db push --include-all` не використовуємо ніколи, а `migration repair` робить лише PM ([walkthrough-dev](walkthrough-dev.md), крок 6.1; слайд 46).

**Чому вимкнено реєстрацію і як тоді створити тестового користувача?**
Publishable-ключ є в JS-бандлі прод-URL, тож з увімкненою реєстрацією будь-хто зміг би зареєструватися сам. Тому PM вимикає «Allow new users to sign up» у налаштуваннях Authentication. «Confirm email» теж вимкнено: вбудована пошта Supabase надсилає лише 2 листи на годину й лише членам організації (точне місце перемикачів перевірте в інтерфейсі). Рядок `[auth] enable_signup = false` у `supabase/config.toml` у хмару не переноситься. Синтетичних `admin@example.test`, `member1@example.test` і `member2@example.test` створює `npm run users:demo` через Admin API. Йому потрібен `SUPABASE_SECRET_KEY`, тому запускає його PM або техлід. Свого тестового користувача `*@example.test` розробник може додати двома способами:

- у Supabase → Authentication → Users → Add user з автопідтвердженням (точні назви полів перевірте в інтерфейсі);
- записом `*@example.test` у `supabase/demo-users.json` через PR «Онбординг»: після merge PM або техлід запускає `npm run users:demo`.

(слайди 29–30)

**Vercel не зробив preview для мого PR або preview просить увійти. Що робити?**
Перший PR кожного (рядок у `docs/team.md`) заодно перевіряє Vercel. Якщо Vercel пише «blocked» і згадує автора коміту, рев'ю роблять локально (`gh pr checkout <N>` → `npm run dev`). У прод такий PR PM зливає merge-комітом («Create a merge commit») або створює деплой вручну в Dashboard Vercel (точну назву кнопки перевірте в інтерфейсі). Vercel не входить в обов'язкові перевірки ruleset-у, тож merge це не блокує. Якщо preview просить увійти у Vercel, PM не вимкнув Require Log In. Якщо вхід у застосунок на preview перекидає на localhost, у Supabase бракує Redirect URL `https://*-<slug>.vercel.app/**` ([walkthrough-dev](walkthrough-dev.md), крок 3; слайди 29, 34).

**Проєкт Supabase «заснув» або в мене вже два проєкти. Що робити?**
Безкоштовний проєкт засинає приблизно після 7 днів без активності. Відновити його може лише Owner, тобто PM, кнопкою Restore project у Dashboard (точну назву кнопки перевірте в інтерфейсі). Робіть це перед заняттям, перед здачею й перед demo day. Ліміт Free — 2 активні проєкти на всі організації, де ви Owner або Administrator. Це стосується лише PM: проєкти з WS5 поставте на паузу або видаліть. Розробник із роллю Developer слота не займає (слайди 5, 30, 46).

### Перевірки, інструменти й домашка

**CodeRabbit і `/opsx:verify` знаходять баги. Чому вони не блокують merge? І чому CodeRabbit не прийшов у мій PR?**
Це порадники на базі LLM, а LLM-рецензент поблажливий: в експериментах Anthropic агент-оцінювач умовляв себе пропустити справжні баги. Merge блокують лише детерміновані перевірки й людський approve, а знахідку порадника перевіряє людина. Публічні репо з менш ніж 10 зірками CodeRabbit автоматично не рецензує. Після створення PR напишіть окремим коментарем `@coderabbitai review`. Кількість рев'ю на годину обмежена, тож просіть його після групи виправлень (слайд 39).

**PM запізнюється зі спекою. Що робити розробникам?**
Онбординг від спеки не залежить, тож починайте в день 0. Відкритий PR спеки PM можна читати й коментувати ще до релізу. Якщо наприкінці дня 3 `spec-v0.1` немає, викладач як collaborator доводить відкритий PR PM до релізу з approve техліда й сам ставить тег. PM втрачає бали за терміни в B, розробники не втрачають нічого. Якщо `spec-v0.1` вийшов пізніше кінця дня 3 або задач-issues `task` на команду менше, ніж по дві на розробника, для повного C розробнику достатньо одного злитого PR задачі ([README](../README.md#що-знімає-бали-pm)).

**Ми працюємо в Cursor або на Windows. Що інакше?**
Файли `.mcp.json` (Supabase MCP лише на читання) і `.claude/settings.json` (заборона агенту читати `.env*` і запускати `supabase db push`) читає лише Claude Code. Cursor бере MCP з `.cursor/mcp.json`, а заборону відкривати `.env*` агентом там тримає лише ваша дисципліна. Скіли з `.claude/skills/` Cursor читає, а команди в ньому пишуться як `/opsx-propose` тощо. На Windows команди walkthrough-ів розраховані на Git Bash. У PowerShell 5.1 немає `&&`, тож виконуйте команди по черзі. На помилку «running scripts is disabled» пишіть `npx.cmd`, `npm.cmd`, `openspec.cmd`, а замість `curl` — `curl.exe` (слайд 28).
