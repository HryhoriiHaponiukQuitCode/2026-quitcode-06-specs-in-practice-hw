Позначення:

- `<я>` — ваш GitHub-логін, `<pm>` — логін PM;
- `<team-slug>` — слаг команди: `property-workflows`, `therapy-scheduling`, `school-purchasing` або `leave-portal`;

Команди — для Git Bash на Windows і терміналу macOS. Де PowerShell відрізняється, це сказано окремо. У Windows
PowerShell 5.1 немає `&&`: виконуйте команди по черзі. Якщо PowerShell відповідає «running scripts is disabled on
this system», пишіть `npx.cmd`, `npm.cmd`, `openspec.cmd` замість `npx`, `npm`, `openspec`.

## Як це влаштовано

```text
 PM:  <pm>/<team-slug>-spec   (шаблон вимог, публічне; PM працює лише у вебінтерфейсі GitHub)
      issue «Продукт» + issues «Вимога» (мітки product, requirement)
        — або — docs/product.md + docs/requirements/*.md (вибір PM записано в README його репо)
      issues «Питання до вимог» (мітка question) — тут питаєте ви, тут відповідає PM
            ▲ питання: вебформа issue          │ /requirements-sync у Claude Code чи Cursor
            │                                  ▼ знімок вимог → гілка sync/<дата> → PR «Оновлення вимог»
 Ви:  <я>/<team-slug>   (шаблон проєкту, публічне; свої Supabase, Vercel, CI, ruleset solo-main)
      requirements/ — знімок вимог PM (руками не правите)
      openspec/     — ваша специфікація: add-<зріз> (переклад вимог), impl-<зріз> (план)
      код · тести з AC ID · docs/conformance.md · docs/spec-reading.md
```

Чотири правила:

1. **Вимоги — у репо PM.** PM змінює вимогу правкою issue чи файлу, додає рядок у розділ «Журнал змін» (дата, що
   змінилось, посилання на питання — повна адреса issue) і пише в чат команди «вимоги оновлено». Версій і тегів
   немає: що саме ви забрали, показує дата знімка в шапці `docs/conformance.md`.
2. **У ваше репо вимоги потрапляють лише через `/requirements-sync`.** Теку `requirements/` руками не правите. Це
   правило є в `AGENTS.md` вашого репо, а CodeRabbit попереджає, якщо її чіпає PR іншого типу.
3. **Специфікацію пишете ви.** Перекладаєте `requirements/` в OpenSpec. ID критеріїв PM (`AC-<AREA>-<NN>`)
   зберігаєте дослівно, правил від себе не додаєте: що неясно — питання до PM.
4. **Питання й пропозиції змінити вимоги — issues «Питання до вимог» у репо PM** через його вебформу. Відповіді там
   само, і їх бачить уся команда.

### Ваш `main` і типи PR

Після кроку 6 у ваш `main` нічого не потрапляє без PR, як на клієнтському проєкті агенції:

- **У `main` — лише через PR.** Прямий push відхиляється, force push і видалення `main` заборонено. Обійти правило не
  може ніхто, і ви теж.
- **Approve не потрібен.** Ви працюєте самі, а свій PR GitHub схвалити не дає. Рецензує CodeRabbit, і на кожен його
  коментар ви відповідаєте виправленням або аргументом.
- **Перевірки** `spec`, `app`, `conformance`, `db-check` мають бути зеленими. Злиття — **Squash and merge** (merge
  commit теж дозволено).
- **Чотири типи PR** (шаблон опису PR у вашому репо):

| Тип | Гілка | Що змінює | Кроки |
|---|---|---|---|
| «Оновлення вимог» | `sync/<дата>` | лише `requirements/` і шапку `docs/conformance.md` (рядок «Вимоги: …»); робить `/requirements-sync` | 8, 13 |
| «Специфікація» | `spec/<id зміни>` | `openspec/**`, рядки `docs/conformance.md`, `docs/spec-reading.md`; плюс окремий коміт, що прибирає з назв тестів ID AC, прибраних зі специфікації | 10, 11, 13 |
| «Реалізація» | `task/<коротко>` (у день 0 — `setup/bootstrap`) | `src/`, `supabase/`, `tests/`, рядки `docs/conformance.md`, `docs/decisions/`, `docs/bootstrap.md`, `docs/img/`, `supabase/demo-users.json`, галочки в `openspec/changes/impl-<зріз>/tasks.md` і archive `impl-<зріз>` | 6, 12, 13 |
| «Оновлення шаблону» | `template/<коротко>` | `git cherry-pick` виправлення шаблону | [розділ нижче](#оновлення-шаблону) |

## Якщо ви вже почали

**Ваше репо створене з шаблону проєкту до другої редакції** (у ньому є `.claude/commands/spec-sync.md`, а
`requirements-sync.md` немає). Спершу перенесіть оновлення шаблону: розділ [«Оновлення
шаблону»](#оновлення-шаблону), SHA комітів — в оголошенні викладача в чаті курсу. Якщо cherry-pick дав конфлікт у
`docs/conformance.md`, візьміть коментар із версії шаблону, а свої рядки таблиці залиште: шапку перепише перша
`/requirements-sync`. Інші конфлікти — у файлах, які ви змінювали самі: залиште свої правки й допишіть зміни
шаблону.

**Ви вже запускали `/spec-sync` з першої редакції** (у репо є копія вимог PM у `product/` і `openspec/specs/`, у
шапці — `Вимоги: … · коміт <sha> · <дата>`):

1. Перенесіть оновлення шаблону (пункт вище).
2. **Замініть копію `product/` версією шаблону** в тій самій гілці `template/<коротко>`, до push. Конфлікт у
   `product/` під час cherry-pick розв'яжіть як завгодно: ці команди однаково замінять теку цілком.

   ```bash
   git rm -r -q --ignore-unmatch product
   git checkout template/main -- product
   git commit -m "Replace the PM product/ copy with the template's product/"
   ```

   Ваш локальний `product/denylist.local.txt` git не відстежує, тож він лишається на місці. Продуктовий контекст
   PM тепер приходить у `requirements/product.md`.
3. **`openspec/specs/` залиште:** це вже початок вашої специфікації. У кроці 10 замість `add-<зріз>` зробіть зміну
   `align-<зріз>` (MODIFIED / ADDED / REMOVED). Кожен AC з `requirements/` має стати сценарієм з тим самим ID і
   тим самим змістом. AC, яких у вимогах PM більше немає, приберіть (REMOVED). Рядки матриці зі статусом
   `відкладено (нова вимога — чекає реалізації)` CI приймає; новим рядкам ставте `відкладено (чекає реалізації)`.
4. **Перша `/requirements-sync`** — з адресою аргументом: `/requirements-sync <pm>/<team-slug>-spec`. Шапка ще в
   старому вигляді, і агент може спитати, яку адресу брати: беріть ту, яку PM дав у чаті команди.

**Ви почали до 15.10 у спільному репо команди.** Створіть власне репо з шаблону й налаштуйте його (кроки 0–6).
Запушити гілку старого репо в нове не вийде: «Use this template» починає нову історію, і GitHub не відкриє PR між
непов'язаними історіями. Тому переносимо файли. Що змінено у вашій гілці, покаже команда:

```bash
git -C ../<старий-клон> diff --name-only origin/main...<ваша-гілка>
```

У новому репо створіть гілку від свіжого `main` (`git switch -c task/<коротко>`) і скопіюйте туди лише свій код:
`src/`, `tests/`, `supabase/migrations/`, `docs/decisions/`. Не переносьте `product/`, `openspec/` і `docs/team.md`.

- **Злиття.** PR з тестами з AC ID зливайте лише після кроку 10: до того у вашій специфікації немає жодного AC, і
  `conformance` падає з `ORPHAN`.
- **Журнал.** `docs/spec-reading/<я>.md` перенесіть у `docs/spec-reading.md` (PR «Специфікація», крок 10).
- **Питання.** Створіть свої питання заново формою репо PM (крок 9) з посиланням на старе issue.

## 1. Власне репо з шаблону (10 хв) — трек A

Через браузер: <https://github.com/koldovsky/2026-quitcode-06-project-template> → **Use this template** →
**Create a new repository** → Owner — ваш особистий акаунт (не організація), Repository name — `<team-slug>`,
**Public** → Create. Потім клон: `gh repo clone <я>/<team-slug>`, `cd <team-slug>`, `npm ci`.

Або однією командою (з теки, де тримаєте проєкти):

```bash
gh repo create <team-slug> --public --template koldovsky/2026-quitcode-06-project-template --clone
cd <team-slug>
npm ci
```

Попередження `npm warn deprecated …` / `allow-scripts` під час `npm ci` очікувані. `npm audit fix` і оновлення
пакетів до latest не запускайте: шаблон перевірено з TypeScript ^5 і ESLint ^9.

**Публічним — одразу й назавжди.** На GitHub Free ruleset і секрети environment діють лише в публічних
репозиторіях. До того ж ваше репо читатимуть PM (для нотатки про реалізації) і перевірка за SHA.

**Доказ:** URL вашого репо — для файлу здачі. Перший прогін CI (Actions → CI) має стартувати після створення. Якщо
прогону немає — Actions → CI → **Run workflow** або `gh workflow run ci.yml`. У ньому всі п'ять jobs, зокрема
`db-check` (на `main` теж). `db-deploy` зелений, але міграцій не застосовує: у лозі буде повідомлення про порожній
`SUPABASE_DB_URL`, і так має бути до кроку 3. Цей прогін знадобиться ruleset-у в кроці 6.

## 2. Supabase: організація, проєкт, Auth (30 хв) — трек A

База — лише ваша: її створюєте ви, і вона займає ваш безкоштовний слот.

1. **Організація.** Dashboard → New organization → назва `<team-slug>`, план **Free**.
2. **Проєкт** у цій організації: назва `<team-slug>`, регіон — найближчий. **Пароль бази** — довгий (≥ 20
   символів), лише з літер і цифр: тоді його не треба кодувати в рядку підключення (крок 3). Збережіть його в
   менеджері паролів.
3. **Auth.** У налаштуваннях Authentication вимкніть **Allow new users to sign up**, а в провайдері Email —
   **Confirm email** (орієнтовно Authentication → Sign In / Providers; точну назву перевірте в інтерфейсі).
   Публічний ключ лежить у JS-бандлі, тож з увімкненою реєстрацією будь-хто зареєструється у вашому застосунку
   сам. Вбудована пошта Supabase надсилає 2 листи на годину на весь проєкт і лише членам вашого проєкту Supabase,
   тому користувачів створює скрипт (крок 5), а не лист. `supabase/config.toml` шаблону має
   `[auth] enable_signup = false`, але це конфігурація CLI: у хмару вона не переноситься, тож перемикач у Dashboard
   обов'язковий.

Проєкт Free **засинає** після ~7 днів без активності. Відновлюєте його ви: Dashboard → Restore project (точну назву
кнопки перевірте в інтерфейсі). Перевіряйте перед кожним заняттям і перед здачею: ваш прод-URL відкриватимуть PM і
перевірка.

## 3. Environment `production` і секрет `SUPABASE_DB_URL` (15 хв) — трек A

Міграції в хмарну базу застосовує лише CI: job `db-deploy` після кожного merge у `main`. Йому потрібен рядок
підключення з паролем бази. Цей секрет має бачити тільки `main`, а не ваші робочі гілки: так незлита міграція з
гілки ніколи не потрапить у прод.

1. **Environment.** Settings → Environments → `production`. Перший прогін CI з кроку 1 міг уже створити його
   автоматично (job `db-deploy` на нього посилається) — тоді відкрийте його. Якщо Vercel (крок 4) створив
   `Production` з великої літери для своїх деплоїв, це те саме середовище: регістр у назвах GitHub не розрізняє.
   Налаштуйте його, нового не створюйте. Якщо середовища ще немає — **New environment** → `production` → Configure
   environment. Deployment branches and tags → **Selected branches and tags** → Add deployment branch or tag rule →
   `main`.
2. **Рядок підключення.** Supabase → кнопка **Connect** угорі проєкту → **Session pooler** (порт `5432`) → URI
   вигляду `postgresql://postgres.<ref>:[YOUR-PASSWORD]@<хост пулера>:5432/postgres`. Замініть `[YOUR-PASSWORD]`
   паролем бази. Потрібен саме Session pooler: пряме підключення на Free працює лише через IPv6, а раннери GitHub —
   IPv4. Transaction pooler (порт `6543`) для зміни схеми не годиться.
3. **Секрет environment.** У тому ж environment → Environment secrets → **Add environment secret** → Name
   `SUPABASE_DB_URL`, Value — рядок із пункту 2. Або в терміналі (значення команда спитає й ніде не надрукує):

   ```bash
   gh secret set SUPABASE_DB_URL --env production --repo <я>/<team-slug>
   ```

   Не кладіть його в Repository secrets: секрет репозиторію дістане будь-який workflow будь-якої гілки.

**Запасний шлях**, якщо `db-deploy` не підключається через пулер: офіційний варіант Supabase — `supabase link` +
`supabase db push` із трьома секретами в тому самому environment `production`. Це `SUPABASE_ACCESS_TOKEN` (токен з
обмеженими правами: Supabase → Account → Access Tokens, лише цей проєкт, право Project Settings → API Keys → API Key
Secrets — Read), `SUPABASE_DB_PASSWORD` і `SUPABASE_PROJECT_ID` (`<ref>`). Секрет `SUPABASE_DB_URL` тоді видаліть:
`db-deploy` сам перейде на цей шлях, у workflow нічого не змінюємо (README шаблону, розділ «Міграції в прод»).
Основним цей шлях не робимо: токени з обмеженими правами вийшли 06.10.2026, і з `supabase link` у них є відкрита
помилка.

## 4. Vercel: імпорт, дві змінні, Require Log In, адреси Auth (30 хв) — трек A

1. Vercel → **Add New → Project** → Import Git Repository → `<я>/<team-slug>` (дайте застосунку Vercel доступ лише
   до цього репо). Framework — Next.js, Node 24.x береться з `engines` у `package.json`.
2. **Environment Variables** для **Production і Preview** — рівно дві: `NEXT_PUBLIC_SUPABASE_URL` і
   `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (Supabase → Project Settings → API Keys, ключ `sb_publishable_…`).
   `SUPABASE_SECRET_KEY` у Vercel **ніколи** не додаємо: він обходить RLS, а застосунку першого зрізу не потрібен.
   **Не** підключайте Supabase через Marketplace-інтеграцію Vercel: вона створює окрему організацію й займає слот.
3. **Deploy** → прод-URL `https://<проєкт>.vercel.app/login` відкривається.
4. Settings → **Deployment Protection** → **Vercel Authentication**: вимкніть перемикач **Require Log In** → **Save**.
   На новому Hobby-проєкті він увімкнений; список «Standard Protection» поруч не чіпайте. Інакше PM, колеги й
   викладач не відкриють preview з ваших PR: на Hobby немає учасників команди, і без входу у ваш акаунт Vercel
   preview закрите. Чому це прийнятно лише для навчального проєкту і за яких трьох правил —
   [нижче](#ризики-відкритих-preview).
5. **Адреси Auth.** Supabase → Authentication → **URL Configuration**: Site URL — прод-URL Vercel; Redirect URLs —
   `http://localhost:3000/**` і `https://*-<slug-акаунта-vercel>.vercel.app/**`. Slug — остання частина адреси
   будь-якого preview: `<проєкт>-<хеш>-<slug>.vercel.app`.
6. Після будь-якої зміни змінних — Deployments → останній деплой → ⋯ → **Redeploy**: змінні діють лише для нових
   деплоїв.

Обмеження Hobby: лише некомерційне особисте використання — застосунок навчальний, дані вигадані, без брендингу
клієнта. Cron — щонайбільше раз на добу.

### Vercel: preview і прод

- **Preview.** На кожен PR бот Vercel пише коментар із preview-URL. Відкрийте його у вікні інкогніто: сторінка
  `/login` має відкритися без входу у Vercel.
- **Прод.** Після merge у `main` Vercel деплоїть прод-URL, а job `db-deploy` застосовує нові міграції. Якщо прод
  одразу після merge показує помилку бази, дочекайтеся завершення `db-deploy`.
- Vercel не є обов'язковою перевіркою ruleset-у: червоний деплой PR не блокує. Але зріз має працювати на вашому
  прод-URL (крок 12).

### Ризики відкритих preview

Ви вимкнули захист preview, щоб PM, колеги й викладач могли їх відкривати. Відтепер кожна адреса деплою — preview
гілки й URL кожного коміту — відкрита будь-кому, хто має посилання, а Vercel публікує ці посилання в коментарях до PR
у вашому публічному репо.

- **Preview працюють з тією самою базою, що й прод** (на Supabase Free окремої бази для preview немає): незавершений
  код будь-якої вашої гілки читає й пише ті самі дані.
- **Старі деплої лишаються доступними** за своїми адресами. Виправлення в базі (міграція) захищає всі деплої одразу,
  а виправлення лише в коді застосунку старих адрес не торкається. Небезпечний старий деплой видаліть у Vercel:
  Deployments → ⋯ → Delete (точну назву перевірте в інтерфейсі).
- **Сторінку входу кожного деплою може пробувати будь-хто**, тому паролі синтетичних користувачів робіть довгими й
  випадковими.

Тому відкриті preview безпечні лише за трьох правил: **секретного ключа немає у Vercel** (preview не обійде RLS),
**RLS і явні GRANT на кожній таблиці** (саме вони захищають дані, а не вхід у Vercel), **дані лише синтетичні**
(`*@example.test`, жодних справжніх клієнтів). У клієнтських проєктах агенції захист не вимикають: там потрібен
платний план із паролем або SSO.

## 5. Перша база, `users:demo`, локальний запуск (20–30 хв) — трек A

1. **Міграції й сид шаблону.** Actions → CI → **Run workflow** → Branch `main`, позначте `include_seed` → Run. Або:

   ```bash
   gh workflow run ci.yml --repo <я>/<team-slug> --ref main -f include_seed=true
   ```

   Job `db-deploy` має бути зеленим, а в лозі — застосована міграція шаблону
   `20261012000000_profiles_and_roles.sql` (точний текст виводу CLI перевірте в лозі). Сид у хмарі виконується
   **лише один раз**, пізніші довідкові дані додаються новою міграцією. `include_seed` після цього не вмикайте.
   Червоний job — перевірте пароль у рядку підключення і чи проєкт не на паузі. Не допомогло — запасний шлях із
   кроку 3.
2. **Локальні перевірки:**

   ```bash
   npm run lint
   npm run typecheck
   npm test
   ```

3. **`.env.local` і синтетичні користувачі.** `.env.local` — у `.gitignore`. Значення — з Supabase → Project
   Settings → API Keys:

   ```bash
   cp .env.example .env.local     # PowerShell: Copy-Item .env.example .env.local
   # заповніть: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY (sb_publishable_…),
   # SUPABASE_SECRET_KEY (sb_secret_…), DEMO_USER_PASSWORD (довгий і випадковий)
   npm run users:demo     # admin@example.test, member1@example.test, member2@example.test
   npm run dev            # http://localhost:3000 → вхід як admin@example.test
   ```

   `SUPABASE_SECRET_KEY` обходить RLS. Він живе лише у вашому `.env.local` для `npm run users:demo`: ніколи у
   Vercel, ніколи з префіксом `NEXT_PUBLIC_`, ніколи в коді застосунку. Значень не вставляйте в чат з агентом:
   `.claude/settings.json` шаблону забороняє Claude Code читати `.env*`. У Cursor такої заборони немає, тож тут
   усе тримається на вашій дисципліні.
4. **Вхід на проді.** Прод-URL → вхід як `admin@example.test` тим самим паролем. Так ви перевіряєте змінні Vercel і
   адреси Auth.
5. **Свої тестові користувачі** — лише синтетичні. З потрібною роллю: запис `*@example.test` у
   `supabase/demo-users.json` у тому самому PR «Реалізація», що й міграція ролей зрізу (крок 12.1), і після merge
   знову `npm run users:demo`.
   Швидкий шлях без ролі: Supabase → Authentication → Users → **Add user** з автопідтвердженням (точну назву поля
   перевірте в інтерфейсі).
6. **Denylist команди.** PM надішле особистим повідомленням список справжніх назв. Збережіть його в
   `product/denylist.local.txt`: по одній назві на рядок, `#` — коментар, шлях уже в `.gitignore`. Тоді
   `npm run spec:check` ловить ці назви у `requirements/`, `openspec/`, `docs/`, `src/`, `supabase/` і `tests/` ще
   до push. Тека `product/` у вашому репо тепер лише для denylist. Перевірка: перша команда має показати рядок
   `!! product/denylist.local.txt` (`!!` означає, що git ігнорує файл) і жодного рядка з `??`. Друга має показати
   «слів у denylist: N», де N — не менше кількості назв:

   ```bash
   git status --short --ignored product
   npm run spec:check
   ```

   Бачите `denylist.local.txt.txt`? Провідник Windows приховав розширення: увімкніть Провідник → Вигляд → Показати →

`supabase db push` з ноутбука, DDL у SQL Editor чи Table Editor, `supabase db reset --linked`, `migration repair`
агентом або поза відновленням за README шаблону («Збої й відновлення»), `db push --include-all`. База ваша, і як
Owner ви технічно можете змінити в Dashboard що завгодно, тож це правило тримається лише на вас. Зміна поза `main`
ламає наступний `db-deploy` («Remote migration versions not found…»), а рубрика C зараховує лише міграції, що
пройшли PR і `db-deploy`.

## 6. Ruleset `solo-main` і CodeRabbit (25 хв) — трек A

Порядок важливий: спершу CI пройшов на `main` (кроки 1 і 5), потім ruleset. Обов'язкові перевірки в ньому
прив'язані до джерела GitHub Actions, а GitHub приймає таку прив'язку, лише коли Actions уже нещодавно звітували
перевірки в цьому репо.

**Налаштування злиття.** Settings → General → Pull Requests: **Allow merge commits** і **Allow squash merging** мають
бути увімкнені (так за замовчуванням), **Allow rebase merging** можна вимкнути. Метод, вимкнений тут, не запрацює й
з ruleset-ом.

**Через `gh api`** (рекомендовано; JSON — [`materials/rulesets/solo-main.json`](../materials/rulesets/solo-main.json)):

```bash
curl -sLo ruleset.json https://raw.githubusercontent.com/koldovsky/2026-quitcode-06-specs-in-practice-hw/main/materials/rulesets/solo-main.json
gh api repos/<я>/<team-slug>/rulesets --method POST --input ruleset.json
rm ruleset.json
```

PowerShell: `curl.exe` замість `curl` (у Windows PowerShell 5.1 `curl` — це інша команда), `Remove-Item ruleset.json`
замість `rm`.

**Або через браузер:** Settings → Rules → Rulesets → New ruleset → **Import a ruleset** → файл `solo-main.json` (спершу
збережіть його за посиланням вище). Або New branch ruleset і вручну:

- Ruleset name — `solo-main`, Enforcement status — **Active**, Bypass list — **порожній**;
- Target branches → Add target → **Include default branch**;
- **Restrict deletions**, **Block force pushes**;
- **Require a pull request before merging**: Required approvals — `0`; Allowed merge methods — **Merge** і
  **Squash**, без Rebase;
- **Require status checks to pass** → Add checks → `spec`, `app`, `conformance`, `db-check` (джерело — GitHub
  Actions); **Require branches to be up to date before merging** — вимкнено → Create.

Точні назви полів перевірте в інтерфейсі. Якщо перевірка не знаходиться в пошуку, відкрийте Actions: прогони з
кроків 1 і 5 мають містити jobs саме з такими назвами. Те саме, якщо `gh api` відповідає помилкою про
`integration_id`: спершу зелений прогін CI на `main`, потім повторіть команду.

Чому саме так. PR обов'язковий навіть для одного розробника: кожна зміна проходить CI і CodeRabbit, а міграція
потрапляє в базу лише після merge. 0 approve — бо свій PR GitHub схвалити не дає. Перевірки без «up to date» — щоб
не оновлювати гілку після кожного merge іншої вашої гілки. Squash дає в `main` по одному коміту на задачу.

**CodeRabbit.** <https://github.com/apps/coderabbitai> → Install → ваш акаунт → Only select repositories →
`<team-slug>`. У публічних репо з < 10 зірок рев'ю не запускається само: після створення PR пишіть окремим
**коментарем** `@coderabbitai review`. Кількість рев'ю на годину обмежена, тож просіть його після групи виправлень, а
не після кожного push. Конфіг `.coderabbit.yaml` уже є в шаблоні. Серед іншого він попереджає, якщо PR не типу
«Оновлення вимог» чіпає `requirements/`.

**Докази налаштування — перший PR під ruleset-ом.** Він же перевіряє ruleset. Прямих комітів у `main` не робимо й
тут:

```bash
git switch -c setup/bootstrap
```

Позначте пункти чекліста `docs/bootstrap.md` і допишіть докази **без жодного значення**: посилання на прогони CI і
`db-deploy`, назви змінних Vercel і де їх задано, прод-URL, знімки екрана в `docs/img/` (вимкнені «Allow new users to
sign up» і «Confirm email», Require Log In, сторінка ruleset-у). Знімки `spec:check` не читає, тож перевірте самі,
що на них немає назв клієнта, імен людей, email не з `example.test` і значень ключів.

```bash
git add docs
git commit -m "Setup evidence in docs/bootstrap.md"
git push -u origin setup/bootstrap
gh pr create --web
```

У шаблоні опису позначте тип «Реалізація», окремим коментарем — `@coderabbitai review`. **Перевірка ruleset-у:** поки
CI не зелений, кнопка merge неактивна. Потім **Squash and merge** → `git switch main` і `git pull`. Посилання на сам
цей PR і його preview допишіть у `docs/bootstrap.md` наступним PR «Реалізація» (наприклад, разом із першою задачею,
крок 12).

**Доказ:** злитий PR зі `docs/bootstrap.md`; сторінка ruleset-у або вивід `gh api repos/<я>/<team-slug>/rulesets`.

Наприкінці — посилання на своє репо й прод-URL у чат команди: вони знадобляться PM для нотатки про реалізації.

## 7. Зустріч команди: перший раунд питань до брифу (15–20 хв)

3. **3 хв — PM:** відповідає або записує питання як відкрите.

## 8. Перші вимоги: `/requirements-sync` (15–30 хв) — трек A

Коли PM напише в чат команди «вимоги оновлено» (до кінця дня 3, 16.10), закомітьте або сховайте незавершені зміни:
`git stash -u` (сховає й нові, ще не відстежувані файли). Команда працює лише з чистим робочим деревом
(`git status --short` порожній). На свіжий `main`
агент перейде сам.

У Claude Code: `/requirements-sync <pm>/<team-slug>-spec` (або повна адреса `https://github.com/<pm>/<team-slug>-spec`).
У Cursor — `/requirements-sync` і ту саму адресу в тому самому повідомленні. Адресу вказуєте лише першого разу, далі
команда бере її з шапки `docs/conformance.md`. Якщо немає ні адреси, ні шапки, агент спитає.

Команди `/requirements-sync` у вашому репо немає? Репо створене до другої редакції шаблону — спершу [«Якщо ви вже
почали»](#якщо-ви-вже-почали).

**Що робить агент.** Скриптів синхронізації немає, лише `gh` і `git`. Агент змінює тільки `requirements/` і шапку
`docs/conformance.md`. Точний вигляд звіту може відрізнятися, але кроки такі:

1. Перевіряє, що робоче дерево чисте, і переходить на свіжий `main`.
2. Знаходить адресу репо PM: шапка `docs/conformance.md`, далі аргумент команди, інакше питає вас.
3. Визначає, де PM тримає вимоги:
   - **issues**, якщо в репо PM є відкриті issues з міткою `requirement`:

     ```bash
     gh issue list --repo <pm>/<team-slug>-spec --label requirement --state open --json number,title,updatedAt,url
     ```

   - **інакше `docs/`:** агент бере останній коміт `main` PM звичайним git, без тимчасових тек
     (`git fetch --depth 1 https://github.com/<pm>/<team-slug>-spec main`), а з нього — `docs/product.md` і
     `docs/requirements/*.md`, крім `_template.md` і `README.md`.
4. Створює гілку `sync/<YYYY-MM-DD>` (наприклад, `sync/2026-10-16`; друга синхронізація за день —
   `sync/2026-10-16-2`).
5. Замінює `requirements/` цілком свіжим знімком:
   - **з issues** — `requirements/<N>-<slug>.md` на кожну відкриту вимогу і `requirements/product.md` з issue
     «Продукт». Кожен файл починається з рядка `> Джерело: <адреса issue> · оновлено <час>`, далі заголовок і текст
     issue дослівно. Вимогу, яку PM закрив, наступна синхронізація прибере;
   - **з `docs/`** — ті самі файли PM у `requirements/`, на початку кожного — рядок джерела з адресою файлу на коміті
     PM, коротким SHA і датою.
6. Показує звіт:
   - які вимоги додано, змінено чи прибрано;
   - які AC ID додано, змінено чи прибрано (порівнює з тим, що було у вашому `main`);
   - нові рядки «Журналу змін» PM.
7. Оновлює шапку `docs/conformance.md`, наприклад:

   ```text
   Вимоги: https://github.com/<pm>/<team-slug>-spec · джерело: issues · знімок 2026-10-16
   ```

   До першої синхронізації там стоїть `Вимоги: — (заповнює /requirements-sync)`. **Рядків матриці агент не
   додає:** AC з'являться у вашій специфікації лише після перекладу (крок 10), і тоді ж — їхні рядки.
8. Комітить «Оновлення вимог з <pm>/<team-slug>-spec (issues, 2026-10-16)». Пушить гілку й відкриває PR
   «Оновлення вимог» — **лише після вашого «так»**.
9. Підказує, що далі: перекласти вимоги у специфікацію (`/opsx:propose`, крок 10), питання — скілом `spec-clarify`
   (крок 9).

**PR «Оновлення вимог».**

1. У шаблоні опису позначте тип «Оновлення вимог» і вставте текст опису, який дав агент: рядок `Вимоги: …`, які
   вимоги й AC додано, змінено чи прибрано, нові рядки журналу PM.
2. Перевірте вкладку Files changed: там лише `requirements/` і шапка `docs/conformance.md`.
3. Окремим коментарем — `@coderabbitai review`.
4. Дочекайтеся зелених `spec`, `app`, `conformance`, `db-check`. Попередження `ac:coverage` «вимогу PM ще не
   перекладено в специфікацію: AC-…» тут очікуване, CI воно не валить. Воно зникне після кроку 10.
5. **Squash and merge** → `git switch main` і `git pull`.

**Ніколи не правте `requirements/` руками**, ні в цьому PR, ні в інших. Не згодні з вимогою чи знайшли в ній
помилку — ставте питання в репо PM (крок 9). PM виправить вимогу, і зміна прийде наступною `/requirements-sync`.
Ручна правка розводить ваш знімок з текстом PM, а наступна синхронізація мовчки її перезапише. Якщо `spec` червоний
через текст PM (наприклад, справжня назва з denylist), файлів теж не правте: напишіть PM у чат команди й повторіть
`/requirements-sync` після його виправлення.

**PM ще не написав вимог?** Поки PM пише, його issues «Вимога» (або файли в `docs/requirements/`) уже видно в
браузері. Читайте їх і готуйте питання (крок 9), а тим часом доналаштуйте своє репо. Синхронізуйте після «вимоги
оновлено».

**Доказ:** злитий PR «Оновлення вимог» у вашому репо; `requirements/` у `main`; шапка `docs/conformance.md` з
адресою репо PM, джерелом і датою знімка.

## 9. Читання вимог і питання (45 хв – 1 год) — трек B1

Після першої `/requirements-sync` вимоги лежать у вашому репо: `requirements/product.md` (бачення, ролі й матриця
прав, глосарій, roadmap, що поза scope) і по файлу на вимогу (навіщо, ролі, основний сценарій, критерії приймання,
поза межами, припущення, відкриті питання, журнал змін).

**Власне око — першим.** Перечитайте вимоги самі до запуску скіла й запишіть свої питання. У журналі має бути
видно, що знайшли ви, а що скіл (розділ «Що пропустив би без скіла / що скіл знайшов зайве»).

Потім у Claude Code або Cursor: «Уточни вимоги скілом spec-clarify». Скіл читає `requirements/` і чернетку вашої
специфікації, якщо вона вже є (крок 10). Репо PM він бере з шапки `docs/conformance.md`, а далі:

1. проходить 11 категорій таксономії і записує таблицю Ясно / Частково / Немає в розділ `## Скан за таксономією`
   вашого журналу `docs/spec-reading.md`;
2. ставить вам **по одному** питанню з варіантами й рекомендацією — ви вирішуєте, чи йде воно до PM;
3. видає готові тексти питань для форми «Питання до вимог» (або коментарів до наявних) і додає рядки в журнал.

Issues скіл сам не створює.

**Спершу перегляньте наявні питання** всієї команди в репо PM:

```bash
gh issue list --repo <pm>/<team-slug>-spec --label question --state all
```

Або відкрийте сторінку Issues репо PM. Ваше питання вже є — допишіть коментар із новим випадком, варіантом чи
впливом, а не дубль (посилання на коментар — `…/issues/N#issuecomment-M`). Зараховуємо щонайменше 3 питання: власні
issues або змістовні коментарі з новим варіантом чи впливом у наявному питанні колеги. З них щонайменше 1 — власне
issue.

**Питання — лише через вебформу:** `https://github.com/<pm>/<team-slug>-spec/issues/new?template=question.yml` (або
Issues → New issue → «Питання до вимог»). Вставте поля з тексту скіла:

- посилання на вимогу: повна адреса issue «Вимога» або шлях `docs/requirements/<файл>` репо PM;
- AC ID;
- питання;
- варіанти поведінки A/B/C (не реалізації) і рекомендований;
- вплив.

Точні назви полів перевірте у формі. Форма сама ставить мітку `question` і тримає однаковий формат для всіх.

**Не `gh issue create`:** у репо PM у вас немає права запису, тому мітку з командного рядка GitHub не поставить, і
питання загубиться серед інших issues. Питання коментарем у самому issue «Вимога» теж не ставте: його текст PM
переписує, а питання мають жити окремо, з міткою `question`.

**Коли.** Питання ставте якомога раніше, найкраще до кінця 17.10: уточнення PM вносить до кінця 18.10. Пізніші
питання PM може не встигнути відпрацювати.

Журнал `docs/spec-reading.md` — один файл у вашому репо:

- **таблиця скану** (11 категорій, статус Ясно / Частково / Немає, де саме). Перевірте, що всі 11 рядків на місці, а
  колонка «Де» вказує на конкретні вимоги чи AC, і виправте, з чим не згодні. Зразок —
  [`spec-reading.md` демо](../examples/leave-portal/2-clarify/spec-reading.md);
- колонка «Issue» — посилання `<pm>/<team-slug>-spec#N`;
- «Рішення (що зробили)» — ваше **робоче припущення**, поки PM не відповів;
- коли PM відповість — «Відповідь PM» і що змінили;
- «Власні припущення» — те, що ви вирішили самі без питання.

Журнал потрапляє в `main` PR-ом «Специфікація» (крок 10). Дописуєте його впродовж тижня в наступних PR цього типу
(крок 13). Зразок змісту питання — [`issue-Q2.md`](../examples/leave-portal/2-clarify/issue-Q2.md): поля там ще зі
старої форми, але варіанти поведінки, рекомендований і вплив пишуться так само.

**Доказ:** щонайменше 3 питання в репо PM (власні issues або змістовні коментарі в наявних питаннях, з них
щонайменше 1 — власне issue); `docs/spec-reading.md` у `main` вашого репо.

## 10. Переклад у специфікацію (1–1,5 год) — трек B2

Вимоги PM написані людською мовою. Агент, CI і `ac:coverage` працюють зі специфікацією OpenSpec, тож перекладаєте ви.
**Перекладаєте, а не дописуєте:**

- кожне `SHALL` і кожен сценарій мають джерело в тексті PM;
- ID критеріїв PM — дослівно;
- нових правил і власних AC немає.

Чого PM не написав, а реалізації потрібно (наприклад, що робити з порожнім полем), — це питання до PM (крок 9) і
рядок в Open questions. Поки PM не відповів, можна записати робоче припущення в Assumptions з позначкою (розробник)
і посиланням на питання. Нове `SHALL` на цьому не пишемо.

```bash
git switch main
git pull
git switch -c spec/add-<зріз>
```

**З агентом** (Claude Code): `/opsx:propose add-<зріз>: переклади вимоги першого зрізу з requirements/ у
специфікацію; пиши лише proposal.md і specs/, без design.md і tasks.md` (у Cursor — `/opsx-propose`). Формат агент
бере з `openspec/config.yaml`. `/opsx:propose` за своєю інструкцією генерує всі артефакти зміни. Якщо він усе ж
створив `design.md` чи `tasks.md`, видаліть їх до коміту: план — окрема зміна `impl-<зріз>` (крок 11). Потім **читайте
й правте кожен рядок**: агент охоче вигадує правила, яких PM не писав, і пише «тощо».

**Вручну:** `npx openspec new change add-<зріз>`, далі файли за [`docs/spec-guide.md`](spec-guide.md).

Куди переходять розділи вимоги PM:

| Вимога PM (`requirements/…`) | Ваша зміна `openspec/changes/add-<зріз>/` |
|---|---|
| Навіщо | `proposal.md` → `## Why` (з посиланням на файл вимоги й дату знімка) |
| Основний сценарій і критерії приймання | `## What Changes` (коротко й списком AC ID) і дельта `specs/<capability>/spec.md` |
| Користувачі й ролі; ролі й матриця прав з `requirements/product.md` | `## Users & roles` (таблиця) |
| Поза межами | `## Non-goals` |
| Припущення | `## Assumptions` (і ваші робочі припущення — з позначкою (розробник) і посиланням на питання) |
| Відкриті питання | `## Open questions` (з посиланнями `<pm>/<team-slug>-spec#N`) |
| — | `## Capabilities` → `### New Capabilities`: назва можливості латиницею (`leave-requests`) |
| Журнал змін | не переносимо: історія лишається в репо PM |

У дельті `specs/<capability>/spec.md`, у розділі `## ADDED Requirements`:

- **вимога** — `### Requirement: <назва>` і одне речення EARS з англійським `SHALL`
  (`WHEN …, the system SHALL …`), яке узагальнює AC під нею;
- **сценарій** — один AC PM: `#### Scenario: AC-<AREA>-<NN> <коротка назва>` (рівно чотири решітки), ID дослівно
  як у PM;
- **кроки** — так велить `openspec/config.yaml` шаблону: «Дано» PM — у `- **GIVEN**`, «Коли» — у `- **WHEN**`,
  «Тоді» — у `- **THEN**`, друге спостереження з «Тоді» — у `- **AND**`. Числа, дати й ролі дослівно, по одній
  поведінці на сценарій.

Терміни беріть із глосарію в `requirements/product.md`: ті самі слова, що в PM, без синонімів.

Зразок формату — [`proposal.md`](../examples/leave-portal/1-spec-v0.1/proposal.md) і
[`spec.md`](../examples/leave-portal/1-spec-v0.1/specs/leave-requests/spec.md) демо (кроки там ще без `GIVEN`:
передумову записано разом із дією у `WHEN`; ви пишете з `GIVEN`, як у [скелеті зміни](spec-guide.md#скелет-зміни)).

**Перевірки:**

```bash
npx openspec validate add-<зріз> --strict
npm run spec:validate
npm run spec:check
```

Потім у Claude Code або Cursor: «Запусти скіл spec-review для зміни add-<зріз>». Скіл:

- запускає ті самі перевірки;
- звіряє зміну з `requirements/`: кожен AC PM є сценарієм із тим самим ID і тим самим змістом, і немає правил без
  джерела в тексті PM;
- проходить чекліст якості AC і 11 категорій неоднозначностей;
- видає таблицю знахідок (БЛОКЕР / ВАЖЛИВО / ДРІБНИЦЯ).

Правки він вносить лише після вашого «так». Знахідка в тексті PM (AC без чисел, дві поведінки в одному AC) —
це питання до PM (крок 9), а не правка у вашій специфікації.

**PR «Специфікація».**

```bash
git add openspec docs/spec-reading.md
git commit -m "Propose add-<зріз> from the PM requirements"
git push -u origin spec/add-<зріз>
gh pr create --web
```

1. Опис PR: тип «Специфікація», рядок `Вимоги: …` із шапки `docs/conformance.md`, перелік AC ID і коротко підсумок
   `spec-review`: що знайшли, що виправили, а що стало питанням до PM. Окремим коментарем — `@coderabbitai review`.
2. **У тій самій гілці, до merge:** archive і рядки матриці. Archive переносить вимоги з
   `openspec/changes/add-<зріз>/` в `openspec/specs/<capability>/spec.md`. Без нього у вашій специфікації не буде
   жодного AC, і `ac:coverage` вважатиме вимоги PM неперекладеними.

   ```bash
   npx openspec archive add-<зріз> -y
   ```

   У `docs/conformance.md` додайте рядок на кожен AC — руками або командою `/conformance`. Статус дослівно
   `відкладено (чекає реалізації)`, колонки «Код» і «Тест» — `—`:

   ```markdown
   | AC-…-01 | <що перевіряє, коротко> | — | — | відкладено (чекає реалізації) |
   ```

   Шапку (рядок «Вимоги: …») не чіпайте: її пише лише `/requirements-sync`.

   ```bash
   npm run spec:validate
   npm run spec:check
   npm run ac:coverage
   git add openspec docs/conformance.md
   git commit -m "Archive add-<зріз>, conformance rows"
   git push
   ```

   `ac:coverage` має бути зеленим і **без попереджень «вимогу PM ще не перекладено в специфікацію»** для AC першого
   зрізу. Попередження лишається, якщо ви пропустили AC або змінили його ID: виправте в цій самій гілці. Якщо PM уже
   написав вимоги другого зрізу, попередження для їхніх AC допустимі.
3. Зелений CI → **Squash and merge** → `git switch main` і `git pull`.

**Перевірка:** на `main` є `openspec/specs/<capability>/spec.md` зі сценаріями `AC-…` PM, а в `openspec/changes/`
немає теки `add-<зріз>` (лише `archive/`).

PM оголосив зміни, поки ви перекладаєте? Закомітьте переклад у його гілку, потім `/requirements-sync` і PR
«Оновлення вимог» (крок 8). Після merge оновіть гілку перекладу (`git switch spec/add-<зріз>`, `git merge main`) і
перенесіть у зміну те, що змінив PM.

**Доказ:** злитий PR «Специфікація» з архівованою зміною `add-<зріз>`; сценарії з AC ID PM; рядки матриці;
`npm run ac:coverage` без попереджень «не перекладено» для першого зрізу.

## 11. План `impl-<зріз>` (30–45 хв) — трек C

Специфікація каже **що** зробити, а як — вирішуєте ви. План — окрема зміна OpenSpec без специфікацій:

```bash
git switch main
git pull
git switch -c spec/impl-<зріз>
npx openspec new change impl-<зріз>
```

1. У `openspec/changes/impl-<зріз>/.openspec.yaml` допишіть рядок `skip_specs: true`. Саме `skip_specs`: помилку в
   ключі OpenSpec мовчки ігнорує. План не змінює вашої специфікації.
2. Файли зміни:
   - `proposal.md` — коротко: який зріз, на якому знімку вимог (дата з шапки `docs/conformance.md`), які AC покриває;
   - `design.md` — таблиці, міграції (GRANT + RLS + політики), server actions, сторінки. Кожне рішення — з посиланням
     на AC ID;
   - `tasks.md` — **вертикальні** задачі (таблиця/RLS + доменна функція + server action/сторінка + тест), кожна
     закінчується рядком `Done when: AC-…`.

   Задач — щонайменше дві, бо рубрика C рахує злиті PR задач. Задача — один AC **або одна область одного AC**
   (міграція й RLS, дія, UI). Правила для агента — у `openspec/config.yaml` (`rules: design`, `rules: tasks`),
   шаблони — `npx openspec instructions design --change impl-<зріз>` і
   `npx openspec instructions tasks --change impl-<зріз>`.
3. Рішення, яких вимоги свідомо не дають (модель даних, бібліотеки), записуйте як ADR у `docs/decisions/`. ADR
   ідуть у PR «Реалізація» тієї задачі, якої вони стосуються, а не в PR плану.
4. `npx openspec validate impl-<зріз> --strict` і `npm run spec:check` → commit → push → PR (тип «Специфікація») →
   `@coderabbitai review` → зелений CI → **Squash and merge**.

Зразок — [`examples/leave-portal/3-impl/tasks.md`](../examples/leave-portal/3-impl/tasks.md) і
[`design.md`](../examples/leave-portal/3-impl/design.md). Задачі-issues не потрібні: задача — це пункт `tasks.md`,
і на кожну — одна гілка й один PR (крок 12).

План можна почати, поки PR кроку 10 чекає на CI. Тести з AC ID у назві зливайте лише після кроку 10. До того
`conformance` падає з `ORPHAN`: AC ще немає у вашій специфікації, і PR не злити.

## 12. Задачі: гілка → PR «Реалізація» → CodeRabbit → merge (4–5 год) — трек C

Одна задача — одна гілка й один PR. Агенту давайте одну задачу з `tasks.md` за раз, а не всі вимоги. У Claude Code
може допомогти `/opsx:apply impl-<зріз>`. Він позначає виконані пункти в `tasks.md`. Галочки, які ставить
`/opsx:apply`, комітьте в цьому ж PR задачі.

```bash
git switch main
git pull
git switch -c task/<коротко>
```

### 12.1 Міграції — лише через PR

```bash
npx supabase migration new <назва>
# SQL: enable row level security; revoke all … from anon, authenticated; явні grant;
#      політика на кожну операцію to authenticated з (select auth.uid())
```

Шлях міграції: файл у PR → `db-check` у CI застосовує **всі** міграції й сид до одноразової бази й перевіряє
порядок відносно `main` → merge → `db-deploy` застосовує її до вашої бази. Локально без Docker міграцію не запустити:
її перевіряє `db-check`.

- **`OLDER`: мітка часу міграції ≤ найновішої на `main`.** Так буває, коли ви ведете дві гілки з міграціями, і іншу
  злили першою. Хмарна база такої міграції не прийме, тому `db-check` червоний і друкує готову команду `git mv` зі
  свіжою міткою. Виправлення: `git pull origin main` у своїй гілці, виконайте цю команду (SQL не змінюється),
  `git commit`, `git push`.
- **`db-deploy` FAIL «Found local migration files to be inserted before the last migration on remote database».**
  Два ваші PR з міграціями пройшли перевірки паралельно (перевірки не вимагають свіжої гілки) і злились у
  зворотному порядку. Виправлення — окремий PR: `git mv` старшого, ще не застосованого файлу (див. журнал
  `db-deploy`) на нову мітку без зміни SQL. `db-check` покаже попередження `RENAMED`, а не FAIL → merge → `db-deploy`
  застосує. `--include-all` — ніколи.
- **Застосовані міграції не редагуємо**, лише додаємо новий файл. Деструктивне (`drop`, перейменування колонок,
  `truncate`) — обережно: база одна для проду й усіх ваших preview, а старі деплої й відкриті гілки ще читають стару
  схему.
- **Кілька записів або перевірка + запис разом** (заявка з позиціями, запуск із копією задач, утримання слоту без
  перетину). У supabase-js немає транзакцій, кожен запит — окрема транзакція. Робіть це однією функцією Postgres
  через `supabase.rpc(…)`, як `submit_leave_request` у демо (`supabase/migrations/20261013000000_leave_requests.sql`):
  `security invoker`, або `security definer` лише в схемі `private` з `set search_path = ''`.
- **Довідкові дані.** Сид шаблону застосовано в кроці 5, а в хмарі сид виконується лише раз. Нові довідкові дані
  додавайте новою міграцією з `insert … on conflict do nothing`.
- **Типи бази** (`src/lib/supabase/database.types.ts`): готовий файл для схеми вашого PR — у Summary прогону
  `db-check`. Скопіюйте його в PR. З ноутбука в базу нічого не пушимо.

**Нові ролі** (замість `member`/`admin` шаблону) — окрема нова міграція в такому порядку:

```sql
alter table public.profiles drop constraint profiles_role_check;               -- 1) зняти старе правило
update public.profiles set role = 'employee' where role = 'member';            -- 2) перевести наявні дані
alter table public.profiles alter column role set default 'employee';          -- 3) новий default
alter table public.profiles
  add constraint profiles_role_check check (role in ('employee', 'manager', 'admin'));  -- 4) нове правило
```

Дані й default оновлюємо **до** нового `profiles_role_check`, інакше він упаде на рядках `member`, які вже створив
`npm run users:demo` у кроці 5. А старе правило знімаємо першим, бо воно не пускає нові значення в `update`. Ролі
тут — з демо, у вас — з ролей і матриці прав у `requirements/product.md` (і розділу `## Users & roles` вашої
специфікації). Нові ролі в `supabase/demo-users.json` пропишіть у тому самому PR: старе `member` новий
`profiles_role_check` уже не пропустить. Після merge і зеленого `db-deploy` запустіть `npm run users:demo` — скрипт
оновить ролі наявних користувачів.

### 12.2 Код, тести, матриця

1. **Тести.** Назва кожного тесту поведінки починається з AC ID: `it("AC-…-02: …")`. Тести — лише у файлах
   `*.test.ts` / `*.test.tsx` (у `src/` або `tests/`): `*.spec.ts` Vitest не запускає, і `ac:coverage` такий тест не
   рахує. Пропущені тести (`.skip`, `.todo`) AC не покривають, а тест без жодного `expect` Vitest вважає проваленим.
2. **Матриця.** У `docs/conformance.md` знайдіть рядок свого AC (ви додали його в кроці 10 зі статусом
   `відкладено (чекає реалізації)`) і змініть його:
   - колонки «Код» і «Тест» — шляхи від кореня репо в бектиках (`src/…`, `tests/…`, `supabase/…`; номер рядка `:12`
     можна);
   - статус — дослівно `реалізовано` або `відкладено (причина)`.

   `ac:coverage` перевіряє, що ці файли є і що тест із цим AC лежить у вказаному файлі. Задача — лише частина AC
   (наприклад, міграція без UI)? Тест із AC ID для своєї частини (тест бази, доменної функції) додаєте, а статус
   лишаєте `відкладено (UI — задача 2.3)`. `реалізовано` ставить PR, що завершує AC. Рядки може оновити й команда
   `/conformance`. Шапку матриці (рядок «Вимоги: …») не чіпайте: її пише лише `/requirements-sync`.
3. **Перевірки перед PR:**

   ```bash
   npm run lint
   npm run typecheck
   npm test
   npm run build          # у виводі має бути ƒ Proxy (Middleware)
   npm run ac:coverage
   npm run spec:check
   ```

### 12.3 PR задачі

```bash
git add src supabase tests docs/conformance.md
git add openspec/changes/impl-<зріз>/tasks.md   # галочки виконаних пунктів
git add openspec/changes        # лише в останньому PR зрізу, після archive impl-<зріз> (нижче)
git add docs/decisions          # якщо додали ADR
git diff --cached --name-only   # жодних requirements/, openspec/specs/ і docs/spec-reading.md
git commit -m "AC-…-02: <що зроблено>"
git push -u origin task/<коротко>
gh pr create --web
```

1. Опис PR: тип «Реалізація», пункт `tasks.md` (наприклад, «Задача 2.1») і AC, які покриває PR. Окремим
   коментарем — `@coderabbitai review`.
2. Відкрийте preview з коментаря Vercel і пройдіть свій AC руками під синтетичним користувачем.
3. На коментарі CodeRabbit відповідайте виправленням новим комітом у ту саму гілку або аргументом у треді. Він
   помічник, а не рецензент: остаточне рішення за вами, але аргумент має бути записаний.
4. Зелений CI → **Squash and merge** → `git switch main` і `git pull`. Якщо PR мав міграцію, дочекайтеся зеленого
   `db-deploy`.

**Відповіді PM ще немає?** Або реалізуйте своє робоче припущення з `docs/spec-reading.md` і назвіть його в PR, або
залиште AC зі статусом `відкладено (чекаю відповідь PM на Q3, <pm>/<team-slug>-spec#N)`.

**Знайшли помилку?** У вимогах PM — питання через форму репо PM (крок 9), а виправлення прийде через
`/requirements-sync`. `requirements/` не правте. У своєму перекладі — нова зміна специфікації (MODIFIED) PR-ом
«Специфікація», як у кроці 13.

**В останньому PR задачі зрізу, до merge:** `npx openspec archive impl-<зріз> -y`. Зміна має `skip_specs: true`,
тож archive переносить її в `openspec/changes/archive/` і не чіпає `openspec/specs/`. Тому archive плану йде в PR
«Реалізація», а не в окремий PR «Специфікація». Після archive додайте теку цілком: `git add openspec/changes`.

**Доказ:**

- щонайменше 2 злиті PR задач у вашому репо зі зеленим CI, тестами з AC ID і рядками матриці `реалізовано`;
- міграції — лише в PR, після merge `db-deploy` зелений;
- в останньому своєму PR задачі — коментар із записом екрана 1–2 хв: ваш зріз на **вашому** прод-URL під
  синтетичним користувачем, без паролів у кадрі.

Якщо PM написав перші вимоги пізніше за кінець дня 3 (16.10), для C достатньо одного злитого PR задачі. Напишіть
це у файлі здачі.
