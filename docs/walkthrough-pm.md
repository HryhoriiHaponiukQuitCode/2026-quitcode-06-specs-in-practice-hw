# Покрокова інструкція: трек PM

> **Оновлено 15.10.2026.** Тепер у PM — власне репо вимог. Кожен розробник робить свою реалізацію у своєму репо й
> забирає ваші вимоги командою агента `/spec-sync`. Спільного репо, бази й деплою команди більше немає. Почали за
> старою інструкцією — див. розділ [«Якщо ви вже почали в репо команди»](#якщо-ви-вже-почали-в-репо-команди).

Ви — власник **вимог** команди. Ведете їх у власному публічному репо `<pm>/<team-slug>-spec`, створеному з легкого
шаблону вимог. У ньому лише `product/` і `openspec/`, перевірки специфікації та CI з одним job `spec`. Застосунку,
Supabase, Vercel і ruleset-у там немає.

Кожен розробник команди будує **власну** реалізацію того самого брифу у своєму репо `<dev>/<team-slug>`. Ваші вимоги
він забирає з `main` командою агента `/spec-sync`. Код ви не пишете. Ваш продукт — `product/`, `openspec/`,
відповіді на питання розробників, а наприкінці тижня — порівняння того, як різні люди й агенти реалізували одні
вимоги.

- Рубрика й Definition of Done — у [README](../README.md#трек-pm--100--5-балів).
- Як писати вимоги й AC — [`docs/spec-guide.md`](spec-guide.md).
- Бриф вашої команди — [`materials/briefs/`](../materials/briefs/).
- Зразок формату — [`examples/leave-portal/`](../examples/leave-portal/).
- Що робить розробник з вашими вимогами — [`docs/walkthrough-dev.md`](walkthrough-dev.md).
- Шаблон вимог — <https://github.com/koldovsky/2026-quitcode-06-spec-template>. Його README — короткий шлях PM.

Позначення:

- `<pm>` — ваш GitHub-логін;
- `<team-slug>` — слаг команди: `property-workflows`, `therapy-scheduling`, `school-purchasing` або `leave-portal`;
- `<dev>` — логін розробника команди;
- `<зріз>` — короткий слаг першого зрізу латиницею.

Команди нижче — для Git Bash на Windows і терміналу macOS. Де PowerShell відрізняється, це сказано окремо. У Windows
PowerShell 5.1 немає `&&`: виконуйте команди по черзі. Якщо PowerShell відповідає «running scripts is disabled on
this system», пишіть `npx.cmd`, `npm.cmd`, `openspec.cmd` замість `npx`, `npm`, `openspec`.

**Бюджет треку: 7,5–9 годин за тиждень.** Це сума кроків нижче без бонусу, без розділу «Якщо ви вже почали…» і без
«Оновлення шаблону». Найбільше часу йде на перший зріз (кроки 5–7, близько 3 год), цикл уточнень (крок 8) і
продуктовий контекст (крок 3).

Дні календарні (з вихідними); «кінець дня N» — 23:59 за Києвом N-го дня після заняття. День 0 — 13.10 (заняття),
кінець дня 2 — 15.10, дня 4 — 17.10, дня 7 — 20.10.

## Як рухаються вимоги (прочитайте до кроку 1)

```text
 Ви:          <pm>/<team-slug>-spec      main = поточні вимоги (product/ + openspec/specs/)
                   ▲                                   │
                   │ issues «Питання до специфікації»  │ /spec-sync у Claude Code чи Cursor
                   │                                   ▼
 Розробники:  <dev>/<team-slug>   у кожного своє репо, своя база, свій деплой
```

- **Поточні вимоги — те, що злито в `main` вашого репо.** Не гілка, не відкритий PR і не повідомлення в чаті.
  - `/spec-sync` забирає з вашого `main` лише теки `product/` і `openspec/specs/` і кладе їх у репо розробника.
  - У шапку своєї `docs/conformance.md` він записує адресу вашого репо, коміт і дату.
  - Незаархівована зміна OpenSpec лежить у `openspec/changes/` і до розробників не доходить.
- **Будь-яка зміна — через PR.** Ruleset-у немає, тож GitHub дасть запушити просто в `main`, але так не робіть.
  Строки (кінець дня 2 і дня 4) рахуємо за часом злиття PR у `main`, а розділ `## spec-review` живе в описі PR.
  Approve не потрібен: свій PR ви зливаєте самі після зеленого `spec`.
- **Історію `main` не переписуємо.** Жодного force-push, amend злитих комітів чи видалення комітів. Розробники
  записують коміт ваших вимог у шапку своєї матриці, і після переписування цей коміт уже не знайти. Знайшли помилку —
  відкрийте новий PR і додайте новий запис у `product/CHANGELOG.md`.
- **Оновили `main` — напишіть у чат команди «вимоги оновлено»** з датою й переліком нових і змінених AC. Інакше
  розробники не знають, що пора запускати `/spec-sync`.
- **Питання й пропозиції до вимог — issues у вашому репо**, через форму «Питання до специфікації». Відповідаєте
  там само, і відповідь бачить уся команда. Права запису розробникам не потрібні, бо репо публічне.

## Якщо ви вже почали в репо команди

За старою інструкцією ви могли створити спільне репо команди `<pm>/<team-slug>` із шаблону проєкту. Вимоги
переносимо, а не пишемо заново. Це ~20–30 хв замість кроку 1, у бюджет треку не входить.

1. Зробіть кроки 1 і 2 нижче: нове репо `<pm>/<team-slug>-spec` із шаблону вимог, мітка, denylist, CodeRabbit.
2. У клоні нового репо створіть гілку і скопіюйте свою роботу зі старого клону. Шляхи нижче розраховано на те, що
   обидва клони лежать поруч.

   ```bash
   cd <team-slug>-spec
   git switch -c product/move
   cp -r ../<team-slug>/openspec/specs/. openspec/specs/
   cp -r ../<team-slug>/openspec/changes/. openspec/changes/
   cp ../<team-slug>/product/denylist.local.txt product/    # локальний файл, у git не потрапить
   ```

   PowerShell: `Copy-Item -Recurse ..\<team-slug>\openspec\specs\* openspec\specs\` (так само для `changes`) і
   `Copy-Item ..\<team-slug>\product\denylist.local.txt product\`.

   - Зміни `impl-…` (план реалізації, `design.md`, `tasks.md`), якщо вони там є, видаліть із нового репо. План
     реалізації тепер у кожного розробника свій.
   - Файли `product/` не копіюйте цілком: у шаблоні вимог службові коментарі `<!-- … -->` уже під нову модель.
     Перенесіть лише свій текст — у редакторі або з агентом: «Перенеси мій текст із ../<team-slug>/product/ у
     product/ цього репо. Службові коментарі лишай із цього шаблону. openspec/config.yaml не замінюй — перенеси лише
     рядок `Продукт:` у context».
   - Записи `## spec-v0.1 — <дата>` у `CHANGELOG.md`, якщо є, перепишіть на заголовок із датою (формат —
     у кроці 7). Тегів у новій моделі немає.

   ```bash
   npm run spec:validate
   npm run spec:check
   git status --short --ignored product      # denylist.local.txt — лише з !!, жодного ?? поруч
   git add product openspec
   git commit -m "Move requirements from the team repo"
   git push -u origin product/move
   gh pr create --web
   ```

   Зелений `spec` → злийте. Якщо в старому репо перший зріз уже був заархівований, цей merge — ваші «перші вимоги
   в `main`»: перевірка й повідомлення в чат — як у кроці 7, пункти 4–5.
3. **Старе репо.** Попередьте в чаті команди: розробники можуть забрати звідти свої гілки (walkthrough-dev).

   - Потім або заархівуйте його: Settings → General → Danger Zone → **Archive this repository** (точну назву
     перевірте в інтерфейсі). Воно лишиться для читання, і ніхто не сплутає, де вимоги.
   - Або лишіть його як власну реалізацію, якщо ви ще й пишете код. Тоді це ваше репо розробника: далі за
     [walkthrough-dev](walkthrough-dev.md), з власною базою і ruleset-ом `solo-main` замість старого.
   - Collaborators старого репо й Developer-інвайти розробників у Supabase вже не потрібні — приберіть їх. Проєкт
     Supabase команди, якщо ви його не використовуєте, поставте на паузу або видаліть: так звільниться слот Free.
   - Відкриті issues із питаннями перенесіть у нове репо: в issue → **Transfer issue** → `<team-slug>-spec` (точну
     назву перевірте в інтерфейсі). Або дайте відповідь у старому репо й запишіть рішення в `decisions.md` нового.

## 0. Підготовка (15 хв)

1. **Акаунт:** особистий GitHub, не клієнтський. Supabase і Vercel PM у цій моделі не потрібні. CodeRabbit — це
   GitHub App, його ставите в кроці 2.
2. Node 24: `node -v` → `v24.…`. Потрібен для `npm ci` і перевірок специфікації. Windows — через nvm-windows або
   fnm, macOS — через fnm, nvm або Homebrew.
3. Git і GitHub CLI: `gh --version`, потім `gh auth login` (браузерний вхід). На Windows без прав адміністратора:
   `winget install --id GitHub.cli --scope user --silent`, після цього перезапустіть термінал.
4. OpenSpec CLI глобально, тієї ж версії, що в шаблоні. Його викликають команди `/opsx:*` агента:

   ```bash
   npm i -g @fission-ai/openspec@1.14.1
   openspec --version          # 1.14.1
   openspec config set telemetry.enabled false
   ```

5. Claude Code або Cursor. Обидва бачать команди `/opsx:*` (у Cursor — `/opsx-*`) і скіл `spec-review` шаблону
   вимог.

**Доказ:** нічого не комітимо. Якщо `openspec --version` показує іншу версію, `/opsx:*` поводитимуться інакше, ніж на
занятті.

## 1. Репо вимог із шаблону (10 хв) — трек A

Робимо **одразу**: поки вашого репо немає, розробникам нікуди ставити питання й нізвідки брати вимоги.

Через браузер: <https://github.com/koldovsky/2026-quitcode-06-spec-template> → **Use this template** →
**Create a new repository**. Owner — ваш особистий акаунт (не організація), Repository name — `<team-slug>-spec`,
**Public** → Create.

Або однією командою (з теки, де тримаєте проєкти):

```bash
gh repo create <team-slug>-spec --public --template koldovsky/2026-quitcode-06-spec-template --clone
cd <team-slug>-spec
npm ci
npm run spec:validate
npm run spec:check
```

Створили репо через браузер — клонуйте його: `gh repo clone <pm>/<team-slug>-spec`, далі `cd` і ті самі три команди
`npm`.

**Публічним — одразу й назавжди.** `/spec-sync` розробника забирає ваш `main` звичайним `git fetch`, без жодних прав
доступу. Форму питань відкриває будь-хто з акаунтом GitHub. Приватне репо зламає обидва шляхи. Тому все в ньому
анонімізоване (крок 2).

Settings → General → Features: **Issues** має бути увімкнено. У нового репо так за замовчуванням.

**Доказ:** URL репо вимог — для файлу здачі. Перший прогін CI (вкладка Actions) має стартувати після створення.
У ньому один job, `spec`, і він зелений. Якщо прогону немає — Actions → CI → **Run workflow** або
`gh workflow run ci.yml`.

## 2. Мітка, denylist, CodeRabbit, повідомлення в чат (15 хв) — трек A

**Мітка.** Форма «Питання до специфікації» ставить мітку `spec-question`, лише якщо мітка вже є в репо. Розробники
права запису не мають і самі її не поставлять. Issues → Labels → **New label** → `spec-question`, опис «Питання до
специфікації». Або в терміналі (`--force` оновить мітку, якщо вона вже існує, замість помилки):

```bash
gh label create spec-question --force --repo <pm>/<team-slug>-spec --description "Питання до специфікації"
```

Перевірка: на `https://github.com/<pm>/<team-slug>-spec/issues/new/choose` є форма «Питання до специфікації».
Нічого не надсилайте.

**Denylist (локальний файл і, за бажанням, секрет).** Справжні назви клієнта — **лише** в локальному
`product/denylist.local.txt` (не в git) і, якщо хочете, у секреті `SPEC_DENYLIST`. Репо публічне, тому справжніх
назв немає ні в `product/denylist.txt`, ні в жодному іншому файлі, issue чи PR. Ще одна причина бути уважним:
`/spec-sync` копіює ваш `product/` у репо кожного розробника. Витік у вашому `main` розійдеться по всіх цих репо, і
прибрати його самотужки ви вже не зможете.

- **Локальний файл (обов'язково).** У своєму клоні створіть у редакторі `product/denylist.local.txt`: по одній назві
  на рядок, `#` — коментар. Шаблон уже має цей шлях у `.gitignore`. Як перевірити:
  - вивід першої команди нижче має містити рядок `!! product/denylist.local.txt` (`!!` — git ігнорує файл) і жодного
    рядка з `??`;
  - друга команда має показати «слів у denylist: N», де N — не менше кількості ваших назв.

  ```bash
  git status --short --ignored product
  npm run spec:check
  ```

  Бачите `denylist.local.txt.txt`? Провідник Windows приховав розширення, і до імені додалось друге `.txt`.
  Увімкніть Провідник → Вигляд → Показати → Розширення імен файлів і перейменуйте файл на `denylist.local.txt`.
- **Секрет для CI (необов'язково, але радимо).** Settings → Secrets and variables → Actions → **New repository
  secret** → Name `SPEC_DENYLIST`, Secret — ті самі назви через кому. Або `gh secret set SPEC_DENYLIST --repo
  <pm>/<team-slug>-spec` (значення спитає й ніде не надрукує). З секретом job `spec` ловить назви й у змінах, які ви
  робите в браузері на GitHub, де локального файла немає.
- **Список для розробників.** Надішліть ті самі назви кожному розробнику **особистим повідомленням** (не в загальний
  чат і не в issue). Вони збережуть їх у `product/denylist.local.txt` свого репо, і `npm run spec:check` ловитиме
  назви в їхньому коді, сидах і тестах. Публічний `denylist.txt` вони отримають разом із вимогами через `/spec-sync`.

**CodeRabbit.** <https://github.com/apps/coderabbitai> → Install → ваш акаунт → Only select repositories →
`<team-slug>-spec`. `.coderabbit.yaml` шаблону вимог перевіряє межі PR (лише `product/` і `openspec/`), archive із
записом у CHANGELOG, якість специфікації й анонімізацію. Рецензент — порадник: зливати PR він не заважає. У публічних
репо з < 10 зірок рев'ю не запускається само: після створення PR напишіть окремим **коментарем**
`@coderabbitai review`.

**Повідомлення в чат команди.** Надішліть посилання на репо й закріпіть повідомлення (Pin): розробники
повертатимуться до нього весь тиждень. Текст можна взяти такий:

```text
Репо вимог команди: https://github.com/<pm>/<team-slug>-spec
Поточні вимоги — те, що в main. Що змінилось і коли — product/CHANGELOG.md.
Перші вимоги — до кінця 15.10, уточнення після ваших питань — до кінця 17.10.
Як забрати вимоги у своє репо: у Claude Code чи Cursor виконайте
  /spec-sync <pm>/<team-slug>-spec
(перший раз — з адресою, далі просто /spec-sync). product/ і openspec/specs/ руками не правимо.
Питання й пропозиції до вимог — лише через форму «Питання до специфікації»:
  https://github.com/<pm>/<team-slug>-spec/issues/new/choose
(не через gh issue create: так губиться мітка spec-question).
Коли оновлю вимоги, напишу тут «вимоги оновлено» з переліком AC.
Киньте сюди посилання на своє репо <dev>/<team-slug> — наприкінці тижня я порівнюватиму реалізації.
```

**Доказ:** мітка `spec-question` у репо; форма на `…/issues/new/choose`; закріплене повідомлення в чаті команди.

## 3. Продуктовий контекст (1–1,5 год) — трек A

```bash
git switch main
git pull
git switch -c product/context
```

Заповніть файли за коментарями в них. `/spec-sync` забирає всю теку `product/`, тож глосарій і матриця прав
потраплять до агента кожного розробника.

| Файл | Що має бути | На що звернути увагу |
|---|---|---|
| `product/vision.md` | проблема, для кого, результат (2–4 вимірні ознаки), межі продукту | одна сторінка; розділ «Обмеження навчального проєкту» лишіть |
| `product/glossary.md` | 8–15 термінів; колонка «Не вживаємо» | кожен іменник зі сценаріїв першого зрізу має бути тут |
| `product/roles.md` | ролі (коротке значення латиницею, хто це, як отримує роль) і **матриця роль × сутність × дія** | заповнені клітинки або «—», без порожніх; ролі шаблону `member`/`admin` замініть своїми; як зберігати роль у базі, вирішує кожен розробник |
| `product/roadmap.md` | зріз на кожне заняття WS6–WS11 | WS6 — перший зріз; далі — з брифу («поза зрізом») |
| `product/denylist.txt` | внутрішні слова, яких не має бути ні в спеках, ні в коді й документації (кодові назви, заглушки з чужих шаблонів на кшталт Contoso); назви сторонніх систем із брифу (QuickBooks, Buildium) — дозволені | справжніх назв клієнта тут **немає** — вони в локальному `product/denylist.local.txt` (не в git) і, якщо ви його створили, у секреті `SPEC_DENYLIST` (крок 2) |
| `openspec/config.yaml` | рядок `Продукт: …` у `context` — назва й одне речення | правила `rules:` не чіпайте; якщо змінюєте — кожен пункт у лапках ([пастки](spec-guide.md#10-пастки-формату-openspec-1141)) |

Перевірте й відкрийте PR:

```bash
npm run spec:check
git status --short --ignored product      # denylist.local.txt — лише з !!, жодного ?? поруч
git add product openspec/config.yaml
git commit -m "Fill product context: vision, glossary, roles, roadmap"
git push -u origin product/context
gh pr create --web
```

**З агентом:** «Зроби крок 3: `npm run spec:check`, commit `product/` і `openspec/config.yaml` у гілку
`product/context`, push і PR» — підтверджуйте кожну команду.

У шаблоні PR («Зміна вимог») позначте «Продуктовий контекст». Окремим коментарем напишіть `@coderabbitai review`.
Зелений `spec` → **Squash and merge**. Approve не потрібен: репо ваше, ruleset-у немає.

**Доказ:** злитий PR (посилання — у файл здачі).

## 4. Зустріч команди: перший раунд питань до брифу (20 хв)

Цю розмову команда проводить сама, у день 0 або 1, ще до чернетки зміни (крок 5). Організовуєте ви: призначте
дзвінок на 15–20 хвилин і покличте всіх розробників. Матеріал — бриф команди в
[`materials/briefs/`](../materials/briefs/).

1. **2 хв — ви:** вголос мета зрізу і три правила з розділу «Рекомендований перший зріз (WS6)» брифу.
2. **4 хв — розробники:** кожен називає одну діру — що неясно, категорію з одинадцяти (слайд 21 деки) і 2–3 варіанти
   поведінки.
3. **3 хв — ви:** відповідаєте або записуєте питання як відкрите.
4. **1 хв — підсумок:** одне питання, яке вас найбільше здивувало.

Результат — список «питання → відповідь» або «питання → відкрите» у вашій нотатці (без назв клієнта). У кроці 5 він
іде в Open questions `proposal.md`. Хто не зміг прийти, пише свою діру в чат команди до кінця дня 1. Не вдається
зібратися — та сама розмова асинхронно в чаті команди: ви публікуєте мету й правила, кожен розробник до кінця дня 1
пише одну діру, ви відповідаєте там само. Окремих балів за зустріч немає.

## 5. Перший зріз: чернетка зміни (1,5–2 год) — трек B

Зріз — з брифу («Рекомендований перший зріз»), але з вашими формулюваннями й рішеннями. Орієнтир: 3–5 вимог,
6–10 AC.

```bash

```

**З агентом** (Claude Code): `/opsx:propose <опис зрізу одним-двома реченнями>` (у Cursor — `/opsx-propose`).

- Агент поставить вам питання й напише `openspec/changes/add-<зріз>/proposal.md` і `specs/<capability>/spec.md`.
  Формат він бере з `openspec/config.yaml`.
- Ви відповідаєте на питання, а потім **читаєте й правите кожен рядок**: агент охоче вигадує правила, яких ви не
  казали, і пише «тощо».

`/opsx:propose` за своєю інструкцією генерує всі артефакти зміни, зокрема `design.md` і `tasks.md` (як реалізувати).
У репо вимог їх не лишаємо. Як реалізувати, кожен розробник вирішує сам — у власній зміні `impl-<зріз>` у своєму

наприкінці `/opsx:propose` пропускайте: у репо вимог цієї команди немає.

**Вручну:** `npx openspec new change add-<зріз>`, далі файли за [скелетом](spec-guide.md#скелет-зміни).

Що перевірити перед кроком 6:

- у теці зміни лише `.openspec.yaml`, `proposal.md` і `specs/` — без `design.md` і `tasks.md`;
- `proposal.md`: Why, What Changes з AC ID, Capabilities, Users & roles (таблиця), Non-goals, Assumptions,
  Open questions;
- кожна вимога — EARS з `SHALL`; кожен сценарій — `#### Scenario: AC-<AREA>-<NN> …`, один критерій, числа й дати;
- жодних таблиць, API, компонентів; дані синтетичні.

## 7. Перші вимоги в `main` (30 хв) — трек B, до кінця дня 2

Не працювали з гілками й PR? Попросіть агента: «Виконай крок 7 за walkthrough-pm; перед кожним git push, створенням
PR і merge питай мене». Агент питає перед push — так задано в `AGENTS.md` шаблону.

Порядок (так само для уточнень у кроці 8): гілка зміни → PR → коментарі → **у тій самій гілці** archive і запис у
`product/CHANGELOG.md` → зелений `spec` → merge → повідомлення в чат.

**Archive — обов'язково до merge.** Він переносить вимоги з `openspec/changes/add-<зріз>/` в `openspec/specs/`, а
`/spec-sync` розробників забирає лише `openspec/specs/` і `product/`. Зміну, злиту без archive, розробники не
побачать: жодного AC у них не з'явиться.

```bash
git add openspec
git commit -m "Propose add-<зріз>"
git push -u origin spec/add-<зріз>
gh pr create --web
```

1. Опис PR: у шаблоні «Зміна вимог» позначте «Нова зміна вимог», у розділі `## AC` — ADDED / MODIFIED / REMOVED з
   AC ID, і додайте розділ `## spec-review`. Окремим коментарем — `@coderabbitai review`.
2. Якщо є час, киньте посилання на PR у чат команди: «чернетка вимог, коментуйте до <час>». Коментувати PR у
   публічному репо може будь-хто з акаунтом GitHub. Питання розробників на цьому етапі — подарунок: відповідь до
   merge дешевша за зміну уточнень. Відповідайте в розмовах PR, а що змінює текст — правте в гілці.
3. **У тій самій гілці, до merge:** archive і запис у журнал.

   ```bash
   npx openspec archive add-<зріз> -y
   ```

   У `product/CHANGELOG.md` додайте запис із **датою злиття** за форматом із коментаря у файлі, наприклад:

   ```markdown
   ## 2026-10-15 — add-<зріз>
   - Зміна: `add-<зріз>` (архів: `openspec/changes/archive/2026-10-15-add-<зріз>/`)
   - ADDED: AC-…-01 … AC-…-08
   - MODIFIED: —
   - REMOVED: —
   - Відкриті питання: Q3, Q4 — див. proposal.md зміни
   ```

   Зразок змісту запису —
   [`examples/leave-portal/4-spec-v0.2/CHANGELOG.md`](../examples/leave-portal/4-spec-v0.2/CHANGELOG.md). Там
   заголовки ще за старою схемою, з тегами; у вас заголовок — дата.

   ```bash
   npm run spec:validate
   npm run spec:check
   git add openspec product/CHANGELOG.md
   git commit -m "Archive add-<зріз>, log the requirements update"
   git push
   ```

   **З агентом:** «Зроби крок 7.3: archive add-<зріз>, запис у product/CHANGELOG.md із сьогоднішньою датою за
   форматом із коментаря у файлі, commit і push у цю гілку» — підтверджуйте кожну команду.
4. CI `spec` зелений → злийте PR (**Squash and merge**; merge commit теж підходить). Потім:

   ```bash
   git switch main
   git pull
   git log -1 --format="%H %cs"
   ```

   Останній рядок — коміт і дата. Саме їх `/spec-sync` розробників запише в шапку їхньої `docs/conformance.md`, якщо
   після вас у `main` нічого не зливали. Знадобиться в кроці 9.

   **Перевірка:** відкрийте `https://github.com/<pm>/<team-slug>-spec/tree/main/openspec/specs`.

   - Там має бути тека вашої можливості з `spec.md`.
   - В `openspec/changes/` не має бути теки `add-<зріз>` (лише `archive/`).

   Якщо не так, зробіть новий PR з archive з гілки від свіжого `main`, а не force-push.
5. Напишіть у чат команди: «Вимоги оновлено (15.10): перший зріз `add-<зріз>`, AC-…-01 … AC-…-08, деталі — у
   `product/CHANGELOG.md`. Забирайте: `/spec-sync`. Питання — через форму:
   https://github.com/<pm>/<team-slug>-spec/issues/new/choose».

**Якщо не встигаєте до кінця дня 2.** Краще менший, але цілий зріз вчасно, ніж усе пізніше: 3 вимоги, 6 AC, чесні
Open questions. Решту додасте зміною уточнень у кроці 8. Напишіть у чат команди, коли чекати вимог. Розробників за
ваше запізнення не штрафують: поки вимог немає, вони налаштовують своє репо, базу й деплой. Ви ж втрачаєте бали за
строк B ([README](../README.md#що-знімає-бали-pm)).

**Доказ:** злитий PR зміни з розділом `## spec-review` (час merge — до кінця дня 2), запис у
`product/CHANGELOG.md`, тека можливості в `openspec/specs/` на `main`.

## 8. Питання розробників і цикл уточнень (1,5–2 год за дні 2–4) — трек C

Розробники відкривають issues у вашому репо за формою «Питання до специфікації»: варіанти A–E, рекомендований,
вплив. Мітку `spec-question` ставить форма. Issue без мітки (відкрите не через форму) позначте самі: справа в issue
→ Labels → `spec-question`.

1. **Відповідайте протягом доби** коментарем в issue: який варіант і чому, одним-двома реченнями. Кожен розробник
   будує свою реалізацію. Без вашої відповіді кожен зробить своє робоче припущення, і ваші вимоги розійдуться на
   кілька різних продуктів.
   - **Дублікати.** Дубль закрийте коментарем «Дубль #N — відповідь там» і Close as duplicate — це теж відповідь.
     У `decisions.md` — один рядок на питання з усіма номерами (#3, #7, #9).
   - **Пропозиції змін** (новий AC, інше формулювання) приходять тією самою формою. Прийняли — внесіть у зміну
     уточнень (пункт 3) і напишіть в issue, яким AC це стало.
2. **Записуйте** кожне рішення в `product/decisions.md`: питання (з `#N`) → відповідь → що змінилось у специфікації →
   коли й яким PR злито в `main`. Зразок —
   [`examples/leave-portal/2-clarify/decisions.md`](../examples/leave-portal/2-clarify/decisions.md). Відповіді на
   ваші власні Open questions — сюди ж.
   - Комітьте `decisions.md` у гілку `spec/clarify-<зріз>` з пункту 3, разом зі зміною.
   - Якщо жодна відповідь не змінює поведінку, усе одно потрібні гілка (наприклад, `product/decisions`) і PR.
     `decisions.md` — частина `product/`, і `/spec-sync` забирає його розробникам.
3. **Якщо відповідь змінює поведінку**, створіть нову зміну в окремій гілці:

   ```bash
   git switch main
   git pull
   git switch -c spec/clarify-<зріз>
   npx openspec new change clarify-<зріз>     # або /opsx:propose у Claude Code (/opsx-propose у Cursor)
   ```

   `openspec new change` створює лише теку зміни з `.openspec.yaml`. Обидва файли нижче пишете ви (або агент).

   - `openspec/changes/clarify-<зріз>/proposal.md` — усі розділи, як у кроці 5; пропущений розділ — блокер у
     `spec-review`:
     - Why — на які питання відповідає зміна (`#N`, Q1…);
     - What Changes — що змінилось, з AC ID;
     - Users & roles — що змінюється для ролей (або «ролі не змінюються» і таблиця змін);
     - Non-goals і Assumptions — для цих відповідей;
     - Open questions — що лишилось відкритим, або «—».

     Без `proposal.md` `validate` проходить, а `openspec show --diff` нижче падає з «has no proposal.md yet».
     Зразок — `openspec/changes/archive/2026-10-09-clarify-leave-rules/proposal.md` у
     [демо-репозиторії](https://github.com/koldovsky/2026-quitcode-06-leave-portal-demo).
   - `openspec/changes/clarify-<зріз>/specs/<capability>/spec.md` — дельта:
     - змінений сценарій: `## MODIFIED Requirements` з **повним** блоком вимоги й усіма сценаріями; AC ID
       незмінні;
     - нове правило: новий сценарій із **новим** AC ID (наступний номер) або `## ADDED Requirements`;
     - скасоване правило: `## REMOVED Requirements` з причиною.

   AC ID не перейменовуйте й ніколи не використовуйте повторно. `/spec-sync` розробників порівнює AC за ID, і
   змінений ID для них виглядає як «один AC прибрано, інший додано».

   Перед PR перегляньте diff проти поточних вимог:

   ```bash
   npx openspec show clarify-<зріз> --diff
   npx openspec validate clarify-<зріз> --strict
   npm run spec:check
   ```

   Зразок diff — [`examples/leave-portal/4-spec-v0.2/spec-v0.2-diff.txt`](../examples/leave-portal/4-spec-v0.2/spec-v0.2-diff.txt).
4. **Злиття до кінця дня 4** — так само, як у кроці 7. Спершу `spec-review` для нової зміни, потім коміт і PR:

   ```bash
   git add openspec product
   git commit -m "Propose clarify-<зріз>"
   git push -u origin spec/clarify-<зріз>
   gh pr create --web
   ```

   Опис PR — як у кроці 7:

   - «Нова зміна вимог», розділ `## AC` (ADDED / MODIFIED / REMOVED) і розділ `## spec-review`;
   - рядки `Closes #3`, `Closes #5` для питань, на які відповідає зміна: після merge ці issues закриються самі з
     посиланням на PR.

   **У тій самій гілці, до merge:** archive і запис у `product/CHANGELOG.md` із датою злиття. У записі —
   MODIFIED, ADDED, REMOVED і на які питання відповідає зміна.

   ```bash
   npx openspec archive clarify-<зріз> -y
   npm run spec:validate
   npm run spec:check
   git add openspec product/CHANGELOG.md
   git commit -m "Archive clarify-<зріз>, log the requirements update"
   git push
   ```

   Змінені (MODIFIED) AC обов'язково перелічіть у записі CHANGELOG і в повідомленні в чат. `/spec-sync` сам покаже
   розробнику додані, змінені й прибрані AC і додасть рядки для нових. А от чи відповідає змінений AC уже написаному
   коду, кожен перевіряє сам, і ваш перелік йому в цьому допомагає.

   **З агентом:** «Зроби крок 8.4: archive clarify-<зріз>, запис у product/CHANGELOG.md із сьогоднішньою датою за
   форматом із коментаря у файлі, commit і push у цю гілку» — підтверджуйте кожну команду.

   CI `spec` зелений → merge → `git switch main` і `git pull` → перевірка `…/tree/main/openspec/specs`, як у
   кроці 7.
5. Повідомте команду: «Вимоги оновлено (17.10): MODIFIED — AC-…-02; ADDED — AC-…-10, AC-…-11 (відповіді на #3, #5).
   Забирайте: `/spec-sync`». Issues, які не закрились через `Closes`, закрийте самі з посиланням на PR.

**Виправлення.** Помилка в уже злитих вимогах (зламаний сценарій, не той AC) — нова гілка від свіжого `main`, PR,
новий запис у CHANGELOG і повідомлення в чат. Не force-push, не amend і не видалення комітів у `main`: розробники вже
записали ваш коміт у шапки своїх матриць.

**Після злиття уточнень** і до здачі нових правил поведінки в `main` не додавайте: розробники саме реалізують те,
що ви злили. На пізніші питання відповідайте в issue й записуйте в `decisions.md` зі статусом «наступне оновлення»
(WS7). У треку C оцінюємо відповіді на issues, відкриті до злиття зміни уточнень.

**Доказ:** відповіді в issues, `product/decisions.md`, `product/CHANGELOG.md`, злитий до кінця дня 4 PR зміни
уточнень зі щонайменше одним MODIFIED або ADDED.

## Оновлення шаблону (коли оголосить викладач, 10–15 хв)

Виправлення шаблону вимог викладач оголошує в чаті курсу з SHA коміту. Не робіть `git merge` шаблону: «Use this
template» починає нову історію, і merge дає конфлікт у кожному файлі, що відрізняється. Натомість:

```bash
git remote add template https://github.com/koldovsky/2026-quitcode-06-spec-template.git   # один раз
git fetch template
git switch main
git pull
git switch -c template/<коротко>
git cherry-pick <sha>
npm ci
npm run spec:validate
npm run spec:check
git push -u origin template/<коротко>
gh pr create --web
```

У шаблоні PR позначте «Оновлення шаблону», в описі — SHA коміту → зелений `spec` → merge. Якщо коміт не чіпає
`product/` і `openspec/specs/`, вимоги він не змінює: запис у CHANGELOG і повідомлення «вимоги оновлено» не потрібні.
Виправлення шаблону проєкту розробники переносять у свої репо самі.

## 9. Нотатка PM — порівняння реалізацій (1 год) — трек D

Це заготовка для фінальної презентації на demo day. Одна ваша специфікація — і кілька реалізацій, які зробили різні
люди з різними агентами. Де реалізації розійшлися, там текст вимог дозволив кілька прочитань. Ваші уточнення з
кроку 8 — частина цієї історії.

**Що відкрити в репо кожного розробника** (`https://github.com/<dev>/<team-slug>`; посилання — у чаті команди,
крок 2, або спитайте):

- **`docs/conformance.md`.**
  - Шапка `Вимоги: <url> · коміт <sha> · <дата>` показує, з якою версією ваших вимог працює розробник. Порівняйте цей
    коміт із вашим `main` (`git log --format="%H %cs %s" -5` у репо вимог). Старіший коміт означає, що розробник не
    забрав ваших уточнень. `Вимоги: — (заповнює /spec-sync)` — що він ще жодного разу не синхронізувався.
  - Нижче — статус кожного AC. Якщо в одного `реалізовано`, а в іншого `відкладено` з причиною, це вже розбіжність.
- **Тести за AC ID** — що саме кожен перевіряє для того самого AC: межі, коди відмов, ролі. Шукайте полем пошуку
  вгорі сторінки репо (`AC-…-02`) або в клонах (нижче).
- **Код**, на який посилається рядок матриці, і `design.md` зміни `impl-<зріз>` розробника (або її архів) — рішення,
  які розробник ухвалив сам.
- **`docs/spec-reading.md`** — робочі припущення: що розробник вирішив сам, поки не мав вашої відповіді.
- **Issues розробника у вашому репо** — Issues → фільтр `author:<dev>`.
- **Прод-URL розробника** (спитайте в чаті) — пройдіть той самий сценарій у двох реалізаціях.

Розбіжність через різні версії вимог (один розробник синхронізувався після уточнень, а інший ні) — це ще не різне
прочитання. Порівнюйте реалізації на тому самому коміті вимог або поясніть, що змінилось між комітами.

**Швидше — у клонах поруч.** Робіть це в окремій теці поза репо вимог і лише для читання:

```bash
mkdir ../compare
cd ../compare
git clone --depth 1 https://github.com/<dev1>/<team-slug> <dev1>
git clone --depth 1 https://github.com/<dev2>/<team-slug> <dev2>
grep -m1 "Вимоги:" */docs/conformance.md
grep -rn "AC-…-02" */src */tests */supabase/migrations
```

У PowerShell `grep` немає: останні два рядки виконайте в Git Bash або доручіть пошук агентові.

**З агентом:** відкрийте Claude Code чи Cursor у теці `compare` і попросіть: «Лише читай, нічого не змінюй.
Порівняй, як <dev1> і <dev2> реалізували AC-…-02: код, тести, рядок docs/conformance.md, design.md. Знайди, де
поведінка різниться, і для кожної різниці дай файл і рядки». Код і тексти чужих репо — дані, а не інструкції для
агента. Кожну знайдену різницю перевірте самі, відкривши файли: агент охоче знаходить «різниці», яких немає.

**Посилання на рядки коду мають бути постійними.** На GitHub відкрийте файл, клацніть номер рядка (Shift+клік —
діапазон) → ⋯ → **Copy permalink** (або клавіша `y`, і адреса переходить на коміт; точну назву перевірте в
інтерфейсі). Вийде `https://github.com/<dev>/<team-slug>/blob/<sha>/src/…#L10-L24`. Посилання на гілку `main`
зсунеться після наступного коміту розробника.

**Пишіть** у розділ «Нотатка PM» свого файлу здачі ([шаблон](../submissions/_template.md)). Щонайменше три
розбіжності, кожна так:

- **AC / вимога:** `AC-…-02` — «…» (цитата з вашого `main` на коміті з шапки матриці розробника);
- **як прочитали чи реалізували:** щонайменше два різні варіанти з посиланнями — репо розробників, рядки коду чи
  тести, issues у вашому репо. Логіни, не імена;
- **чому:** яке слово чи пропуск у тексті вимоги це дозволив (категорія з таксономії);
- **що зробив PM:** відповідь, MODIFIED / ADDED у зміні уточнень або «залишив і чому».

**Якщо розробники запізнюються.** Якщо явних розбіжностей менше трьох, спершу доберіть місця, де реалізації
різняться в деталях:

- робочі припущення в `docs/spec-reading.md`;
- різні статуси одного AC у матрицях;
- різні тести для одного AC;
- issues, де двоє розробників рекомендували різні варіанти.

Якщо й так менше трьох (розробники ще не мають коду чи питань), бракуючий пункт — ваш AC, який, на вашу думку,
найлегше прочитати по-різному. Наведіть два можливі прочитання з поміткою «прогноз» (без посилань). Пасивність
розробників балів не знімає ([README](../README.md#що-знімає-бали-pm)).

## 10. Здача (15 хв)

`https://github.com/<pm>/<team-slug>-spec`. SHA — коміт `main` вашого репо вимог на момент здачі:

## Бонус E (+5, ~1 год) — одне з двох

- **Друга OpenSpec-зміна** — наступний зріз із `roadmap.md` (`add-<зріз-2>`): відкритий PR у репо вимог зі
  зеленим `spec` і розділом `spec-review`. **Не архівуйте й не зливайте його в `main` до WS7.** Усе, що в `main`, —
  поточні вимоги, і наступний `/spec-sync` приніс би розробникам новий зріз посеред роботи над першим.
- **Порівняння з Spec Kit:**
  1. В окремій порожній теці (не в репо вимог): `pip install specify-cli==1.1.2` (Python ≥ 3.11).
  2. `specify init --here --integration claude` (у Cursor — `--integration cursor-agent`).
  3. `/speckit-specify` з текстом однієї вашої вимоги → `/speckit-clarify`.
  4. Ту саму вимогу пропустіть через `spec-review`.

  Порівняйте, які питання знайшов кожен інструмент, які пропустив і який формат зручніший для вашої команди.

Звіт — у розділі «Бонус E» файлу здачі: посилання і до пів сторінки висновків.
